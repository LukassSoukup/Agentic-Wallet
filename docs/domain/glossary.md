# Glossary (ubiquitous language)

Draft from [PROJECT_BRIEF.md](../../PROJECT_BRIEF.md) and [docs/architecture/](../architecture/README.md). It gets refined in T-003.

- **Agent**: an instance of our shopping agent for one user (one per purpose), with an identity, a status and bound mandates. It searches, builds carts and proposes purchases. It can't pay without a Decision and never holds a payment token, a saved payment method or a provider key.
- **Agent harness**: our runtime around the user's chosen LLM: chat, shopping tools, mandate drafting, memory, trace. Untrusted; it reaches the control layer only through the control MCP server and admitted merchants' catalogues only through the connector gateway; it connects no other server and holds no merchant account.
- **Harness fence**: the harness connects exactly two MCP servers, ours, at configured addresses and refuses to start with any other; its web access is `GET` only through an egress proxy; an egress policy allows nothing else; it never holds a merchant account, a payment token or a saved payment method ([ADR-0008](../adr/ADR-0008-merchant-connectors-and-the-connector-catalogue.md)).
- **Merchant connector**: an operator-admitted integration with one merchant's own API or MCP server, described by a connector manifest; its discovery-class tools run through the connector gateway, its account-, quote- and order-class tools in the backend only, behind the `MerchantCatalogue`, `MerchantAccount` and `Checkout` ports. Not to be confused with a shop's **discovery document**.
- **Connector manifest**: the versioned, security-reviewed description that admits a connector: origin, endpoints and authorization server, the canonicalised tool objects by hash, each tool's class, OAuth scopes, argument and output schemas and caps, the attributes the merchant settles, the allowance per weighed line and whether fees and deposits are in the quote, that the merchant accepts and looks up our order reference, how the payment method on file is read, how its charges appear and the authorisation lag, the merchant's terms, an approval expiry. Drafted by the merchant or us; only the reviewed version is admitted.
- **Admission**: the operator's act of accepting a manifest version into the catalogue in the operator console, audited; with approval, enablement, suspension and expiry it forms the connector's state.
- **Connector catalogue**: the admitted manifests; the operator enables a subset for the deployment; the user turns individual connectors on and off per agent instance in the app. Turning one on is never a permission to buy. Users cannot add servers.
- **Tool class**: what a connector tool can do and who may call it: *discovery* (search and read the catalogue; the agent, through the gateway, anonymously), *account* (past orders, the order record by our reference, the payment method on file; the backend), *quote* (slots, a quote, a slot hold; the backend while gathering evidence, never a payment), *order* (place the order on a quote; the backend, from a checkout attempt for an APPROVE). Account administration is never in a manifest. Distinct from the evidence tiers.
- **Discovery tool**: a discovery-class tool as the harness sees it: the manifest's stored definition, served by the gateway, with capped arguments and untrusted output.
- **Connector gateway**: the boundary deployable that exposes admitted connectors' discovery tools to the harness, checks each call with the backend, enforces the manifest's schemas and caps, verifies the tool hash, drops a merchant's instructions, prompts and notifications, calls merchants anonymously through its own egress fence and logs every call; stateless, no business logic.
- **Account link**: one OAuth consent per cardholder and connector, given from the cardholder app with the manifest's scopes (PKCE, state, issuer check, exact redirect URI); the token is kept by `payments` under a key per link wrapped by the cardholder's key, never in an event; ended by unlink, operator disable or manifest expiry, with a resolution-only use until every attempt and reconciliation read is final. A toggle off or an agent stop only blocks an instance's use of it. Naming the linked account in a mandate is a loosening.
- **Quote (connector)**: the priced answer a connector gives the backend for exact lines, the picked slot and the profile's delivery address; the second source of tier-1 evidence. An order is placed on exactly that quote, idempotent on our order reference.
- **Order reference**: our idempotency key sent with a connector order; the merchant treats a repeat as the same order and lets us look the order up by it, which is how `UNKNOWN` and `PENDING_USER` are resolved.
- **Slot pick / slot hold**: `payments` lists the merchant's delivery slots inside the mandate's window and a pure rule in `control-core` picks one (earliest, then cheapest); a hold the merchant puts on it has an expiry that bounds the step-up like a session's. The agent never proposes a slot.
- **Ceiling**: `quoteTotal + Σ round(weighedLinePrice × allowance) + fees + deposits`, a pure function in `control-core` over components `payments` gathers from the quote and the manifest, half-even to 2 dp at each step. The hard amount rule and the reservation use it; reconciliation checks the billed amount against it.
- **One-line mode**: a connector order paid with the card on file at the merchant, so only the decision and the step-up stand between the agent and the charge (no provider token limits it); the bank-issued agent card that once covered such orders moved to banks later ([ADR-0010](../adr/ADR-0010-standalone-app-and-provider-payment-tokens.md)); allowed only by an explicit `settings` choice, labelled "one line of defence" wherever it shows, announced to linked users when it changes.
- **Substitution policy / slot window / minimum order**: typed facts for delivery merchants: the mandate's substitution policy (none, or same category at or below the line price), the mandate's slot window, and the manifest's minimum order (unmet is DECLINE).
- **Merchant-derived list**: a standing mandate's item requirements built by a fixed rule from the account class (items ordered in at least `k` of the last `n` orders), confirmed by the user; a hard caution rule gives STEP_UP with its own reason code until a purchase under that mandate version has completed, and the first due run is at confirmation.
- **Control MCP server**: the thin, stateless door from the agent harness to the control backend; a fixed list of typed tools. Confirming, approving and answering step-ups are not among them.
- **Agent trace**: the searches, pages read, candidates and reasons behind a proposal. Untrusted data, kept for the audit export; it can only add caution.
- **Mandate**: the user's rules for what agents may do. Written in plain language, compiled into structured rules, shown back and active only after confirmation. Can be tightened at any time, never loosened silently.
- **Mandate compiler**: an LLM-guided conversation that helps the user state their rules, asks clarifying questions, and compiles the result into structured hard rules (the mandate draft). It's an authoring aid only. It never takes part in a decision, and its output has no effect until the user confirms it.
- **Mandate draft**: a compiled but not yet confirmed mandate. It has no effect. It carries two states: **enforceable**, the backend's fixed checklist that every fact the rules need is present (missing items are returned by name), and **ready**, the agent's own judgement that it understands the request well enough to search accurately. Neither is a permission; only the user's confirmation makes a mandate.
- **Mandate readjustment**: after repeated declines for one reason under a mandate version, or searches that find nothing fitting, the agent shows the user what happened (the declines' amounts and reasons from the backend; any web price labelled merchant-reported and unverified) and offers a new draft; the change goes through the version diff and the confirm screen, loosening shown as such.
- **Purchase proposal / attempt**: an order an agent asks the control layer to approve: merchant, lines (item ids or item specs) with quantities, a `purchaseKey`, and the agent's own (untrusted) description. Never personal data.
- **Item spec**: a typed description of what to buy where the merchant sells offers rather than catalogue items (a flight: origin, destination, local date, passenger count, cabin), from a closed set of categories with validated values; `payments` resolves it against the merchant's offers and a pure rule picks among the matches.
- **Profile**: the cardholder's buyer, traveller and delivery entries and notification channels, versioned, edited only in the app; a mandate names the entries it may use, a decision records the version it was made with, and only version ids leave the `profiles` module.
- **Standing mandate**: a confirmed mandate with a run frequency and a purchase count, run without the user in chat (a price watch, "look every morning"); it is **fulfilled** when the count is reached.
- **Due run / run claim**: one scheduled run of a standing mandate, kept by `agents`; the harness runtime claims it once and receives the run token for it.
- **Watch**: the harness module that runs standing mandates; its price check is advisory, the backend decides on the merchant's cart.
- **Merchant cart**: the priced cart a shop returns through an agent checkout session (UCP, ACP) at its own endpoint, fetched by the backend, with the **merchant-signed checkout** (UCP checkout JWT) where the protocol provides one, verified and stored as tier-1 evidence. With the connector quote, the only source of binding cart facts.
- **Cart evidence tiers**: 1 the merchant cart or the connector quote; 2 product records the backend fetched from the merchant; 3 what the agent says. Auto-purchase needs tier 1 with every requirement settled by fixed rules ([ADR-0007](../adr/ADR-0007-cart-evidence-and-auto-purchase.md)).
- **Checkout session**: a shop-side session opened by the backend through an agent checkout protocol (UCP, ACP) at the endpoint the shop's discovery document names; it holds the cart, the shipping options and its expiry, and is completed with the payment token.
- **Control layer**: the deterministic decision engine plus security checks between agents and payment.
- **Decision**: `APPROVE`, `DECLINE` or `STEP_UP`, always with reasons. Logged append-only.
- **Step-up**: a question to the user in the app for unclear cases (missing details, possible duplicate, split order). It doesn't count toward limits until approved.
- **Risk signal**: an optional model output that may make a Decision more cautious, never less.
- **Untrusted text**: any text from merchants or agents (descriptions, item details). It is data, never instructions.
- **Base currency**: the user's own currency, a per-user rule input held in `profiles` and recorded in every `DecisionInput`. Each user has one, set at sign-up from their location (EUR by default) and changeable by the user; a change applies from the next budget period. A mandate's amounts keep the currency the user confirmed them in: its budget periods count in that currency, each purchase converted into it at the decision's rate (the foreign-currency margin on the cart side only), so changing the base currency never changes a confirmed mandate; the user drafts a new version through the confirm screen if they want one. Mandates and search are never restricted to one currency: before every comparison, amounts are converted into the currency of the limit they are compared with (the mandate's confirmed currency; the base currency for the global budget and for new mandates; invariant 6), and the user always sees the shop's own price and charge currency, a converted figure only labelled as the rules' check ([ADR-0010](../adr/ADR-0010-standalone-app-and-provider-payment-tokens.md), superseding the per-deployment setting of [ADR-0009](../adr/ADR-0009-tech-stack-revision.md) B5). The leash test pack uses CHF (see [starting-dataset](../data/starting-dataset.md)).
- **Route / routing**: which of the user's saved payment methods pays (for a connector order: the linked account and the payment method on file there), chosen by fixed rules in `payments` before the checkout session from the mandate's allowed methods and the user's preference order; recorded and re-validated by the decision and the step-up re-check, which can only decline it, and again when the attempt leaves `CREATED`. No route means DECLINE.
- **Reconciliation**: matching the decision and its token terms against the provider's token events and the shop's order record; mismatches we can see open a case; the blind spots (the amount billed in the card's currency, refunds, chargebacks, charges outside our token) are stated in the app.
- **Saved payment method**: a card or wallet (card, Google Pay, Apple Pay, Link, Klarna) the user saved through the payment provider's own form in our web app; we hold only the provider's reference with its display data (brand, last four digits, expiry), never card data; ordered by preference; can be blocked or removed at once. A mandate names the methods it may pay with. Crypto wallets are a later feature (N6). (Supersedes the card "enrolled" with a network.)
- **Payment provider**: the third party through which a token is issued on the user's saved payment method and the shop charges it (Stripe first); it holds the card data and moves the money from the user's bank to the shop, never through us.
- **PaymentProvider (port)**: `payments`' port to the provider: save a payment method (the provider's own form; we keep the reference), issue a scoped payment token, revoke it, read its state. One adapter now (Stripe Shared Payment Tokens) and a simulator; network agent tokens through a partner and Google Pay are later adapters. Our key for it is restricted: no charge, refund or payout rights.
- **Payment token**: the provider's scoped, revocable token issued after an APPROVE on the routed saved payment method (a Stripe Shared Payment Token first), limited by the token terms; at most one per decision (idempotency key from the attempt id), deactivated after its first confirmed use. Its id stays on the checkout attempt, never in an event, a log or the harness. The provider's enforcement of its limits is the second line of defence, set by us and described as such. (Replaces the network's single-use credential.)
- **Token terms**: what a payment token allows, a pure function of the decision stored in its `DecisionInput`: the seller's provider identity from the merchant directory, a maximum amount equal to the approved cart total in the cart's currency, that currency, and an expiry at the earlier of the stored checkout session expiry and the decision time plus the attempt window from `settings`. Owned by `payments`; never widened. (Replaces the **pre-approval**.)
- **Attempt window**: the `settings` value bounding a payment token's life after its decision.
- **Dead token**: a token the provider reports revoked, deactivated or expired; only then may a reservation be released, so budget never frees while money can still move.
- **Unexpected token usage**: a use of a token the attempt does not expect (a second use, a use after the attempt was cancelled or failed, an amount above the terms, a token we hold no attempt for); recorded as an event, opens a case, never changes the ledger silently.
- **Discovery document**: the protocol's fixed document at a shop's HTTPS origin (UCP `/.well-known/ucp`, or the ACP equivalent), fetched by the backend for the domain the agent named, under the fence; the only source of the shop's checkout endpoints and the seller's provider identity, never a session response, a page or the agent.
- **Merchant scan**: the harness's look-up of reviews and rating for a shop the user never bought from through us; untrusted text that may order results and add caution, shown to the user, never a permission.
- **Shop history**: the backend's record of the shops each user bought from successfully, a shop keyed by its domain together with the seller's provider identity from its discovery document (a change of either is a new shop); the first purchase by a user at a shop new to them is at least STEP_UP (a fixed caution rule).
- **Provider webhook**: the provider's signed event (token `requires_action`, `active`, `used`, `deactivated`), received on one public path of `control-backend`, signature-verified, deduplicated by event id and recorded insert-only; a trigger, while a release rests on a state read. Shop order webhooks (UCP, ACP) are recorded the same way as merchant-reported, untrusted data.
- **Reservation**: the ledger's hold of an approved amount against a budget period; it becomes counted when the checkout completes and is released when it fails or is cancelled, for a token purchase only once the token is dead.
- **Budget period**: one row per budget and period in the ledger, holding reserved and counted totals in one currency (a mandate budget's in the mandate's confirmed currency, the global budget's in the user's base currency current when the period opens), each purchase converted into it at the decision's rate; locked while a decision that may reserve runs.
- **Merchant directory**: `payments`' list of shops with an agent checkout path: protocol, checkout endpoints and the seller's provider identity from each shop's discovery document, or the connector and its endpoints from an admitted manifest, plus the structured attributes each settles. Filled from discovery documents fetched for agent-named domains under the fence, the admitted connector manifests and, in the PoC, the demo shop; never from the agent.
- **Global budget**: one budget all agents draw from, with its own period; a purchase may not exceed the smaller of it and the agent's own remaining limit. Each of its periods counts in the user's base currency current when the period opens, so a change of base currency applies from the next period ([ADR-0010](../adr/ADR-0010-standalone-app-and-provider-payment-tokens.md)).
- **Intent check**: compares the user's rules with the proposed purchase, reading untrusted text; verdict matches, deviates or uncertain; it can only make a decision stricter.
- **Suspicious-text flag**: set when untrusted text contains instructions; raises the decision to at least STEP_UP.
- **Mismatch case**: opened when a token event or the shop's order record differs from what was approved (a different amount where the event carries it, a second use, a use or an order with no decision, a missing confirmation); holds expected against actual and a drafted dispute evidence package the user files with their bank, never filed automatically.
- **Audit log**: append-only record of every Decision with its inputs and reasons, which can be replayed.
- **Pre-approval** (superseded): the bank-first design's record a hook responder matched an authorisation against; replaced by the **token terms** ([ADR-0010](../adr/ADR-0010-standalone-app-and-provider-payment-tokens.md)).
- **Checkout attempt**: the persisted state of paying for one approved decision (`CREATED`, `TOKEN_ISSUED`, `COMPLETING`, `PENDING_USER`, `COMPLETED`, `FAILED`, `UNKNOWN`, `CANCELLED`); at most one token per decision; `PENDING_USER` is a 3-D Secure challenge at redemption; `FAILED` and `CANCELLED` are entered only once the token is dead; `UNKNOWN` is announced by its own event.
- **DecisionInput**: everything a decision was based on, stored with it; replaying it through the pure core must return the same decision.
- **Agent session token**: signed by the backend, short-lived, bound to cardholder, agent instance and audience; the only way an agent's identity reaches the control layer during a chat.
- **Agent run token**: the same, minted for one claimed run of a standing mandate, bound also to the mandate and the run id and limited to proposing, reading and sending the trace; short-lived.
- **Agent-instance credential**: the harness's only credential towards the control layer, long-lived; it can only claim due runs of its own agent instance.
- **Foreign-currency margin**: `converted × rate`, with a rate ≥ 0 from `settings`, added to a converted amount before it is compared with a limit, because the user's bank bills at its own rate; it can only make the amount rule stricter. An amount already in the currency of the limit it is compared with has margin zero (ADR-0010).
- **Strict / inclusive limit**: the mandate's comparison operator for its amount limit: strict passes when `converted + margin < limit`, inclusive when `converted + margin ≤ limit`; a failure is DECLINE in both.
- **Purchase count**: how many purchases a mandate allows in its lifetime (one for a one-shot watch); kept in the ledger as reserved and counted purchases under a per-mandate lock row.
- **Hook, hook responder, shadow mode** (superseded): the bank processor's real-time authorisation call and the service that answered it, removed with the bank on 2026-11-19; a bank-side check may return with banks later as a third line consuming the token terms ([ADR-0010](../adr/ADR-0010-standalone-app-and-provider-payment-tokens.md)).
- **Enrolment** (superseded): registering a card with a network for an agent; replaced by saving a payment method through the provider.
- **Visa Intelligent Commerce, Mastercard Agent Pay** (not integrated): the networks' agent payment programmes; in Europe only bank-led pilots, so not integrated directly; their agent tokens may sit underneath the provider's token, and may become a later `PaymentProvider` adapter through a partner.
- **3-D Secure**: the user's bank's challenge when a shop charges a token; the user completes it in our web app through the provider's own SDK; unanswered, the purchase lapses.
- **Banks later**: a later channel in which a bank offers the app to its customers; nothing bank-specific is built now.
- **Outbox**: events stored as rows in the same transaction as the change that caused them, then delivered at least once to idempotent listeners.
- **Intent model**: a model that answers fixed, typed questions about merchant product text, outside the pure core; it can find a problem, never clear one.
- **Idempotency key**: identifies repeat deliveries of the same request, so they yield the same outcome once: the `purchaseKey` per agent instance for a proposal, a client-generated id per owner for a call that creates something, the natural key for a call that changes something ([ADR-0009](../adr/ADR-0009-tech-stack-revision.md)).
- **Link key**: the key one account-link token is encrypted under (one per cardholder and connector), wrapped by that cardholder's **cardholder key**; the cardholder keys are wrapped by the **deployment key-encryption key**, which lives outside the database. Deleting a link key unlinks one connector; deleting a cardholder key erases all of that cardholder's links ([ADR-0009](../adr/ADR-0009-tech-stack-revision.md)).
- **Error catalogue**: the list of named errors with their stable problem `type` URIs, kept in `control-api`; every problem response and MCP tool error names one of them ([ADR-0009](../adr/ADR-0009-tech-stack-revision.md)).
- **Configuration versus settings**: configuration is topology and plumbing (addresses, certificates, pool sizes, timeouts), fixed per deployment and changed by redeploy; `settings` are the parameters the operator changes at runtime per deployment, stored, versioned and audited, and the only path by which a deployment parameter reaches a decision; per-user rule inputs such as the base currency come from `profiles` and are recorded in the `DecisionInput` ([ADR-0009](../adr/ADR-0009-tech-stack-revision.md), [ADR-0010](../adr/ADR-0010-standalone-app-and-provider-payment-tokens.md)).
