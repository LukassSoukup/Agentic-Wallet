# ADR-0008: Merchant connectors and the connector catalogue

## Context
[ADR-0007](ADR-0007-cart-evidence-and-auto-purchase.md) lets a purchase go ahead only on a priced cart from a network agent checkout session, so a merchant without one gets "can't buy here". An end-to-end walkthrough of a grocery order on 2026-10-31 (a Czech online grocer that publishes its own MCP server, with the user's account and card on file) showed two things. First, the design had no sentence forbidding the harness from connecting a third-party MCP server or holding a merchant account session; had someone connected such a server, a prompt-injected agent could have called its ordering tool and paid with the card on file, outside every decision, hook and reconciliation. Second, the brief excluded the merchant's own ordering API along with form filling, although an API order placed by the trusted backend on a priced quote is neither form filling nor untrusted. The user wants such merchants reachable, under the condition that what gets connected is approved by someone other than the user, and decided on 2026-10-31: **users cannot install their own MCP servers; they choose from a catalogue, turn individual connectors on and off, and link their own account where a connector needs one.** This ADR records that decision and what it takes. It supersedes the part of ADR-0007 that ties binding evidence to a network checkout session and amends [ADR-0006](ADR-0006-architecture-style-and-module-cut.md) (a new boundary deployable, a fence on the harness, new facts in `payments`, `settings` and `agents`). Reviewed the same day; the review's findings are folded in.

## Options considered
1. **A catalogue of operator-admitted merchant connectors; the user turns connectors on and links their own account; catalogue reads through a boundary gateway, account, quote and order calls in the trusted backend (chosen).**
2. Let the user connect any MCP server to the harness: a tool description is prompt text into the model, so each server is a prompt-injection and exfiltration channel a cardholder cannot judge; a server can change its tools after approval (`tools/list_changed`), and MCP's sampling and elicitation let a server use our model or question our user. A read-only variant has the same channels. Rejected.
3. Keep ADR-0007 as it is and reach such merchants through the networks only: safe, but leaves groceries and most of the Czech market as "can't buy here" indefinitely, with no second path.
4. Let the harness call the merchant's API directly with the user's token: the agent would then hold an ordering credential. Rejected: it reopens the hole the fence closes.

## Decision
- **The harness fence.** The harness connects exactly two MCP servers, `control-mcp` and the connector gateway, both ours, at addresses that are deployment configuration; it refuses to start with any other. It never holds a merchant account session, token or card. Its web access is read-only by mechanism: `GET` only, no cookies or credentials, through an egress proxy that refuses private address ranges, and an egress policy that lets the harness reach only the LLM gateway, the two servers and that proxy. Nothing in a conversation, a tool result or the user's settings can add a server.
- **Admission is the operator's act, never the user's.** A merchant integration enters the catalogue only as a versioned **connector manifest**: the merchant or we draft it, we security-review it, and only the reviewed version is admitted. Standalone, we admit it; in a bank, the bank approves it in the console. `payments` owns admission, suspension and expiry; `settings` owns the bank's approval and enablement; every one of these changes is audited. Per deployment the bank enables a subset of the catalogue. The manifest pins the merchant's HTTPS origin, each endpoint and its authorization server (issuer); the canonicalised tool objects (name, title, description, input and output schema, annotations) by hash; for each tool its **tool class** (below); the minimum OAuth scopes for the account, quote and order classes (discovery is anonymous and needs none): never a scope that writes payment methods, addresses or the password, or reads addresses; reading the payment method on file is limited to the last four digits and the network, for the route rule (a merchant that offers only a username and password is not connectable); per-argument schemas with enumerated or numeric fields where the merchant allows and a length cap from `settings` on every free-text field; output caps and schemas, every free-text field typed `UntrustedText`, personal fields dropped; which cart attributes the merchant settles as structured data; the allowance per weighed line as a percentage, and whether fees and deposits are inside the quote or declared as maxima; that the merchant accepts our order reference, treats a repeated order with the same reference as the same order, and looks an order up by it (an admission requirement); how the payment method on file is read (last four digits and network) and how the merchant's charges appear in authorisation and clearing, with the usual lag between order and authorisation; the merchant's terms for third-party automated ordering; an approval expiry. The gateway and the backend serve the harness and the core the **stored** tool definitions, never the live ones; they drop the server's `initialize` instructions, prompts, resources and logging or progress notifications; they verify the live hash at every session and on `notifications/tools/list_changed`; a drift **suspends** the connector (a state the decision and the gateway check; user toggles and account links are untouched, so re-approval restores service without the user doing anything). The backend's and the gateway's MCP clients advertise no sampling, elicitation or roots.
- **Four tool classes, by what a tool can do and who may call it.** *Discovery* (search and read the catalogue): called by the agent through the **connector gateway**, a stateless boundary deployable with no database that reads the manifests the backend publishes, exposes only the discovery tools of connectors the caller's agent instance has on (checked with the backend per call, cached for seconds), enforces the argument and output caps, logs every call to the ingest, and calls merchants anonymously: no user token of any kind in v1. *Account* (past orders, the order record by our reference, the payment method on file): called by the backend only, through a `MerchantAccount` port, with the user's token; nothing from it reaches the harness. *Quote* (a priced quote for exact lines, the delivery slot, a slot hold): called by the backend only while it gathers evidence for a decision, rate-limited per mandate like a checkout session, a side effect at the merchant but never a payment. *Order* (place the order on a quote): called by the backend only from a checkout attempt that exists for an APPROVE. Account-administration tools (address, payment method, password) are never in a manifest.
- **Turning a connector on is not a permission.** The user turns connectors on and off in the cardholder app, per agent instance (`agents` holds the toggles; `get_agent_configuration` tells the harness which discovery tools it may use). With a discovery connector on, the agent can search that merchant. Buying there needs, as hard rules with their own reason codes: the connector admitted and enabled and not suspended; the toggle on for this agent instance; the cardholder's account linked; **and the confirmed mandate naming that linked account** (adding it is a loosening, so it passes the confirm screen); then a decision on a binding quote. Invariant 4 is unchanged.
- **The user links only their own account, in the app.** An account link is one OAuth authorization-code consent per cardholder and connector, started from the cardholder app, never from the agent or through a tool: PKCE, a `state` bound to the app session and checked at the callback, issuer identification against authorization-server mix-up, the exact registered redirect URI, the scopes the manifest fixes and no others, refresh-token rotation. `payments` keeps the token under a key per cardholder and connector, wrapped by the cardholder's key; it is never in an event, a read model or a log. A toggle off or an agent stop only blocks the link's use by that instance; the link itself ends by the user's unlink, the bank disabling the connector, or the manifest's expiry. Ending a link stops new quotes and orders at once, keeps a **resolution-only** use of the token until every checkout attempt and reconciliation read for that link is final or, at the latest, until the last order's slot end plus a reconciliation window from `settings`, then revokes it at the merchant where the merchant offers revocation and deletes it; a case still open after that runs on the stored order record only. A proposal at a merchant whose ordering connector is not linked is DECLINE with the reason "link your account in the app first"; the app, not the chat, offers the link.
- **Binding evidence from a connector: the quote.** Tier 1 of ADR-0007 gains a second source: a **priced quote the backend obtained from an admitted connector** for exactly the proposal's lines, the delivery slot `payments` picked and the delivery address from the profile version the decision records. The agent proposes no slot: `payments` lists the merchant's slots inside the mandate's window and a pure rule in `control-core` picks one (the earliest, then the cheapest, inside the window); every candidate goes into the `DecisionInput`. The quote binds the same way a session cart does. Auto-purchase through a connector further requires that the order is bound to the quote: a quote id the merchant binds to its prices with an order idempotent on our reference, or a two-phase create-and-confirm order. A merchant that offers neither is not admissible for ordering: the backend never writes into the user's own cart, and such a merchant is DECLINE "can't buy here". Where the final amount can differ from the quote, the decision approves a **ceiling**, a pure function in `control-core` over components `payments` gathers: `ceiling = quoteTotal + Σ round(weighedLinePrice × manifestAllowance) + fees + deposits`, where fees and deposits are the quote's when the manifest says the quote includes them, else the manifest's declared maxima; every product is rounded half-even to 2 dp; the substitution policy adds nothing because the only policies are *none* and *same category at or below the line price*. The hard amount rule compares the ceiling with the limit; the ledger reserves and the pre-approval is written at the ceiling; `reconciliation` matches the cleared amount at or below the ceiling and the merchant's invoice lines against the approved lines. Substitution policy, delivery slot window and the merchant's minimum order are typed mandate and manifest facts; an unmet minimum order is DECLINE; a slot hold's expiry feeds the step-up expiry like a session's.
- **Payment through a connector.** The order is paid with what is on file at the merchant, or with a network credential where the merchant's order API accepts one (T-005 and T-038 find out). In a bank deployment the user puts a bank-issued **agent card** on file: a card for agent orders only, enrolled through us, which the hook responder covers by its card id at the processor, so the pre-approval written at the ceiling is enforced, and a manual order on that card is declined in enforcing mode (the user is told so when the card is issued). `payments` reads the payment method on file (last four digits and network) through the account class while gathering evidence, and a hard route rule compares it with the enrolled agent card; it reads it again when the attempt enters `COMPLETING`, and a card that no longer matches fails the attempt with "card on file changed". A mismatch at decision time is DECLINE unless `settings` allows the **one-line mode**, in which the decision and the step-up are the only line of defence. That mode exists only by the operator's explicit setting, is labelled "one line of defence" wherever it shows, is announced to every linked user when it is turned on, and is the user's decision for the standalone product. The pre-approval window and the `UNKNOWN` resolution window of a connector order run to the slot's end plus the manifest's authorisation lag. The checkout attempt for a connector order skips `CREDENTIAL_REQUESTED`, goes `CREATED → COMPLETING`, carries our idempotency key as the order reference, resolves `UNKNOWN` or `PENDING_USER` by looking that reference up, never places an order again blindly, and, when a lookup is impossible, stays `UNKNOWN` and opens a mismatch case rather than failing silently.
- **"My usual groceries" stays a preference.** A mandate must name items or categories; "what I usually buy" alone is a draft-validation error that leads to a question (since 2026-10-31 a missing scope item of the enforceable checklist, T-003). For a standing mandate the backend derives a list from the account class by a fixed rule (merchant item ids and quantities ordered in at least `k` of the last `n` orders, both from `settings`; no model), the user confirms it as item requirements, and the mandate records that the list was merchant-derived. A hard rule gives STEP_UP with its own reason code, not mapped through the "when unsure" policy, while that mandate version has no completed purchase in the ledger (the ledger records the mandate version on each counted purchase); `agents` makes the first due run due at confirmation, so the user answers it in the app. Past orders are never a rule input beyond that.

## Consequences
- \+ Groceries and other merchants with their own API become buyable without the agent ever holding an ordering credential; a prompt injection can still at most propose a purchase.
- \+ The catalogue is the bank's third-party-risk control: every integration is a reviewed, versioned, expiring document, and a merchant can draft one itself against the published manifest format, so reach grows through merchants' work as well as the networks' programmes.
- \+ Turning a connector on is a one-tap setting with a plain description of its tool classes; nobody pastes a server URL.
- − The brief's "checkout only through the networks' agent protocols" is widened to "or through an admitted connector called by the trusted backend"; form filling and browser automation stay out. The user changed the brief on 2026-10-31.
- − Without an agent card, a connector order has one line of defence instead of two or three. The bank variant is the reference; standalone is labelled.
- − A discovery query is free text within a cap, so a compromised harness can leak conversation text through it, as it can through a web search; the harness holds no card or personal checkout data, which bounds the damage.
- − A fifth JVM (the connector gateway). T-037 measured both ([07-walking-skeleton](../architecture/07-walking-skeleton.md)): hosted inside `control-mcp` it costs at most about 16 MB resident, as its own JVM 182 MB; the Pi can afford either, so it stays inside the `control-mcp` process behind its own listener and its own client certificate towards the backend, limited to the connector endpoints, until epic K needs it apart.
- − The ledger counts the ceiling; the difference to the billed amount, refunds and deposits returning budget are open items.
- − Each connector adds a merchant-specific adapter behind the `Checkout`, `MerchantCatalogue` and `MerchantAccount` ports plus a manifest to operate; drift suspends it.
- − Whether ordering on a user's linked account with a card on file makes us a payment initiation service or a similar regulated party is a legal question the user takes to counsel before the first bank; nothing here assumes an answer.
- Supersedes ADR-0007's "no checkout session, no purchase": it becomes "no binding quote, no purchase". Amends ADR-0006 as listed in its 2026-10-31 bullets.
