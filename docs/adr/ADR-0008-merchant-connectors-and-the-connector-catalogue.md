# ADR-0008: Merchant connectors and the connector catalogue

## Context
[ADR-0007](ADR-0007-cart-evidence-and-auto-purchase.md) lets a purchase go ahead only on a priced cart from a network agent checkout session, so a merchant without one gets "can't buy here". An end-to-end walkthrough of a grocery order on 2026-10-31 (a Czech online grocer that publishes its own MCP server, with the user's account and card on file) showed two things. First, the design had no sentence forbidding the harness from connecting a third-party MCP server or holding a merchant account session; had someone connected such a server, a prompt-injected agent could have called its ordering tool and paid with the card on file, outside every decision, hook and reconciliation. Second, the brief excluded the merchant's own ordering API along with form filling, although an API order placed by the trusted backend on a priced quote is neither form filling nor untrusted. The user wants such merchants reachable, under the condition that what gets connected is approved by someone other than the user, and decided on 2026-10-31: **users cannot install their own MCP servers; they choose from a catalogue, turn individual connectors on and off, and link their own account where a connector needs one.** This ADR records that decision and what it takes. It supersedes the part of ADR-0007 that ties binding evidence to a network checkout session and amends [ADR-0006](ADR-0006-architecture-style-and-module-cut.md) (a new boundary deployable, a fence on the harness, new facts in `payments`, `settings` and `agents`).

## Options considered
1. **A catalogue of operator-admitted merchant connectors; the user turns connectors on and links their own account; catalogue reads through a boundary gateway, account, quote and order calls in the trusted backend (chosen).**
2. Let the user connect any MCP server to the harness: a tool description is prompt text into the model, so each server is a prompt-injection and exfiltration channel a cardholder cannot judge; a server can change its tools after approval (`tools/list_changed`), and MCP's sampling and elicitation let a server use our model or question our user. A read-only variant has the same channels. Rejected.
3. Keep ADR-0007 as it is and reach such merchants through the networks only: safe, but leaves groceries and most of the Czech market as "can't buy here" indefinitely, with no second path.
4. Let the harness call the merchant's API directly with the user's token: the agent would then hold an ordering credential. Rejected: it reopens the hole the fence closes.

## Decision
- **The harness fence.** The harness connects exactly two MCP servers, `control-mcp` and the connector gateway, both ours. It never connects a third-party server, never holds a merchant account session, token or card, and its web access is read-only search and page reads. Nothing a user does in the app can change that.
- **Admission is the operator's act, never the user's.** A merchant integration enters the catalogue only as a versioned **connector manifest** that we produce and security-review. Standalone, we admit it; in a bank, the bank approves it in the console, an audited `settings` change. Per deployment the bank enables a subset of the catalogue. The manifest pins the merchant's HTTPS origin and its authorization server; the exact tool list (name, schema and description) by hash; for each tool its **class** and **caller**; the minimum OAuth scopes (a merchant that offers only a username and password is not connectable); argument length and data-class caps (a structured query only; never chat text, memory or profile data); output caps and schemas, every free-text field typed `UntrustedText`; which cart attributes the merchant settles as structured data and how its final amount can differ from the quote (weighed goods, substitutions, fees, deposits); how its charges appear in authorisation and clearing; the merchant's terms for third-party automated ordering; an approval expiry. A tool list whose hash drifts suspends the connector until it is re-approved; the check runs on every session. The backend's and the gateway's MCP clients advertise no sampling, elicitation or roots.
- **Three tiers, by what a tool can do.** *Discovery* (search and read the catalogue): called by the agent through the **connector gateway**, a stateless boundary deployable with no database that reads the manifests the backend publishes, allows only the discovery tools of connectors the caller has turned on (checked with the backend per call, cached for seconds), enforces the caps, logs every call to the ingest, and holds no user token unless the merchant issues a read-only one. *Account* (the user's past orders, favourites, saved addresses, store credit): called by the backend only, summarised into structured facts; nothing from an account reaches the harness except through a read-only tool that returns those facts. *Ordering* (quote, delivery slot, order): called by the backend only, after an APPROVE, exactly as it completes a network checkout session today. Account-administration tools (changing the address, the payment method or the password) are never in a manifest, and their scopes are never requested.
- **Turning a connector on is not a permission.** The user turns connectors on and off in the cardholder app, per agent instance (`agents` holds the toggles; `get_agent_configuration` tells the harness which discovery tools it may use). With a discovery connector on, the agent can search that merchant. Buying there still needs a confirmed mandate that covers the merchant and a decision on a binding quote; a mandate that names a linked account is a loosening and goes through the confirm screen. Invariant 4 is unchanged.
- **The user links only their own account, in the app.** An account link is an OAuth consent at the merchant, started from the cardholder app, never from the agent or through a tool, with the scopes the manifest fixed and no others. The token is kept by `payments` per cardholder and connector, encrypted at rest, never in an event, revoked when the user unlinks, turns the connector off or stops the agent, and expiring with the manifest's approval. A proposal at a merchant whose ordering connector is not linked is DECLINE with the reason "link your account in the app first"; the app, not the chat, offers the link.
- **Binding evidence from a connector: the quote.** Tier 1 of ADR-0007 gains a second source: a **priced quote the backend obtained from an admitted ordering connector** for exactly the proposal's lines, the delivery slot the mandate allows and the delivery address from the profile version the decision records. It binds the same way a session cart does. Auto-purchase through a connector additionally needs an order placed on exactly that quote: a quote id the merchant binds to its prices with an idempotent order call (preferred), a two-phase create-and-confirm order, or, as the last resort, a cart write followed by a version check at order time, with the race documented in the manifest. A merchant that offers none of these gives at most STEP_UP; the backend never writes into the user's own cart when a quote or order call exists. Where the final amount can differ from the quote, the decision approves a **ceiling**: the quote total plus the manifest's declared allowance per weighed line, the mandate's substitution allowance, fees and deposits. The hard amount rule compares the ceiling with the limit; the ledger reserves and the pre-approval is written at the ceiling; `reconciliation` matches the cleared amount at or below the ceiling and the merchant's invoice lines against the approved lines. Substitution policy (none, same category at or below the price, ask), delivery slot window and minimum order are typed mandate facts; an unmet minimum order is DECLINE; a slot hold's expiry feeds the step-up expiry like a session's.
- **Payment through a connector.** The order is paid with what is on file at the merchant, or with a network credential where the merchant's order API accepts one (T-005 and T-038 find out). In a bank deployment the user puts a bank-issued **agent card** on file, enrolled through us as a token reference, so the hook responder's scope covers it and the pre-approval written at the ceiling is enforced. Without an agent card the hook has no opinion on the charge and the decision plus the step-up are the only line of defence: that mode exists only when the operator sets `settings` to allow it, the setting is labelled "one line of defence" wherever it shows, and the user is told at the account link that the control layer cannot stop a charge it did not approve on that card. Standalone in the PoC runs in that mode, by the user's decision. The checkout attempt for a connector order skips `CREDENTIAL_REQUESTED`, goes `CREATED → COMPLETING`, carries our idempotency key as the merchant's order reference, resolves `UNKNOWN` by looking that reference up and never retries an order blindly, and enters `PENDING_USER` when the merchant requires the cardholder's authentication on a card-on-file order.
- **"My usual groceries" stays a preference.** In chat, the mandate is merchant, budget, category and slot window, and the quote is shown to the user as a STEP_UP. For a standing mandate, the backend summarises the user's past orders from the account tier into a list the user confirms as item requirements; the first run of such a list is a STEP_UP by a fixed rule (the first time the list meets prices, stock and fees), so it is started right after confirmation while the user is in the app. Past orders and favourites are ranking inputs, never rule inputs.
- **Spending insights from the bank's transaction history** (the user's note of 2026-10-31) are not decided here. The direction is recorded in the backlog: a backend module behind a `TransactionHistory` port, derived coarse facts only, raw lines never leaving the trusted zone or reaching a model, a caution-only use in decisions, opt-in per cardholder.

## Consequences
- \+ Groceries and other merchants with their own API become buyable without the agent ever holding an ordering credential; a prompt injection can still at most propose a purchase.
- \+ The catalogue is the bank's third-party-risk control: every integration is a reviewed, versioned, expiring document, and a merchant can prepare one itself against a published manifest format, so reach grows through merchants' work as well as the networks' programmes.
- \+ Turning a connector on is a one-tap setting with a plain description of its tier; nobody pastes a server URL.
- − The brief's "checkout only through the networks' agent protocols" is widened to "or through an admitted connector called by the trusted backend"; form filling and browser automation stay out. The user changed the brief on 2026-10-31.
- − Without an agent card, a connector order has one line of defence instead of two or three. The bank variant is the reference; standalone is labelled.
- − A fifth JVM (the connector gateway) on the Pi; in the PoC it may run inside the `control-mcp` process behind its own listener, which T-037 measures.
- − The ledger counts the ceiling; the difference to the billed amount, refunds and deposits returning budget are open items.
- − Each connector adds a merchant-specific adapter behind the `Checkout` and `MerchantCatalogue` ports plus a manifest to maintain; drift suspends it, so the catalogue needs operating.
- Supersedes ADR-0007's "no checkout session, no purchase": it becomes "no binding quote, no purchase". Amends ADR-0006 as listed in its 2026-10-31 bullets.
