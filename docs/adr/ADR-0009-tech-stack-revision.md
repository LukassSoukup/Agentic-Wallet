# ADR-0009: Tech stack revision and the conventions every deployable follows

## Context
[ADR-0001](ADR-0001-tech-stack.md) chose the stack for a 26-hour hackathon: one app container plus a database, a single user without authentication, teammates' laptops, an x402 crypto rail whose SDKs exist only outside Java, and event APIs unknown until the day. The product has changed since. It is an agent platform with a deterministic control layer, delivered to banks ([PROJECT_BRIEF.md](../../PROJECT_BRIEF.md)); it is built as a service-based system of five backend deployables and a web app ([ADR-0006](ADR-0006-architecture-style-and-module-cut.md), [02-system.md](../architecture/02-system.md)); and it admits merchant connectors with one OAuth account link per cardholder and connector ([ADR-0008](ADR-0008-merchant-connectors-and-the-connector-catalogue.md)). ADR-0006 already superseded ADR-0001's module layout. The user decided the stack on 2026-10-29. This ADR records each item of that decision with its reason, records the choices that were settled elsewhere and belong to the stack (one LLM gateway, the intent model per T-036, x402 out, generated UI as a reference only), and fixes the cross-cutting conventions that every deployable follows, so that the contracts of T-003 and the toolchain of T-008 have one place to point at.

What this ADR does not do: pin versions (T-008, on the Pi), write port contracts (T-003), choose the network adapters and their simulators (T-005), or set the coverage and mutation floors (the user, in T-008). Where [02-system.md](../architecture/02-system.md), [03-modules.md](../architecture/03-modules.md), [06-consistency.md](../architecture/06-consistency.md), ADR-0006 or ADR-0008 already fix a mechanism, this ADR cites it and does not restate it; where something is genuinely open it says so and the row is in [05-open-items.md](../architecture/05-open-items.md).

Constraints: the nine invariants and the quality bar in [CLAUDE.md](../../CLAUDE.md); development on a Raspberry Pi 5 with 16 GB that is also the home server, where four JVMs (five once the connector gateway leaves the `control-mcp` process), the simulators and PostgreSQL must fit; one developer with AI agents, so the stack must be one that agents reproduce reliably from current documentation; the same OCI images run in our EU cloud or inside a bank's perimeter, so nothing may depend on where it runs except configuration.

## Options considered
For each item where a real choice existed, the options and why the chosen one wins. Items the architecture already fixed (Spring Modulith, the outbox, no broker in v1, the Maven reactor layout) are cited in the decision and not re-argued here.

1. **Language.** Java 21 LTS (the broadest tool support today) or **Java 25 LTS (chosen, the user)**. Records, sealed types and pattern-matching `switch` are in both. What 25 adds and this project uses: compact object headers (JEP 519, turned on by a JVM flag), which cut heap per object on a memory-bound Pi; flexible constructor bodies (JEP 513), so a non-canonical record constructor or a class constructor validates its arguments before delegating to `this(...)` or `super(...)`; and one LTS line for the years the product takes to reach a bank. The [clean-code](../../.claude/skills/clean-code/SKILL.md) idioms are written for 25. The cost is tooling that lags behind a new class-file version; T-008 verifies it (consequences).
2. **Application framework.** Quarkus or Micronaut (less memory and faster start, which matters on the Pi) or **Spring Boot (chosen, the user)**. Spring AI with its MCP server and client, Spring Modulith's module verification and event publication registry, Spring Security's OAuth client and Boot's observability stack exist only here; the memory and start-time cost is measured in T-037 and capped per JVM.
3. **MCP implementation.** A hand-written JSON-RPC server (full control, more surface to get wrong), a Node sidecar for the MCP parts (a second runtime: the hackathon's trap again), or **Spring AI's MCP server and client over the official MCP Java SDK (chosen, the user)**. Transport: streamable HTTP for every server we run, never stdio (a stdio server is a child process of its client, on the client's host, which the trust zones forbid).
4. **Build.** Gradle with the Kotlin DSL (ADR-0001; faster incremental builds, but build logic is code, and code generated for a new Boot line drifts) or **Maven (chosen, the user)**: a declarative reactor whose module list is the layout of [03-modules.md](../architecture/03-modules.md), Spring's own documentation is Maven-first, one `./mvnw verify` is the build.
5. **Persistence.** Plain SQL through `JdbcClient` (ADR-0001: every mapping by hand), jOOQ (typed SQL, a code generator in the build), or **Hibernate/JPA in the persistence adapters only (chosen, the user)**. JPA removes the hand-written mapping cost for the many small aggregates; confined to adapters it leaves invariant 9 enforced by the compiler, and native SQL stays available in the same adapter where JPA fights the design (locks, upserts, the insert-only audit).
6. **Migrations.** Liquibase (XML or YAML change logs) or **Flyway with versioned SQL files (chosen, the user)**: plain SQL is what the PostgreSQL manual shows, reviewable line by line, and the insert-only grants and triggers of the audit are SQL anyway.
7. **Events between processes, when they come.** Kafka (a partition and ordering model, and a footprint, that nothing here pays for) or **RabbitMQ behind the same outbox (chosen, the user; ADR-0006)**, added only when a second process needs the events. In v1 there is no broker ([01-style.md](../architecture/01-style.md)).
8. **LLM access.** One SDK per provider (one key, one adapter and one review per vendor), Bedrock (a hackathon-time option that went with the event), or **one OpenAI-compatible gateway (chosen, already decided)**: OpenRouter in the PoC, the model id as configuration, the allowed list from `settings`, a fixture adapter, a spend cap per user; a bank replaces the base URL and key with its own gateway and nothing else changes.
9. **Frontend.** Thymeleaf with htmx (one toolchain, but the chat stream, the confirm screen and the step-up answer are app-like, and a bank embeds the UI as a separate deliverable), Next.js (a server runtime we do not need), or **React with TypeScript and Vite (chosen, the user)**. Generated UI stays a reference.
10. **Quality control.** Sonar in CI (the user): a self-hosted SonarQube (a server that needs memory the Pi does not have to spare, and one more thing to operate) or **SonarQube Cloud (chosen)**, free for a public repository, which this one is; the user's rule (2026-10-31): the cloud service while it is free, a self-hosted server deployed by the Pi admin agent otherwise.
11. **Service-to-service token format.** An opaque token with introspection (a round trip per call on the chat path), PASETO (fewer footguns, few Java libraries), or **a signed JWT (chosen)** whose claims 02-system already names; signed with a symmetric key while the backend is the only verifier, asymmetric with a published key set when a second verifier appears.
12. **Certificates for mutual TLS.** Public certificates (prove a host name, not a peer), a service mesh (sidecars on a Pi, and a bank's operations learning a mesh for five processes), SPIFFE (the same idea; adopt it if a bank runs one), or **a private certificate authority per deployment (chosen)**, loaded through Spring Boot SSL bundles from mounted files.
13. **The OAuth client for account links.** A purpose-built client over `RestClient` (fewer moving parts, every control re-implemented and re-reviewed) or **Spring Security's OAuth2 client (chosen)** with the manifest-fed registrations, our encrypted link store and the checks the library lacks added in front of the token exchange.
14. **Where secrets come from.** A secrets SDK in the code (ties the artefact to one store), `sops`-style encrypted files in the repository (secrets in git history), or **mounted files and environment variables named by Spring properties (chosen)**, filled by `.env` and compose in the PoC and by the deployment's secret store in cloud or bank.
15. **Error model.** Exceptions for everything (business failures and bugs look alike, and a wider `catch` hides both) or **result values for expected failures and exceptions for the unexpected (chosen)**, with RFC 9457 problem details at every HTTP edge.
16. **Observability.** Plain Prometheus client and ad-hoc logs, or **Micrometer with the OpenTelemetry bridge and Boot's structured logging (chosen)**: one instrumentation for metrics and traces, W3C trace context across the deployables, JSON logs a bank's collector ingests.
17. **Configuration.** Profile files baked into the image (one image per environment), a config server (one more process), or **externalised configuration bound to validated typed properties, one image for every environment (chosen)**.
18. **Retries.** Declarative retry annotations (retries disappear from the transaction-boundary review), a circuit-breaker library from day one (nothing to protect yet: the LLM and the intent model already fail closed to "no answer"), or **an explicit, tested retry decorator per port adapter (chosen)**; a library may provide the decorator once more than a few sites exist.
19. **Idempotency of calls that create something.** An `Idempotency-Key` header (a second store of request hashes, and a header every client must remember), natural keys only (nothing to key a creation on before it exists), or **a client-generated id for every new resource (chosen)**, carried in the request and unique per owner, the way the harness's `purchaseKey` is unique per agent instance (06-consistency §5).
20. **API versioning.** A version header or media type (invisible in logs and contract files), no versioning with additive changes only (no way to make a breaking change), or **a major version in the path per API side, additive within a major (chosen)**; the same additive rule for MCP tools and events, with a new name for a breaking change.

## Decision

### A. The stack
- **Java 25 LTS** for every backend deployable: `control-backend`, `control-mcp`, `connector-gateway`, `hook-responder`, `agent-harness`, and the simulators. Temurin builds on aarch64 (T-008 installs and verifies). Compilation fails on warnings (`-Xlint:all -Werror`), as the quality bar requires.
- **Spring Boot 4** (the current line; T-008 pins the version) with Spring Framework 7 for the five backend deployables and the simulators. Nothing from Spring, Jakarta or any library enters `shared-kernel` or `control-core`: those two Maven modules declare no third-party dependency (`control-core` depends on `shared-kernel` only), so the compiler enforces invariant 9 against libraries, and an ArchUnit rule is the second check (ADR-0006), banning the JDK's own side doors under one rule, **no JDK API that reads the host's clock, randomness, defaults, environment, file system or network**, with these as the named examples: the `java.time` `now()` methods, `Clock.systemUTC()`, `Clock.systemDefaultZone()`, `new Date()`, `Calendar.getInstance()` and the `System` clocks; `Random`, `SecureRandom`, `ThreadLocalRandom`, `Math.random()` and `UUID.randomUUID()`; `ZoneId.systemDefault()`, `TimeZone.getDefault()`, `Locale.getDefault()` and `Charset.defaultCharset()`; `java.net`, `java.sql`, `java.nio.file` and the `java.io` file classes; `System.getenv` and `System.getProperty`. Locale-implicit calls such as `toUpperCase()` without a `Locale` are left to static analysis.
- **Spring AI** for the MCP server in `control-mcp` and `connector-gateway`, the MCP clients in `agent-harness`, in `connector-gateway` (towards merchants' discovery tools) and in `control-backend`'s connector adapters (towards merchants' account, quote and order tools, ADR-0008), and the chat client in the harness. Every MCP server we run speaks **streamable HTTP**; the harness's clients are configured with exactly two server addresses (the fence, ADR-0006). The clients advertise no sampling, elicitation or roots (these are client capabilities), drop a merchant's `initialize` instructions, prompts, resources and notifications, and handle `notifications/tools/list_changed` as ADR-0008 says. T-008 verifies that the SDK covers this and reports gaps.
- **Maven** with the wrapper (`./mvnw`), one reactor with the modules of [03-modules.md](../architecture/03-modules.md): `shared-kernel`, `control-core`, `control-backend`, `control-api`, `control-mcp`, `connector-gateway`, `hook-responder`, `agent-harness`, `web`, `simulators`. Versions are declared once in the parent (Spring Boot's BOM for what it manages, exact versions for the rest); the Enforcer plugin bans every dependency outside test scope (compile, runtime, provided and system alike) from `shared-kernel`, allows `control-core` only `shared-kernel` outside test scope (test scope may use JUnit, AssertJ, jqwik and ArchUnit), and bans duplicate or snapshot versions everywhere. `./mvnw verify` runs formatting, static analysis, compilation with warnings as errors, unit, property, architecture and Testcontainers tests, coverage and mutation on `control-core` (floors set by the user in T-008), and the dependency vulnerability check; the web module runs its own build and tests in the same reactor through the frontend Maven plugin or a CI step, whichever T-008 finds reliable on the Pi.
- **PostgreSQL** (current major, 18; T-008 pins it) with the instance, schema and role layout of [02-system.md](../architecture/02-system.md), and **Hibernate/JPA in persistence adapters only**:
  - JPA entities, repositories and `EntityManager` use live in the persistence adapters of `control-backend` and `agent-harness`, in adapter-private classes mapped to and from the core's records at the port boundary. No entity, annotation, lazy proxy or persistence context crosses a port; `control-core`, `shared-kernel` and the match rule used by `hook-responder` know nothing of them. Open-session-in-view is off; `ddl-auto` is `validate` and never generates schema. `hook-responder` uses `JdbcClient` with plain SQL, not JPA: it reads published views and writes two insert-only tables on a 300 ms budget, with no object graph to map.
  - Native SQL in the same adapter where JPA fights the design: the `SELECT … FOR UPDATE` locks in the fixed order (06-consistency §1, through a pessimistic lock mode or a native query), `INSERT … ON CONFLICT DO NOTHING`, the run claim's `UPDATE … WHERE claimed_at IS NULL` (§9), the cursor reads of the hook's tables (§4), and the audit insert.
  - Money columns are `numeric(19,2)`, FX rates `numeric(18,8)`, the foreign-currency margin rate and the weighed-line allowance `numeric(9,6)`, never a floating-point type; `BigDecimal` maps to them unchanged (invariant 6), and an adapter rejects a value whose scale exceeds the column's instead of letting PostgreSQL round it silently. Ids are UUID columns; instants are `timestamptz`. The `DecisionInput` and the ingested trace are `jsonb` with a schema version (B7).
  - HikariCP's pool size is explicit per deployable (configuration, B5), sized against PostgreSQL's connection limit on the Pi; the hook responder has its own small pool on its own role.
- **Flyway** SQL migrations, versioned and forward-only, one series per module schema, run by a **separate one-shot migration step** (a compose job in the PoC, a pipeline step in cloud or bank) whose login role is the only member of the schema-owner roles; no running process has that login. Each schema is owned by a `NOLOGIN` role; the runtime roles receive grants only, so a compromised process cannot disable a trigger, truncate or drop a table. The audit tables are insert-only by role and trigger (02-system: the roles lack `UPDATE` and `DELETE`); this ADR adds that `TRUNCATE` is revoked too and a statement-level `BEFORE TRUNCATE` trigger rejects it, since a row-level trigger does not fire on `TRUNCATE`, and that Flyway's `clean` is disabled everywhere. A migration never drops or rewrites an audit column. A Testcontainers test per audit table proves two things: the runtime role is denied `UPDATE`, `DELETE` and `TRUNCATE`, and the triggers reject all three even for the owner and migration roles. Testcontainers runs the migrations against a real PostgreSQL in every DB adapter test, then Hibernate validates the mapping against the result.
- **Spring Modulith** for module boundaries and the outbox, exactly as ADR-0006 and [03-modules.md](../architecture/03-modules.md) fix them: the verification runs in a test and fails the build on a cycle; the event publication registry is the outbox in PostgreSQL; listeners are idempotent and tolerate reordering (06-consistency §7). The registry records each publication's status (published, processing, failed, resubmitted) and completes it when the listener returns; with its republish-on-restart setting turned on it resubmits incomplete publications at start-up. The scheduled resubmission is **our own job** and resubmits **failed publications only**, through the registry's failed-publications API with a backoff and the registry's completion-attempt count as the budget; the registry's staleness monitor is what turns a listener lost mid-flight into a failed publication, and B6 fixes its bounds against the listeners' deadlines. Because a monitor can only ever bound a hang, not know of one, the checkout attempt also carries its own fence (B6): every attempt transition is a compare-and-set on the state it expects, and a redelivery that finds an attempt mid-call does nothing; after the call's recorded deadline the resolver settles it with the `UNKNOWN` rule of 06-consistency §3, never with a `FAILED` on missing evidence. T-037 verifies the restart resubmission, the job, a hung listener past the bound and that no redelivery changes an attempt's state. **No message broker in v1**; RabbitMQ is added behind the same registry when a second process needs the events (ADR-0006).
- **One LLM gateway** behind the harness's `ModelGateway` port ([03-modules.md](../architecture/03-modules.md)): Spring AI's OpenAI-compatible chat client pointed at **OpenRouter**'s base URL in the PoC, the model id as configuration, the allowed models and the spend cap per user from `settings` through `get_agent_configuration`, the cap enforced in the harness's `model-gateway` module from the gateway's usage fields before the next call, and a **fixture adapter** for tests, the benchmark runner and offline work. A bank replaces the base URL and key with its own gateway. Why one gateway: one adapter and one review instead of one per vendor, model choice as data, EU-hosted models selectable from a list. No card, token or personal checkout data ever enters a prompt (02-system). The decision core never calls a model (invariant 2).
- **The intent model** is chosen per T-036 behind the `IntentModel` port in the backend, with a fixture adapter ([ADR-0007](ADR-0007-cart-evidence-and-auto-purchase.md), [ADR-0003](ADR-0003-model-use-caution-only.md)); nothing more is decided here.
- **React and TypeScript** with Vite for `web`: strict TypeScript, typescript-eslint's type-checked strict configuration, Vitest for unit tests, Node LTS pinned by the repository and a lockfile installed with `npm ci`; the browser end-to-end tool for the few flows that need one (confirm screen, step-up answer) is picked in T-008, Playwright being the candidate. The production build is static files served by the reverse proxy of the compose setup (02-system), not by a Spring process. **Generated UI** (Claude Design or similar) is a reference for screens and words; its code is rebuilt to the quality bar, never merged.
- **Tests:** JUnit Jupiter in the version Spring Boot's BOM manages (6 for Boot 4), AssertJ, **Mockito**, **jqwik** for property tests (`Money`, FX conversion and rounding, the caution combiner, the `ceiling` function), **Testcontainers** with PostgreSQL for every DB adapter, **ArchUnit** for the core's purity and the layering inside each module, Spring Modulith's module tests, and the replay harness over labelled cases (06-consistency §6). Mockito stands in for ports in adapter and application-service tests only; the pure core is tested with values and never mocked; one shared contract suite runs against every adapter of a port that has more than one (quality bar). Spring context tests are few and slow by design; the core's suite is fast.
- **Quality control:** SonarQube Cloud in CI on its free plan for public projects, with the floors the user sets; if that plan stops covering this repository or its pull-request analysis, a self-hosted SonarQube takes over, deployed by the Pi admin agent, with the same floors. T-008 confirms that the free plan analyses pull requests, not only `main`. A formatter, static analysis with warnings as errors, coverage and mutation tools for `control-core`, and a dependency vulnerability check are each picked and verified on the Pi in T-008 and run by `./mvnw verify` and in CI. Dependencies are pinned (parent POM and lockfile) and checked for known vulnerabilities on every pull request.
- **GitHub Issues and GitHub Actions.** CI runs on every pull request into protected `main`: the data check (`python3 scripts/data_check.py`), `./mvnw verify`, the web build and tests, Sonar and the vulnerability check; nothing is pushed to `main` directly (CLAUDE.md). The backlog stays in [backlog.md](../backlog.md) (CLAUDE.md). Whether the implementation items T-007 produces also become GitHub Issues carrying their `T-NNN` id is a proposal for the user to take in T-007, not decided here.
- **Notifier adapters for the PoC** (the library half of the open item in 05-open-items): server-sent events to the open web app through Spring MVC's `SseEmitter`, and e-mail through Spring Boot's mail starter (Jakarta Mail) with a fixture sender in tests and `dev`. Web push is not in the PoC; its library is chosen when epic J needs it. The `Notifier` port's contract and what "reachable" means are T-003's.
- **Out of the stack:** x402 and its TypeScript wallet side (N6 is a nice-to-have with no Java SDK; a private key never lives in the Java app; if N6 returns it gets its own ADR), Gradle, plain-SQL-only persistence, Bedrock and AgentCore, Spring serving the web build, and the hackathon's single-user API without authentication (identity is in 02-system).

### B. Conventions every deployable follows
These bind `control-backend`, `control-mcp`, `connector-gateway`, `hook-responder`, `agent-harness` and `web`, and the simulators where they apply. T-003 cites them in every contract instead of restating them.

**B1. Service-to-service authentication.** Who authenticates to whom with what is fixed in [02-system.md](../architecture/02-system.md), section "Identity between deployables": the agent session token issued by `identity`, forwarded verbatim by `control-mcp` and verified by the backend on every call; mutual TLS between `control-mcp` and the backend, which proves only which process is calling; the harness's client certificate towards `control-mcp` and its agent-instance credential that can only claim due runs; the single-use run claim and the short-lived agent run token; the connector gateway's own client certificate towards the backend, limited to the connector endpoints, and its per-call check; the processor's own scheme per hook profile (shared-secret signature or mutual TLS); and the OAuth account link's controls (PKCE, `state` bound to the app session, RFC 9207 issuer identification, the exact registered redirect URI, exactly the manifest's scopes, refresh-token rotation, RFC 7009 revocation at link end). This ADR adds the mechanics:
- **Token format.** The agent session and run tokens are JWTs (JWS compact serialisation) with `iss`, `sub` (the cardholder), `aud` (`control-backend`), `iat`, `exp` and `jti`, a `kid` header parameter, plus claims for the agent instance and, for a run token, the mandate id, the run id and the allowed tools, as 02-system lists them. Because `identity` issues and the backend verifies and nobody else does, v1 signs with a **symmetric key (HMAC-SHA256)** held only by the backend, rotated by `kid` with two keys valid during the overlap. When a second verifier appears (a bank's own agent host, or `control-mcp` rejecting malformed tokens early), the signature moves to an asymmetric key (Ed25519 or ES256) with a published key set; the claims do not change. The token carries an explicit kind claim (session or run). **The backend enforces the kind per endpoint group**: the agent endpoints take either, the connector endpoints take no run token (02-system), and a run token is limited to its listed tools; `control-mcp` and the gateway may refuse an obviously wrong kind early, but with a symmetric key they cannot verify a signature, so their checks are filtering, never authorisation. Verification pins the algorithm per `kid` (never read from the token, RFC 8725), checks `iss` and `aud` exactly, `exp` and `iat` against the `Clock` port with a small skew, and the kind; a run token is not stored (06-consistency §9). The cardholder and console endpoints accept only the user's session (a distinct kind and audience, through `CallerIdentity`) and refuse every agent session or run token and every request presenting `control-mcp`'s or the gateway's client certificate. The credential the harness receives with a chat session is **never one those endpoints accept**: it is bound to the harness as audience, or scoped to a separate origin or cookie scope, so that even a compromised harness cannot confirm, answer or toggle anything (02-system); T-003 fixes the mechanism in the `CallerIdentity` contract and the test is required in 06-consistency. The run claim itself is authenticated by the harness's client certificate and its agent-instance credential (02-system), which is neither token; that credential's format, rotation and revocation are T-003's, under `identity`. A token never carries personal data beyond the ids.
- **Mutual TLS.** Every certificate between our processes is issued by a **private certificate authority per deployment**: the compose setup generates the CA and the leaf certificates in a one-shot job at first start (PoC); a bank's PKI issues them inside its perimeter. The CA's private key exists only inside that job (kept on a volume mounted into that job alone, so a rotated leaf is issued by the same CA) or the PKI, and is never mounted into a running process; each leaf key is mounted only into the one process it identifies (two keys in one process while the gateway is co-located in `control-mcp`), so a compromised harness holds no key but its own and cannot mint a peer's certificate. The CA key, each process's own leaf key and the deployment key-encryption key (B2) are rows in 02-system's secrets table. Each process loads its key and trust material through **Spring Boot SSL bundles** from mounted PEM files, never from the classpath or the image, with reload on file change for the server side, so a server certificate rotates by a file swap; a client certificate (`control-mcp` → backend, harness → `control-mcp`, gateway → backend) rotates by a restart unless T-008 shows the clients reload too. Each listener between our processes trusts only its own deployment's CA (the hook responder's processor-facing listener follows the processor's scheme instead, 02-system) and checks the client certificate's subject alternative name against the one peer it expects: the backend accepts the connector endpoints only under the gateway's certificate and the agent endpoints only under `control-mcp`'s; `control-mcp` and the gateway accept the harness's calls only under the harness's. The web app and the merchant-facing endpoints use ordinary server TLS from the reverse proxy.
- **The user's session** with the web app, the harness and the backend is behind the `CallerIdentity` port (local accounts in the PoC, the bank's identity provider over OIDC later; 02-system); its contract, including how the agent session token reaches the harness with the chat session, is T-003's.
- **The OAuth client for account links** is Spring Security's OAuth2 client, used only in `payments`' adapter: the client registrations are built from the admitted manifests (issuer, endpoints, scopes, our client credentials per connector), the authorized-client store is `payments`' encrypted link store (B2), the client sends the registered `redirect_uri` unchanged in the authorization and token requests (the exact match is the authorization server's check), and the RFC 9207 `iss` check runs before the token exchange where the library does not perform it; a refresh replaces the stored token under the same link key; the revocation call at link end follows RFC 7009 where the merchant offers it. The outbound calls to the merchant's authorization server go through the same egress fence as every merchant call (02-system). Whether the library supports the issuer check and manifest-fed registrations without a fork is verified when epic K starts (open item).

**B2. Secrets.** Which secret lives in which deployable, and that account-link tokens are encrypted under a key per cardholder and connector wrapped by the cardholder's key, is fixed in the secrets table of [02-system.md](../architecture/02-system.md). This ADR adds:
- **How a secret reaches a process.** As a mounted file or an environment variable named by a Spring property; the repository holds the property names only (CLAUDE.md). In the PoC a gitignored `.env` and compose secrets fill them; in our cloud or a bank's perimeter the deployment's secret store (a vault, a cloud key service or the bank's own) fills the same properties, with no code change. No secret is in an image, a profile file, a test resource or the Maven settings; the simulators get their own synthetic secrets, labelled.
- **The key hierarchy for account-link tokens.** A token is encrypted with AES-256-GCM under its **link key** with a fresh nonce per encryption; the link key is wrapped by the **cardholder key**; the cardholder keys are wrapped by a **deployment key-encryption key** that lives outside PostgreSQL: a mounted file in the PoC, a key in the deployment's key service or an HSM in cloud or bank, where the wrap and unwrap then happen inside that service. Wrapped keys live in `payments`' schema beside the ciphertext; the key-encryption key never does. Rotating it re-wraps the cardholder keys and nothing else; deleting a cardholder key erases every one of that cardholder's links at once (the erasure item in 05-open-items); unlinking one connector deletes one link key. This envelope encryption uses the JDK's JCA primitives only, with no custom algorithms; the JWS of B1 uses the JOSE library Spring Security ships (Nimbus JOSE+JWT), and no other third-party cryptography enters the stack unless T-008 finds a need and the user agrees.
- **The signing keys** of B1 and the connector OAuth client credentials follow the same rules; the LLM gateway key lives only in the harness.
- **Never** in an event, a read model, a log line, a metric label, a trace attribute, a problem response, a `DecisionInput`, a URL, an exception message or a `toString`. Types that hold a secret or a token print their type name and nothing else; the actuator exposes only `health` and the metrics scrape, on the management port; `env`, `configprops`, `heapdump`, `threaddump`, `loggers` and every other endpoint are off in every profile, since a heap dump would hold decrypted link tokens and the signing key.

**B3. The error model.**
- **In `control-core` and `shared-kernel` an expected failure is a value.** Each port's contract comment names its failure modes (CLAUDE.md), and the port returns them as a sealed result type, one case per mode, so a caller's `switch` must handle every one. `decide` never throws for a business reason: a decline is a decision, a conflict on an idempotency key is a named error (06-consistency §5), a cap exceeded (02-system) or an unknown field in a proposal line (ADR-0006) is a named error. A currency the FX source has no rate for is an expected input, not a bug: `FxRates` returns a named "no rate" mode, the application service records that answer in the `DecisionInput` beside the rates it did get (so `decide(storedInput)` reproduces the outcome without any adapter, 06-consistency §6), and `decide` turns it into a DECLINE with its own reason code, audited like any decision (invariants 1 and 8); an amount already in the base currency needs no rate. A source that is unreachable or returns a stale rate is a separate named mode of the same port; whether it ends in a DECLINE or in no decision with a named error is settled in T-003's rule catalogue. A violated precondition inside the core (a negative margin rate, which `settings` validation already refuses, 06-consistency) is a programming error and an unchecked exception: fail fast, never a default.
- **Adapters translate.** Every database, network and library failure becomes one of the port's declared modes at the adapter; a failure the contract does not name propagates as an exception and is a bug to fix by adding the mode or fixing the adapter, never by a wider `catch`.
- **At every HTTP edge** (the backend's REST API, the ingest and run-claim endpoints, the harness's chat API, the hook responder where the processor profile allows it, the simulators) a failure is an **RFC 9457 problem details** response (`application/problem+json`, Spring's `ProblemDetail`): `type` is a stable URI from the error catalogue in `control-api`, `title` is the error's name, `status` the HTTP status, `detail` a fixed sentence that never contains untrusted text or personal data, `instance` the request path; extensions carry the `traceId` (B4) and, for validation, an `errors` array of field and code. An unexpected exception is a `500` whose only detail is the trace id; the stack goes to the log at `ERROR`.
- **At the MCP surface** a named failure is a tool result flagged as an error with a structured body carrying the same `type` and name, so the model sees a typed fact and never a transport failure or a stack trace; the connector gateway maps a merchant's failure the same way and never relays the merchant's text as an error message.
- **No swallowed exceptions.** A `catch` exists only to translate into a port's mode, to add context and rethrow, or in the single top-level handler of a process that logs and answers a problem. No empty `catch`, no `catch (Exception)` that returns a default, no checked exception turned into `null`. Static analysis fails the build on an empty or ignored catch (T-008 configures it).
- **Listeners and jobs.** A listener that fails leaves its publication **failed** and is resubmitted (B6); it never catches and continues past a business failure. After the completion-attempt budget the publication stays failed, is visible in the console's read model and is never dropped.

**B4. Logging, metrics and tracing.**
- **Logs.** SLF4J over Logback through Spring Boot, as **structured JSON** (Boot's structured logging in ECS format) in every deployed profile and plain text in `dev`. `ERROR` is a bug or a lost call; `WARN` an expected failure an operator should see; `INFO` lifecycle, state transitions and ids; `DEBUG` never in a deployed profile. A log line carries **ids and codes only**: cardholder id, agent instance id, `purchaseKey`, decision id, attempt id, connector id, mandate version id, trace id, reason codes, states, the model id and token counts of an LLM call. An id that comes from the untrusted side (`purchaseKey`, the ingest event id, the draft id of `draft_mandate`, the client-generated ids of B6) has a **fixed format** (a UUID, or at most 64 characters from `[A-Za-z0-9_-]`) enforced by the id type's own factory in the shared kernel (parse, don't validate), so `control-mcp` rejects a bad id and the backend rejects it again; a watch run derives its `purchaseKey` as a name-based UUID (version 5) over the mandate id, the run id and the merchant's offer id, so the derivation fits the format and carries no merchant text. Only a format-validated id is ever logged; no other agent-supplied value is. A pseudonymous id such as the cardholder id is still personal data in the GDPR sense, so logs and traces carry a **retention bound** set in configuration, and the erasure item in 05-open-items covers them with the audit store. Never: names, addresses, documents, e-mail addresses, conversation text, merchant text, tool arguments or results, prompts or completions, amounts together with a merchant (that is the audit's business, not the log's). The rule is enforced by type: `UntrustedText` and the personal-data records of `profiles` print their type and a length from `toString`, tokens and secrets print their type name only (B2), never the content. The application log is not the audit log: invariant 8 lives in `audit` ([01-style.md](../architecture/01-style.md)).
- **Metrics.** Micrometer, exposed on the management port only (not the service port, bound to the internal network) for a Prometheus-style scrape. Per port adapter: calls, failures by mode, latency; decisions by outcome and reason code; outbox lag and incomplete publications; the hook's latency histogram against its 300 ms p99 budget; the LLM spend per model and per deployment. Labels are enumerations and low-cardinality ids (deployable, module, port, outcome, reason code, connector id, processor profile); never a cardholder id, a `purchaseKey` or free text.
- **Tracing.** Micrometer Tracing with the OpenTelemetry bridge; W3C `traceparent` is propagated web → harness and harness → `control-mcp` and → `connector-gateway`; at the trust boundary `control-mcp` and the gateway **start a new trace** and attach the incoming one as a span link, so a trace id that reaches the backend, a problem response (B3) or an audit row was generated by our code and never by the harness; a hook call starts its own trace. The audit row's trace id (an id, not personal data) joins a decision to the request logs around it. Span attributes follow the log rule: ids and codes, nothing personal, nothing untrusted. Export is OTLP to a collector that is deployment configuration: none required in the PoC, the bank's collector later. Which log and telemetry formats a bank's operations accept is a first-bank item (05-open-items).

**B5. Configuration per deployment.**
- **One OCI image per deployable for every environment** (02-system); everything that differs is externalised configuration: environment variables and mounted files bound to `@ConfigurationProperties` records validated with Jakarta Validation at start-up. A missing or invalid value fails start-up naming the property; there is no silent default for an address, a key, a certificate, a mode or a cap. The harness refusing to start with any server other than its configured two (ADR-0006) is this rule applied.
- **Configuration versus `settings`.** Configuration is topology and plumbing: addresses and ports, certificates, pool sizes, memory caps, timeouts (B6), the identity provider, which network adapters are live, the processor profile, the LLM gateway's base URL and key, the log format, the telemetry endpoint. It changes only by redeploy. `settings` ([03-modules.md](../architecture/03-modules.md)) is every parameter the bank or operator changes at runtime (allowed models, caps and quotas, hook mode and fallback, kill switch, margins, enabled connectors, the one-line mode) or fixes at deployment (the base currency: set before go-live, refused once the first budget-period row exists), stored, versioned and audited. Nothing is in both. A rule input is never read from configuration: it comes through `settings` into the `DecisionInput` (06-consistency §6), so a replay sees it. The **base currency** (invariant 6) is such an input: a `settings` value set at deployment whose change is refused once the first budget-period row exists (budget rows are held in it), recorded in every `DecisionInput`.
- **Profiles.** `dev` (the Pi: fixture adapters by default, the simulators through the `sim` compose profile, plain logs), `test` (Testcontainers) and the deployed profile (JSON logs; every adapter named explicitly; a fixture adapter or a simulator bean on the classpath of a deployed profile fails start-up). Simulator images are never in a cloud or bank deployment (02-system).
- **Memory.** Every JVM runs with an explicit heap cap set in configuration and in compose (02-system); T-008 sets the first values and T-037 measures them (05-open-items).

**B6. Timeouts, retries and idempotency for remote calls.** [06-consistency.md](../architecture/06-consistency.md) fixes the transaction rule (remote calls happen before or after the decision's transaction, never inside it), the checkout attempt's one-credential rule and its `UNKNOWN` handling, the idempotency keys (the `purchaseKey` and the attempt id towards merchants and networks, the event id for the ingest, the processor's authorisation id for the hook) and the outbox's at-least-once delivery. This ADR adds:
- **Timeouts.** Every outbound HTTP call (networks, merchants, connector tools, OAuth endpoints, the LLM gateway, the intent model, the FX source) goes through Spring's `RestClient`, or the MCP and chat clients' underlying client, with an **explicit connect timeout and an explicit per-call read timeout**, both configuration (B5) with a default stated in the port's contract comment; no library default is relied on. The calls the egress fence of 02-system covers (merchants, connector tools, the OAuth endpoints the manifests name, in the backend and in the gateway) need a client that checks every resolved address against private ranges before it connects, follows no redirect and pins the origin; the JDK `HttpClient` has no per-client resolver hook, so these calls use **Apache HttpClient 5** behind Spring's request factory with a custom resolver, and the MCP transport towards merchants must accept the same client or sit behind an egress proxy of its own (T-008 checks which). Calls that are not fenced use the JDK `HttpClient`. The mail sender is SMTP through Jakarta Mail, whose connection, read and write timeouts are infinite by default, so all three are required configuration. The intent model's and the LLM's timeouts are bounded by the chat's own wait, and a timeout is "no answer" (ADR-0003). The hook responder makes no outbound call on its request path (02-system).
- **Retries.** Only for calls that are read-only or idempotent on our key; bounded in count and in total deadline below the caller's own timeout; exponential backoff with jitter; never inside a database transaction; **never for a credential request or an order placement** (06-consistency §3: at most one, a timeout is `UNKNOWN` and is resolved by lookup). A retry is a **decorator around the port adapter** with an explicit, tested policy per port ([design-patterns](../../.claude/skills/design-patterns/SKILL.md): never swallowing a failure), not an annotation on a service; a library may provide the decorator once more than a few sites exist, with the same policy objects.
- **Outbox and jobs.** The registry resubmits incomplete publications at start-up; our resubmission job resubmits failed publications only, with a backoff and a completion-attempt budget that are configuration. **Every listener has a deadline**, a true bound: `n × (pool acquisition timeout + PostgreSQL transaction_timeout) + Σ each outbound call's total retry deadline (the Retries bullet, not one attempt's timeout) + a configured margin` for the listener's own work, where `n` is the number of transactions it commits. `transaction_timeout` (PostgreSQL 17 and later) is required, since `statement_timeout` bounds one statement and not the idle time between statements. The application sets the database timeouts on every connection it opens, from configuration, so start-up holds the real values and validates that the staleness monitor's processing bound exceeds the largest listener deadline (B5); HikariCP's acquisition timeout is set explicitly like every other timeout; the monitor's published and resubmitted bounds stay zero, since an event waiting in the queue is not a lost one. **The attempt's own fence** (amends 06-consistency §3): every attempt transition, by a listener or by the resolver, is a compare-and-set on the state it expects under the row lock, so whoever commits second changes nothing and a listener that no longer finds `CREDENTIAL_REQUESTED` never uses its credential; when `payments` commits `CREDENTIAL_REQUESTED` or `COMPLETING` it stores on the attempt row the deadline of that call plus the bound of the follow-up commit; before it a redelivery does nothing; after it only the resolver acts, and it sets `COMPLETED` on confirmed completion, `FAILED` only when the merchant or network confirms the session or order was not and can no longer be completed, and otherwise `UNKNOWN`, the existing path, never a `FAILED` on missing evidence. After the budget the publication stays failed and visible (B3). Scheduled jobs (step-up expiry, the attempt resolver, the hook cursor, due runs, the resubmission) read the `Clock` port and act on rows by state under row locks, so a duplicate run is harmless. The design assumes one backend process per deployment; running several (job locking, resubmission) is an open item in 05-open-items.
- **Inbound idempotency.** A proposal is idempotent on (agent instance, `purchaseKey`) (06-consistency §5), an ingest event on (agent instance, event id), a hook call on the processor's authorisation id (§4). The run claim is **single-use, not idempotent** (§9): a response lost after the claim committed leaves that run consumed, the retry is answered "nothing due" and recorded as a duplicate claim, and the next due run is independent. A cardholder or console call that changes an existing thing is idempotent on its natural key (the mandate version confirmed, the decision answered, the connector toggled, the link ended); a call that **creates** something (a mandate draft, a profile entry, a card enrolment, an account link) carries a **client-generated id** for the new resource, keyed as **(owner, client id)** where the owner comes from the verified token or session and never from the body, so a redelivered create finds its own row and an id another cardholder happens to use is simply absent for this one. As in §5, a repeat with the same binding fields returns the stored outcome, different binding fields are a named conflict, and nothing about another owner's resource is disclosed. There is no idempotency header.

**B7. API and event versioning.**
- **REST.** The OpenAPI document in `control-api` is the contract. Paths carry the major version per API side: `/api/v1/agent/…` (called by `control-mcp`), `/api/v1/connector/…` (called by the gateway), `/api/v1/cardholder/…` and `/api/v1/console/…` (called by the web app). Within a major version changes are additive: new optional fields, new endpoints, new enum values; a consumer treats an unknown enum value as a named error, never as a crash or a default. A breaking change is a new major version served beside the old for a deprecation window. `control-mcp`, the gateway and the web client are tested against the document (the contract-test tool is picked in T-008). `control-mcp`'s ingest and run-claim endpoints and the harness's chat API follow the same path-version and additive rules under their own contracts. The hook's inbound API is the processor's and is versioned per profile.
- **MCP tools.** The tool list is the contract (02-system). A tool's input and output schemas change additively; a breaking change is a new tool under a suffixed name, the old one kept for a window and then removed. The connector gateway serves a manifest's stored tool definitions, versioned by the manifest version (ADR-0008).
- **Events.** The records in the shared kernel's `events` package are the contract (ADR-0006). A published event's record is never renamed or moved to another package (the registry stores the class name) and its fields are never renamed or removed, because stored outbox rows and audit records must deserialise forever; additions are optional with a default; a breaking change is a new record type with a version suffix, consumed beside the old during the migration. The serialised event carries its type name (Spring Modulith's registry) and a `schemaVersion` field. JSON serialisation (Jackson 3 with Boot 4) happens in adapters only; the kernel's records carry no annotations.
- **Stored audit records.** The `DecisionInput` and every audit row carry a `schemaVersion` and the rule set's version, so a replay knows what it compares; what replay does when rules have changed since is T-003's. Flyway migrations are forward-only and never destructive on audit tables.

## Consequences
- \+ One Spring Boot, Spring AI and Spring Modulith line for every backend deployable: agents reproduce it from current documentation, a bank reviews one build, one quality gate and one set of images.
- \+ JPA removes the hand-written mapping cost of ADR-0001 while invariant 9 stays enforced by the compiler, because the entities never leave the adapters.
- \+ Conventions B1 to B7 are testable: the problem catalogue, the redacting `toString`, the start-up validation, the retry decorators and the additive-change rules each get tests, and T-003's contracts cite them instead of restating them.
- − Four to five Spring Boot JVMs on the Pi: memory per JVM is the binding constraint, and start time is the second. T-008 sets the caps, T-037 measures (05-open-items).
- − Java 25 is ahead of parts of the toolchain. Mockito and ByteBuddy, JaCoCo, the mutation tool, Sonar's analyser, Flyway and Testcontainers must all handle the new class-file version on aarch64; if a tool fails on 25, T-008 reports and the user decides; no fallback to Java 21 is assumed.
- − A symmetric token key means `control-mcp` cannot reject a forged token before forwarding it; the backend's verification is the only check, as 02-system already says. The switch to an asymmetric key changes no claims.
- − Spring Security's OAuth client may lack the RFC 9207 check or manifest-fed registrations; verified before epic K, which is after v1.
- − Two toolchains, JDK and Node; the web build runs in CI and in the reverse proxy's image, never in a Spring process.
- − Sonar depends on the cloud service's free plan for public repositories; the fallback is a self-hosted server on a host that is also the home server, operated by the Pi admin agent.
- **What T-008 must verify on the Pi before pinning anything:** (a) Temurin 25 on aarch64 and the memory per JVM under the caps, with `free -h` before and after; (b) a Spring Boot 4 version for which Spring Modulith and Spring AI releases exist together, and that Spring AI's MCP server and client cover the ADR-0006 tool surface over streamable HTTP, let a client (the harness's, the gateway's and the backend's) advertise no sampling, elicitation or roots, present a client certificate from an SSL bundle, and handle `tools/list_changed`; (c) JUnit 6 with jqwik, ArchUnit, Mockito, Testcontainers and Spring Modulith's test support; (d) Flyway and Hibernate `validate` against PostgreSQL 18 in Testcontainers on aarch64; (e) structured logging, Micrometer Tracing with the OpenTelemetry bridge including a new trace with a span link at the boundary, SSL bundles with server-side file reload and whether the clients reload too, Apache HttpClient 5 with a resolver check behind `RestClient` and under the MCP transport, and the Modulith republish-on-restart setting and staleness monitor; (f) SonarQube Cloud's pull-request analysis on the free plan, the formatter, static analysis with warnings as errors, the coverage and mutation tools and the vulnerability check, with proposed floors for the user; (g) Spring context start time per deployable; (h) Node LTS and the web toolchain. Then `./mvnw verify` goes into CI and into the Commands section of CLAUDE.md.
- Supersedes [ADR-0001](ADR-0001-tech-stack.md) in full (its module layout was superseded by ADR-0006 already). Kept from it: Java 25, Spring Boot 4, PostgreSQL, Flyway, the insert-only audit by role and trigger, `numeric` columns, `Money` as an exact-decimal record in the kernel, React and TypeScript, the test libraries. Dropped: Gradle, plain-SQL-only persistence, Bedrock at the event, x402's TypeScript wallet, Spring serving the web build, the single-user API without authentication.
- Open items added to [05-open-items.md](../architecture/05-open-items.md): Java 25 support across the toolchain; the OAuth client library's support for the issuer check and manifest-fed registrations; the log and telemetry formats a bank accepts; more than one backend process per deployment. The `Notifier` row there is narrowed to web push, and the erasure row is widened to logs and traces. Amends [06-consistency.md](../architecture/06-consistency.md) §3 (the attempt's call deadline as a fence against redelivery) and §6 (the FX source's answer, the base currency, the schema and rule-set versions in the replay unit), and adds two rows to 02-system's secrets table.
- Status: proposed. The stack items are the user's decisions of 2026-10-29; the conventions await the user's agreement; accepted once the user agrees and T-008 has confirmed (a) to (e) on the Pi.
