# 03 Module cut

Decided in [ADR-0006](../adr/ADR-0006-architecture-style-and-module-cut.md); since 2026-11-19 the `authorisation` module and the pre-approval are gone and `payments` pays through the `PaymentProvider` port ([ADR-0010](../adr/ADR-0010-standalone-app-and-provider-payment-tokens.md)). Aggregates and port contracts are detailed in T-003 and the domain model ADR-0011; this page fixes the boundaries.

## Control backend
Each module is a bounded context with its own schema, a published application API (Java interfaces and records) and events. Nothing reaches into another module's internals or tables. Spring Modulith verifies the boundaries in a test; ArchUnit checks the layering inside each module.

### Shared kernel
`Money` (exact decimal, scale 2, half-even, one currency), the `FxRates` port (its adapter and cache are a small `fx` package in `control-backend`, used by `ledger` and `decisioning`), typed ids, `UntrustedText`, `Clock` and `Random` ports, `PurchaseKey`, the tagged external reference (`CheckoutSession | PaymentToken | ProviderEvent | ShopOrder | ConnectorOrder | …`), the typed `ItemSpec` categories, `ConnectorId` and the `ConnectorToolClass` enum (discovery, account, quote, order), and the `events` package with every event type consumed outside its publishing module (ids, amounts and enums only, which keeps the package small by construction). Small and stable by intent; a change here is reviewed as a change to every module.

### Where transactions end
One `propose_purchase` runs in one transaction once the evidence is gathered: the decision with its token terms (APPROVE only), the ledger reservation (APPROVE only; a STEP_UP counts once approved, invariant 5), the audit record with the full `DecisionInput` and the outbox rows commit together, under row locks on the budget periods it touches. A step-up approval is a second decision committed the same way. Discovery, merchant, provider and model calls happen **before** the transaction (gathering evidence) or **after** it (the token and the checkout, as an event listener driving a persisted checkout attempt). No transaction is held open across a remote call. The mechanics are in [06-consistency.md](06-consistency.md).

### Dependency rules
- `decisioning` depends on the published APIs of `mandates`, `ledger` and `payments`; nothing depends on `decisioning` except through its events.
- `payments` starts a checkout and issues a token only from a `DecisionMade` event whose outcome is APPROVE; a step-up approval is such a decision, re-checked by `decisioning` (never by `payments`). The token's terms are those stored with that decision; `payments` never widens them.
- `profiles` is read by `payments` (by version id at checkout; the current version's country and postcode when opening a session), by `notifications` (channels), by `decisioning` (the current version id and the base currency), by `ledger` (the base currency when a period of the global budget opens; a mandate's own periods keep the mandate's confirmed currency) and by `mandates` (the entry and a channel exist at confirmation); nothing else reads personal data, and no event carries it.
- **Every event type consumed outside its publishing module lives in the shared kernel's `events` package** (records of ids, amounts and enums; no module type inside). A listener then depends on the kernel, not on the publisher, so the module graph stays acyclic in code even where modules listen to each other both ways (`mandates`↔`agents`, `payments`↔`mandates`, `decisioning`→`payments` by API and `payments`→`decisioning` by event). T-037 confirmed the arrangement under Spring Modulith's verification.
- `agents` computes due runs from `MandateConfirmed` and stops them on `MandateFulfilled`, `MandateRevoked` and its own stop; `identity` mints the run token on a claim. The harness is never called.
- `payments` reads the agent's status and the connector toggle through `agents`' API and the enablement through `settings`' API; `agents` knows nothing of `payments`. The slot pick, the shipping option pick, the ceiling and the token terms are pure functions in `control-core`; `payments` gathers their inputs and the decision stores them. The connector gateway reaches the backend only through `control-api` (the published manifests and the per-call check); no module knows the gateway.
- `audit` is written through the `AuditLog` port by every module, inside the module's transaction.
- `activity` only listens; it never writes another module's data.
- No cycles; Spring Modulith's verification fails the build on one.

## Maven layout
```
agentic-wallet/                    (Maven reactor)
├── shared-kernel/                 pure Java, no dependencies
├── control-core/                  pure Java: the domain of every control module, the rules, the combiner,
│                                  the token terms function, the ports; depends only on shared-kernel
├── control-backend/               Spring Boot + Spring Modulith: application services, REST API, the
│                                  provider webhook path, JPA persistence adapters, provider and merchant
│                                  adapters, outbox
├── control-api/                   the OpenAPI contract of the backend's REST API (agent and cardholder sides)
├── control-mcp/                   Spring Boot + Spring AI MCP server; no persistence
├── connector-gateway/             Spring Boot + Spring AI MCP server and client; no persistence
│                                  (hosted inside control-mcp's process in the PoC, ADR-0008)
├── agent-harness/                 Spring Boot + Spring AI (chat, MCP clients)
├── web/                           React + TypeScript
└── simulators/                    payment-provider, demo-shop, demo-connector, scripted-agent-driver,
                                   benchmark-runner (M16) (test scope)
```
`control-core` has no framework, database, HTTP, clock or random dependency, so the compiler enforces invariant 9; ArchUnit is the second check. `control-core` mirrors the backend's module packages (`…core.mandates`, `…core.decisioning`, `…core.payments`, …), and because Spring Modulith's verification does not run there, an ArchUnit rule in `control-core` forbids imports between those packages except through the shared kernel. A build test in `control-backend` asserts that the `PaymentProvider` adapter makes no charge, refund or payout call ([02-system.md](02-system.md)).

## Agent harness
| Module | Holds |
|---|---|
| `chat` | conversations, streaming to the web app, the model picker |
| `model-gateway` | `ModelGateway` port: our gateway's model list, a fixture adapter; a hard spend cap per user; no payment or token data ever in a prompt |
| `shopping-tools` | search, read page, the **merchant scan** (reviews and rating of shops new to the user, untrusted, for ranking and caution only, shown to the user), and the discovery tools of the connectors the user turned on (from `get_agent_configuration`, called through the connector gateway); everything read is untrusted text; no other tool server can be configured |
| `mandate-drafting` | the guided conversation that produces a structured draft through `draft_mandate`, asks the user about the items the backend's checklist names as missing, sets the agent's `ready` assertion on the draft, and offers a readjusted draft when a decision carries the readjustment reason code or its searches find nothing that fits, with amounts from the backend's declines and web prices labelled merchant-reported and unverified; it may search first to learn the market; it never activates anything |
| `memory` | purchases, merchants, categories, price points, habits as counters in PostgreSQL; ranking input only, never a rule input |
| `trace` | records searches, pages read, candidates and reasons; sends them and the conversation to the ingest endpoint |
| `watch` | the runner for standing mandates: claims due runs with the agent-instance credential, runs the price check without a model where it can (the threshold check in the harness is advisory; the backend decides on the merchant's cart), calls the model only when a candidate appears, proposes with a `purchaseKey` derived from the mandate, the run and the offer, one run at a time per mandate; keeps no state it cannot rebuild from `get_mandate` (the claim names the mandate) and the backend's answers |
| `control-client` | the MCP clients to `control-mcp` and to the connector gateway (the only two servers the harness can connect; their addresses are deployment configuration, never data), plus the runtime's ingest and run-claim calls |

## Events (outbox)
| Event | From | Consumed by |
|---|---|---|
| `MandateConfirmed`, `MandateRevoked`, `MandateFulfilled` | mandates | agents (bound mandates, due runs start and stop), payments (on revoke or fulfilment, cancel attempts still in `CREATED` and revoke unused tokens, [06-consistency.md](06-consistency.md) §3), decisioning (on revoke or fulfilment, decline open step-ups), notifications (`MandateFulfilled`), activity |
| `AgentStopped`, `AgentResumed` | agents | payments (on stop, cancel the instance's attempts in `CREATED` and revoke its unused tokens; account links are untouched, their use by the instance is gated by the status in the decision), decisioning (decline open step-ups), activity |
| `RunClaimed` | agents | activity (watch state) |
| `ConnectorToggled` | agents | payments (on off: cancel this instance's attempts in `CREATED` at that merchant; the link is untouched), decisioning (on off: decline this instance's open step-ups at that merchant), activity |
| `AccountLinkChanged`, `ConnectorStateChanged` | payments | decisioning (link ended or connector suspended, disabled or expired: decline open step-ups at that merchant), activity (catalogue and console views), notifications (suspended connector, link ended or expiring) |
| `ProfileChanged` | profiles | agents (suspend or resume due runs by whether a channel remains), activity (version shown, never the data) |
| `DecisionMade` | decisioning (first decisions and every step-up outcome) | payments (checkout and token on APPROVE), activity, notifications (STEP_UP; DECLINE on a standing mandate) |
| `PaymentMethodSaved`, `PaymentMethodRemoved` | payments | activity (the user's saved payment methods, M1) |
| `SettingsChanged` | settings | activity (console); payments (a connector disabled by the operator ends its account links as an unlink does and cancels attempts in `CREATED` there; the one-line mode turned off cancels connector attempts in `CREATED` that would pay with the card on file); decisioning (the same two changes decline open step-ups at the affected merchants); notifications (the one-line mode turned on or off is announced to every linked user) |
| `PaymentTokenIssued`, `CheckoutCompleted`, `CheckoutFailed`, `CheckoutCancelled` | payments | reconciliation, mandates (`CheckoutCompleted`: read the count from `ledger`, raise `MandateFulfilled` when reached), activity, notifications (`CheckoutCompleted`, `CheckoutFailed`); the reservation's count or release happens in `payments`' transaction through `ledger`'s API, a release only once the token is dead ([06-consistency.md](06-consistency.md) §3) |
| `CheckoutPendingUser`, `CheckoutOutcomeUnknown` | payments | notifications, activity |
| `PaymentTokenUsed`, `PaymentTokenEnded`, `UnexpectedTokenUsage` | payments (from the provider's webhooks) | reconciliation, activity, notifications (`UnexpectedTokenUsage`) |
| `ShopOrderReported` | payments (from a shop's order webhook; merchant-reported, untrusted) | reconciliation, activity |
| `MismatchCaseOpened` | reconciliation | activity, notifications |

Every listener is idempotent, keyed on the event id or the `purchaseKey`, and tolerates reordering ([06-consistency.md](06-consistency.md) §7).
