## Why the MCP server is separate and thin
The LLM side reaches the control layer only through MCP tools. Making that server its own process with no database turns "the LLM cannot touch the core except through these tools" from a code convention into a network fact. Any later agent host (a bank's own assistant, a partner platform) plugs into the same server. The server is stateless and cheap.

### The tool surface
| Tool | What it does | Notes |
|---|---|---|
| `list_mandates`, `get_mandate` | read the active mandates of the caller | read only |
| `draft_mandate` | turn the conversation's structured draft into a mandate draft and return its plain-words rendering | a draft has no effect (invariant 4) |
| `propose_purchase` | merchant reference, lines (each a merchant item id **or** a typed item spec, with a quantity), `purchaseKey`, the agent's own description and reasons | the agent's text is untrusted and can only add caution ([ADR-0007](../adr/ADR-0007-cart-evidence-and-auto-purchase.md)); a line never carries personal data, that comes from `profiles` |
| `get_decision` | outcome, reasons, payment state of a proposal | read only |
| `get_activity` | answers "what did my agent buy and why" from the log | read only; amounts and ids come from the backend, never from the model |
| `get_agent_configuration` | the allowed models, the LLM spend cap and what is left of it, the agent's status, the connectors the user turned on (ids and the discovery tools each offers) | read only; how the bank's `settings` and the user's toggles reach the harness |

The harness learns the outcome of a step-up by polling `get_decision` for its `purchaseKey` while the conversation waits; the user sees the question and the answer in the app in any case. A step-up's expiry is set per decision as `min(the setting in settings, the stored checkout session expiry − a margin)` and recorded in the `DecisionInput`, so an approval after a step-up never lands on an expired session. A merchant whose sessions live minutes (airlines) therefore gets no useful step-up: there the outcome is auto-buy or no buy.

Not tools, by design: confirm a mandate, answer a step-up, approve anything, start a checkout, change an agent's status, revoke a mandate, edit the profile, turn a connector on or off, link a merchant account. Confirming, answering, revoking, profile edits, connector toggles and account links come only from the cardholder app to the backend, authenticated as the user. The confirm screen renders the mandate from the backend's **structured draft**, never from the chat's text, so what the user confirms is what the rules will enforce. Checkout starts in the backend after an APPROVE, never because the agent asked.

The agent harness's own runtime (not the model) sends the conversation and the agent trace to `control-mcp`'s ingest endpoint, so the audit export holds the whole thread. Ingest is idempotent by event id and stores the content as untrusted data. Because it comes from the untrusted side it is bounded: a size cap per event, a quota per agent instance and day (configurable, with a separate quota for watch runs so a long watch cannot starve the chat), and an event is attached to a `purchaseKey` only if that key belongs to the token's agent instance; otherwise it is stored unattached. Exceeding a cap is a named error and is itself recorded.

The same runtime claims due runs of standing mandates through `control-mcp`'s **run claim** endpoint (not a tool; the model never sees it). The backend answers with the run's mandate id and a short-lived agent run token, or with "nothing due".

### The connector gateway
Merchants that publish their own API or MCP server reach the agent only as **connectors** admitted into the catalogue ([ADR-0008](../adr/ADR-0008-merchant-connectors-and-the-connector-catalogue.md)). A connector's tools are classed in the manifest as **discovery** (search and read the catalogue), **account** (past orders, the order record by our reference, the payment method on file), **quote** (a priced quote, the slot list, a slot hold) or **order** (place the order on a quote). The gateway is the harness's second and last MCP server and exposes, per caller, the discovery-class tools of the connectors that caller's agent instance has turned on, and nothing else; the other three classes exist only in the backend's connector adapters. On each call it asks the backend whether the token's agent instance has that connector on, enabled and not suspended (the answer is cached for seconds); validates the arguments against the manifest's schema (enumerated or numeric fields where the merchant allows, every free-text field capped at the length in `settings`); calls the merchant anonymously at the manifest's address through its own egress fence (pinned origins, resolved addresses checked against private ranges on every connection, no redirects, arguments never placed in a host or path); caps and schema-checks the response, drops personal fields, types every free-text field `UntrustedText`; and logs the call into the ingest under the caller's agent instance. It serves the harness the manifest's **stored** tool definitions, never the live ones; it verifies the live canonicalised tool objects' hash at session start and on `notifications/tools/list_changed`, and a drift suspends the connector (the backend is told; toggles and links are untouched). It drops a merchant's `initialize` instructions, prompts, resources and logging or progress notifications. Like `control-mcp` it has no database and no business logic. Its MCP client towards merchants advertises no sampling, elicitation or roots, so a merchant can neither use our model nor question our user. A discovery query is still free text within its cap, so a compromised harness could leak conversation text through it as it could through a web search; the harness holds no card or personal checkout data, which bounds that. Until T-037 says the Pi can afford a fifth JVM it runs inside the `control-mcp` process behind its own listener and its own client certificate towards the backend, limited to the connector endpoints; it is a separate deployable by design so a bank can place it apart.

## Identity between deployables
- **User → web → harness / backend:** local accounts in the PoC, the bank's identity provider over OIDC later, behind one `CallerIdentity` port. The backend never holds passwords from a bank.
- **Harness → control-mcp → backend:** the backend's `identity` module issues an **agent session token**: signed by the backend, bound to the cardholder, the agent instance and the audience `control-backend`. For a chat it is issued when the user opens the chat in the web app and is short-lived. The web app hands it to the harness with the chat session; the harness attaches the token to every MCP call and cannot mint or widen one. `control-mcp` forwards it **verbatim** and never derives or adds claims; the backend verifies it itself on every call. The model never supplies or sees identity. An agent's identity comes from this token, never from a request body. `control-mcp` and the backend also authenticate each other with mutual TLS, which proves the caller is `control-mcp` but grants no user rights by itself.
- **Standing mandates** ("look every morning", the price watch V9): the schedule is trusted data. The confirmed mandate carries the run frequency; `agents` keeps the **due runs**. The harness authenticates to `control-mcp` with mutual TLS (one client certificate per harness deployment); `control-mcp` passes that verified identity to the backend under its own mutual TLS. The harness runtime holds one long-lived **agent-instance credential**, bound to that certificate and able to do exactly one thing: claim due runs of its own agent instance. On a claim, `identity` mints a short-lived **agent run token** for that run, bound to the cardholder, the agent instance, the mandate and the run id, and limited to `propose_purchase`, `get_decision`, `get_mandate` and the trace ingest, so an unattended run leaves the same thread in the audit export as a chat. A claim is single-use; a second claim of the same run is refused and recorded, so a stolen credential racing the harness becomes visible. No run is due once the mandate is fulfilled, expired, revoked or the agent stopped, or while the cardholder has no notification channel left; nothing long-lived in the harness can propose a purchase on its own.
- **Harness → connector-gateway → merchant:** the same agent session token as towards `control-mcp`; the gateway forwards it to the backend's per-call check and never to a merchant. Towards a merchant the gateway is anonymous; no user token of any kind in v1. A run token is not accepted by the gateway: a standing mandate's list names merchant item ids, so a run needs no discovery.
- **User → merchant (account link):** one OAuth authorization-code consent per cardholder and connector, started from the cardholder app: PKCE; a `state` bound to the app session and checked at the callback; issuer identification (RFC 9207) so a response from one authorization server cannot be mixed with another's; the exact registered redirect URI; exactly the scopes the manifest fixes; refresh-token rotation. The merchant redirects to the backend's callback, and `payments` stores the token under a key per cardholder and connector wrapped by the cardholder's key. The agent cannot start, see or use it. A toggle off or an agent stop only blocks the link's use by that instance. The link ends by the user's unlink, the bank disabling the connector or the manifest's expiry: new quotes and orders stop at once, a resolution-only use remains until every checkout attempt and reconciliation read for the link is final or, at the latest, until the last order's slot end plus a reconciliation window from `settings`, then the token is revoked at the merchant (RFC 7009, where offered) and deleted; a case still open afterwards runs on the stored order record.
- **Bank processor → hook-responder:** the processor's own scheme (shared secret signature or mutual TLS), per profile.

## Data ownership in PostgreSQL
| Owner | Schema(s) | Others' access |
|---|---|---|
| control-backend | one schema per module (`identity`, `profiles`, `settings`, `agents`, `mandates`, `decisioning`, `ledger`, `payments`, `authorisation`, `reconciliation`, `audit`, `activity`, `notifications`) plus the event publication registry | hook-responder: `SELECT` on published views of `authorisation`, `agents` and `settings` only |
| hook-responder | `hook`: insert-only call log and pre-approval consumption ([06-consistency.md](06-consistency.md) §4) | control-backend reads it by cursor for reconciliation |
| agent-harness | its own database (`harness`): conversations, memory | none; control data is not reachable from here |
| control-mcp, connector-gateway | none | — |

Account-link tokens live in the `payments` schema, each encrypted under a key per cardholder and connector that is wrapped by the cardholder's key, so that unlinking one connector deletes one key and erasing the cardholder deletes the wrapping key; they are never in an event, a read model or a log. Toggles, account links, admission, approval, enablement, suspension and expiry are audited like every other change.

The audit tables are insert-only: the roles lack `UPDATE` and `DELETE`, and a trigger rejects them.

**Personal data and erasure.** The audit store is insert-only, yet it holds whole conversations, and the bank as data controller may have to erase a cardholder's data. Retention and erasure are **deferred** (user, 2026-10-29): the design keeps the option open by never putting personal text into a key, index or hash input, and by recording the cardholder id on every audit row, so a later erasure mechanism (per-cardholder encryption with key deletion is the candidate) touches only the storage adapter. The `profiles` schema holds the buyer, traveller and delivery data a checkout needs; other modules and the `DecisionInput` keep only its version ids, so erasing a profile does not break a replay. Open item in [05-open-items.md](05-open-items.md).

**The control backend and the hook responder must share one PostgreSQL instance** (a bank may run it highly available, but not split it): the hook reads a pre-approval the moment its decision commits, and consumes it under a unique constraint. Splitting them would need a replicated pre-approval feed and a different consumption design; that is a new decision, not configuration. The harness's database may live on a separate instance.

## The backend's outbound calls to merchants
The trusted backend talks to merchants (checkout sessions, product records, offer searches for item specs, and, through admitted connectors, account reads, quotes, delivery slots and orders). That is the one place where the trusted zone reads from the outside world, so it is fenced: endpoints come only from the merchant directory, which is filled from the networks' merchant registries, from the admitted connector manifests (and the demo shop in the PoC); the agent supplies a merchant reference, never a URL; responses are parsed with size limits and strict schemas into typed fields; free text inside them is `UntrustedText`; private address ranges and redirects are refused. A connector call carries the user's account-link token only for the account-, quote- and order-class tools the manifest names, and only for the cardholder the decision or the reconciliation read belongs to; an order-class call is made only from a checkout attempt that exists for an APPROVE. The same fence (pinned origins, address checks on every connection, no redirects) applies to the OAuth token endpoints the manifest names. Because each proposal opens a session or a quote at the merchant (for an airline, possibly a seat hold; for a grocer, possibly a slot hold), proposals are rate-limited per agent instance and per mandate in `settings`.

## The hook responder's scope and failure behaviour
- **Which authorisations:** only those on network tokens enrolled through us (the token references in `agents`), or on an enrolled agent card by its card id. For any other token or card the answer is **no opinion**, mapped to whatever the processor profile uses for "let the issuer's own rules decide". It never declines a cardholder's ordinary purchases. A connector order is covered only when it is paid with a bank-issued **agent card** the user put on file at the merchant: a card for agent orders only, enrolled through us, which the hook recognises by its card id at the processor (a card-on-file charge carries the merchant's stored credential, not our network token). On that card a manual order has no pre-approval and is declined in enforcing mode; the user is told so when the card is issued. `payments` reads the payment method on file before each order and a hard route rule compares it with the enrolled agent card; a mismatch is DECLINE unless `settings` allows the labelled **one-line mode**, in which the hook has no opinion on the charge ([ADR-0008](../adr/ADR-0008-merchant-connectors-and-the-connector-catalogue.md)). The pre-approval window of a connector order runs to the slot's end plus the manifest's authorisation lag, because a grocer authorises at picking or delivery.
- **No matching pre-approval for an enrolled agent token:** shadow mode records "would decline". Enforcing mode declines with the processor's code for a cardholder-elected control, and records the authorisation for reconciliation.
- **Currency:** the pre-approval stores the approved amount in the merchant's transaction currency. The match compares against the authorisation's **transaction** amount and currency, never the cardholder's billing amount. A profile that only carries the billing amount is not supported until a tolerance rule is decided with that bank.
- **Database unavailable or budget exceeded:** the answer is the bank's configured fallback (`settings`: no opinion, or decline agent tokens), and the call is logged locally and replayed into `hook` when the database returns.
- **Mode and kill switch:** set by the bank in `settings` through the console; the hook responder reads them from a published view and caches them for at most a few seconds.

Never in a repository; only the names of the settings that hold them.

## Deployment
- **PoC and development:** `docker compose` on the Pi: PostgreSQL, control-backend, control-mcp (hosting the connector gateway behind its own listener until T-037 says the Pi can afford a fifth JVM; the gateway is idle in the PoC, since V10 comes after v1), hook-responder, agent-harness, the harness's egress proxy, a reverse proxy serving the web build, plus a `sim` profile with the simulators and the demo shop. Each JVM gets an explicit memory cap; check `free -h` first.
- **Our EU cloud or inside a bank's perimeter:** the same OCI images, one instance per bank. What differs is configuration: which network adapters are live, the processor profile, the identity provider, and whether model calls egress through the bank's gateway. Simulator images are never part of these deployments.
