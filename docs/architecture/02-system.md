## Why the MCP server is separate and thin
The LLM side reaches the control layer only through MCP tools. Making that server its own process with no database turns "the LLM cannot touch the core except through these tools" from a code convention into a network fact. Any later agent host (a partner platform, a bank's own assistant once banks come) plugs into the same server. The server is stateless and cheap.

### The tool surface
| Tool | What it does | Notes |
|---|---|---|
| `list_mandates`, `get_mandate` | read the active mandates of the caller | read only |
| `draft_mandate` | store the conversation's structured draft with the agent's **ready** assertion and a draft key; return its plain-words rendering, the backend's **enforceable** checklist result (the missing items by name), `ready` as stored and the draft's version | a draft has no effect (invariant 4); idempotent by the draft key (same content returns the stored response, changed content creates the next version); `ready` is the agent's own judgement that it can search accurately, audited with the draft, and nothing in the backend branches on it; a draft with missing items cannot be confirmed; the shopping tools need no mandate, `propose_purchase` does |
| `propose_purchase` | the shop's domain (or an admitted connector's merchant reference), lines (each a merchant item id **or** a typed item spec, with a quantity), `purchaseKey`, the agent's own description and reasons | the agent's text is untrusted and can only add caution ([ADR-0007](../adr/ADR-0007-cart-evidence-and-auto-purchase.md)); the domain is a name, never a URL, and the backend reaches the shop only through its discovery document ([ADR-0010](../adr/ADR-0010-standalone-app-and-provider-payment-tokens.md)); a line never carries personal data, that comes from `profiles` |
| `get_decision` | outcome, reasons, payment state of a proposal | read only |
| `get_activity` | answers "what did my agent buy and why" from the log | read only; amounts and ids come from the backend, never from the model |
| `get_agent_configuration` | the allowed models, the LLM spend cap and what is left of it, the agent's status, the connectors the user turned on (ids and the discovery tools each offers) | read only; how the operator's `settings` and the user's toggles reach the harness |

The harness learns the outcome of a step-up by polling `get_decision` for its `purchaseKey` while the conversation waits; the user sees the question and the answer in the app in any case. A step-up's expiry is set per decision as `min(the setting in settings, the stored checkout session expiry − a margin)` and recorded in the `DecisionInput`, so an approval after a step-up never lands on an expired session. A merchant whose sessions live minutes (airlines) therefore gets no useful step-up: there the outcome is auto-buy or no buy.

Not tools, by design: confirm a mandate, answer a step-up, approve anything, start a checkout, issue or revoke a token, save a payment method, change an agent's status, revoke a mandate, edit the profile, turn a connector on or off, link a merchant account. Confirming, answering, revoking, profile edits, payment methods, connector toggles and account links come only from the cardholder app to the backend, authenticated as the user. The confirm screen renders the mandate from the backend's **structured draft**, never from the chat's text, so what the user confirms is what the rules will enforce. Checkout and the token start in the backend after an APPROVE, never because the agent asked.

The agent harness's own runtime (not the model) sends the conversation and the agent trace to `control-mcp`'s ingest endpoint, so the audit export holds the whole thread. Ingest is idempotent by event id and stores the content as untrusted data. Because it comes from the untrusted side it is bounded: a size cap per event, a quota per agent instance and day (configurable, with a separate quota for watch runs so a long watch cannot starve the chat), and an event is attached to a `purchaseKey` only if that key belongs to the token's agent instance; otherwise it is stored unattached. Exceeding a cap is a named error and is itself recorded.

The same runtime claims due runs of standing mandates through `control-mcp`'s **run claim** endpoint (not a tool; the model never sees it). The backend answers with the run's mandate id and a short-lived agent run token, or with "nothing due".

### The merchant scan
When a search turns up a shop the user never bought from through us (as the harness's memory of purchases knows it; a labelled stand-in, and T-046 decides whether the harness reads the backend's record of shops through a tool instead), the harness's shopping tools also look up the shop's reviews and rating on the open web, through the same `GET`-only egress, and use them to rank results and to tell the user ([ADR-0010](../adr/ADR-0010-standalone-app-and-provider-payment-tokens.md), V11). Reviews are untrusted text: a rating may order results and raise caution in the conversation, it never reaches a rule as a permission. The backend does not depend on the scan: its own record of shops each user bought from drives the fixed rule that the first purchase at a new shop is at least STEP_UP.

### The connector gateway
Merchants that publish their own API or MCP server reach the agent only as **connectors** admitted into the catalogue ([ADR-0008](../adr/ADR-0008-merchant-connectors-and-the-connector-catalogue.md)). A connector's tools are classed in the manifest as **discovery** (search and read the catalogue), **account** (past orders, the order record by our reference, the payment method on file), **quote** (a priced quote, the slot list, a slot hold) or **order** (place the order on a quote). The gateway is the harness's second and last MCP server and exposes, per caller, the discovery-class tools of the connectors that caller's agent instance has turned on, and nothing else; the other three classes exist only in the backend's connector adapters. On each call it asks the backend whether the token's agent instance has that connector on, enabled and not suspended (the answer is cached for seconds); validates the arguments against the manifest's schema (enumerated or numeric fields where the merchant allows, every free-text field capped at the length in `settings`); calls the merchant anonymously at the manifest's address through its own egress fence (pinned origins, resolved addresses checked against private ranges on every connection, no redirects, arguments never placed in a host or path); caps and schema-checks the response, drops personal fields, types every free-text field `UntrustedText`; and logs the call into the ingest under the caller's agent instance. It serves the harness the manifest's **stored** tool definitions, never the live ones; it verifies the live canonicalised tool objects' hash at session start and on `notifications/tools/list_changed`, and a drift suspends the connector (the backend is told; toggles and links are untouched). It drops a merchant's `initialize` instructions, prompts, resources and logging or progress notifications. Like `control-mcp` it has no database and no business logic. Its MCP client towards merchants advertises no sampling, elicitation or roots, so a merchant can neither use our model nor question our user. A discovery query is still free text within its cap, so a compromised harness could leak conversation text through it as it could through a web search; the harness holds no payment or personal checkout data, which bounds that. T-037 measured it both ways (at most about 16 MB resident hosted, 182 MB as its own JVM; [07-walking-skeleton](07-walking-skeleton.md)), so until epic K needs it apart it runs inside the `control-mcp` process behind its own listener and its own client certificate towards the backend, limited to the connector endpoints; it is a separate deployable by design so it can be placed apart without a redesign.

## Identity between deployables
- **User → web → harness / backend:** local accounts are the production identity of the standalone app ([ADR-0010](../adr/ADR-0010-standalone-app-and-provider-payment-tokens.md)), behind one `CallerIdentity` port, so a bank's identity provider over OIDC can be added when banks come. Operators sign in to the console with operator roles in the same `identity` module.
- **Harness → control-mcp → backend:** the backend's `identity` module issues an **agent session token**: signed by the backend, bound to the cardholder, the agent instance and the audience `control-backend`. For a chat it is issued when the user opens the chat in the web app and is short-lived. The web app hands it to the harness with the chat session; the harness attaches the token to every MCP call and cannot mint or widen one. `control-mcp` forwards it **verbatim** and never derives or adds claims; the backend verifies it itself on every call. The model never supplies or sees identity. An agent's identity comes from this token, never from a request body. `control-mcp` and the backend also authenticate each other with mutual TLS, which proves the caller is `control-mcp` but grants no user rights by itself.
- **Standing mandates** ("look every morning", the price watch V9): the schedule is trusted data. The confirmed mandate carries the run frequency; `agents` keeps the **due runs**. The harness authenticates to `control-mcp` with mutual TLS (one client certificate per harness deployment); `control-mcp` passes that verified identity to the backend under its own mutual TLS. The harness runtime holds one long-lived **agent-instance credential**, bound to that certificate and able to do exactly one thing: claim due runs of its own agent instance. On a claim, `identity` mints a short-lived **agent run token** for that run, bound to the cardholder, the agent instance, the mandate and the run id, and limited to `propose_purchase`, `get_decision`, `get_mandate` and the trace ingest, so an unattended run leaves the same thread in the audit export as a chat. A claim is single-use; a second claim of the same run is refused and recorded, so a stolen credential racing the harness becomes visible. No run is due once the mandate is fulfilled, expired, revoked or the agent stopped, or while the cardholder has no notification channel left; nothing long-lived in the harness can propose a purchase on its own.
- **Harness → connector-gateway → merchant:** the same agent session token as towards `control-mcp`; the gateway forwards it to the backend's per-call check and never to a merchant. Towards a merchant the gateway is anonymous; no user token of any kind in v1. A run token is not accepted by the gateway: a standing mandate's list names merchant item ids, so a run needs no discovery.
- **User → merchant (account link):** one OAuth authorization-code consent per cardholder and connector, started from the cardholder app: PKCE; a `state` bound to the app session and checked at the callback; issuer identification (RFC 9207) so a response from one authorization server cannot be mixed with another's; the exact registered redirect URI; exactly the scopes the manifest fixes; refresh-token rotation. The merchant redirects to the backend's callback, and `payments` stores the token under a key per cardholder and connector wrapped by the cardholder's key. The agent cannot start, see or use it. A toggle off or an agent stop only blocks the link's use by that instance. The link ends by the user's unlink, the operator disabling the connector or the manifest's expiry: new quotes and orders stop at once, a resolution-only use remains until every checkout attempt and reconciliation read for the link is final or, at the latest, until the last order's slot end plus a reconciliation window from `settings`, then the token is revoked at the merchant (RFC 7009, where offered) and deleted; a case still open afterwards runs on the stored order record.
- **User → provider (saved payment method, 3-D Secure):** the user enters card or wallet details in the provider's own form inside the web app and completes 3-D Secure challenges in the provider's own SDK; the device talks to the provider directly. The backend creates the provider's setup on the user's behalf and receives only the provider's reference to the saved method ([06-consistency.md](06-consistency.md) §8).
- **Backend → provider:** the restricted key over the provider's API (below). **Provider → backend:** the provider's webhook signature, verified with the webhook signing secret.

## Data ownership in PostgreSQL
| Owner | Schema(s) | Others' access |
|---|---|---|
| control-backend | one schema per module (`identity`, `profiles`, `settings`, `agents`, `mandates`, `decisioning`, `ledger`, `payments`, `reconciliation`, `audit`, `activity`, `notifications`) plus the event publication registry | none |
| agent-harness | its own database (`harness`): conversations, memory | none; control data is not reachable from here |
| control-mcp, connector-gateway | none | — |

Every row that belongs to a user carries the cardholder id, and every lookup is scoped to the caller's cardholder: one multi-tenant installation serves every user ([ADR-0010](../adr/ADR-0010-standalone-app-and-provider-payment-tokens.md)).

Account-link tokens live in the `payments` schema, each encrypted under a key per cardholder and connector that is wrapped by the cardholder's key, so that unlinking one connector deletes one key and erasing the cardholder deletes the wrapping key; they are never in an event, a read model or a log. Saved payment methods are held only as the provider's references (with the brand, last four digits and expiry the provider returns for display), never card data. A payment token's id is kept on its checkout attempt to revoke and read it; it is never in an event, a read model, a log line or anything the harness can reach. Toggles, account links, payment methods, admission, approval, enablement, suspension and expiry are audited like every other change.

The audit tables and the webhook event record are insert-only: the roles lack `UPDATE` and `DELETE`, and a trigger rejects them.

**Personal data and erasure.** The audit store is insert-only, yet it holds whole conversations, and **we are the data controller** for every user of the standalone app ([ADR-0010](../adr/ADR-0010-standalone-app-and-provider-payment-tokens.md)). Retention and erasure were deferred on 2026-10-29; since 2026-11-19 they need their own ADR **before the first live user**. The design keeps the mechanism open by never putting personal text into a key, index or hash input, and by recording the cardholder id on every audit row, so an erasure mechanism (per-cardholder encryption with key deletion is the candidate) touches only the storage adapter. The `profiles` schema holds the buyer, traveller and delivery data a checkout needs; other modules and the `DecisionInput` keep only its version ids, so erasing a profile does not break a replay. Open item in [05-open-items.md](05-open-items.md).

## The backend's outbound calls to merchants
The trusted backend talks to merchants (discovery documents, checkout sessions, product records, offer searches for item specs, and, through admitted connectors, account reads, quotes, delivery slots and orders). That is the one place where the trusted zone reads from the outside world, so it is fenced ([ADR-0010](../adr/ADR-0010-standalone-app-and-provider-payment-tokens.md)):
- **Discovery.** The agent supplies a shop's domain, never a URL. The backend fetches only the protocol's fixed discovery document at that domain's HTTPS origin (UCP `/.well-known/ucp`, or the ACP equivalent) and takes the checkout endpoints and the seller's provider identity from there only, never from a session response, a page or the agent. The backend's record of shops a user bought from keys a shop by its domain together with that seller's provider identity, so a change of either is a new shop. The merchant directory caches the result with its fetch time; admitted connector manifests (and the demo shop in the PoC) are its other sources.
- **The fence**, for every merchant call: public addresses only (resolved addresses checked against private ranges on every connection), no redirects off the origin, responses parsed with size limits and strict schemas into typed fields, free text inside them typed `UntrustedText`.
- **Personal data before the decision.** Opening a session to price shipping and VAT sends the shop only the country and postcode from the current profile version where its protocol allows; the full address goes after APPROVE from the recorded profile version. Where a shop needs the full address to price, it is sent and the disclosure is recorded with the decision.
- **Connectors.** A connector call carries the user's account-link token only for the account-, quote- and order-class tools the manifest names, and only for the cardholder the decision or the reconciliation read belongs to; an order-class call is made only from a checkout attempt that exists for an APPROVE. The same fence (pinned origins, address checks on every connection, no redirects) applies to the OAuth token endpoints the manifest names.

Because each proposal opens a session or a quote at the merchant (for an airline, possibly a seat hold; for a grocer, possibly a slot hold), proposals are rate-limited per agent instance and per mandate in `settings`.

## The payment provider: restricted key and inbound webhooks
- **The restricted key.** The provider key the backend holds can save payment methods and issue, revoke and read payment tokens, and nothing else: no right to create charges, refunds or payouts, so the key the backend holds cannot pull money into our balance, and we never hold customer funds. A build test asserts that the `PaymentProvider` adapter contains no charge call. No running process holds an unrestricted key, and the provider dashboard roles that could charge a saved method are limited to named people and audited ([ADR-0010](../adr/ADR-0010-standalone-app-and-provider-payment-tokens.md); the account owner's residual ability to charge goes to the legal opinion, T-043).
- **One public webhook path.** The provider's events (token `requires_action`, `active`, `used`, `deactivated`; saved-method events) arrive on one public path of `control-backend`, not on a new JVM. Each request's signature is verified with the webhook signing secret before anything is parsed further; an unsigned or wrongly signed request is refused and counted. Events are deduplicated by the provider's event id under a unique constraint and recorded insert-only; processing follows from the record, idempotently and tolerating reordering ([06-consistency.md](06-consistency.md) §8).
- **Shop order webhooks** (UCP, ACP) arrive on their own path, are verified where the protocol defines a signature, and are recorded as **untrusted, merchant-reported** data: they feed reconciliation and the activity page, never a decision or a release of budget.
- **Cross-process traffic** is therefore: harness → `control-mcp` and `connector-gateway` → backend; web → harness and backend; web ↔ provider (form and 3-D Secure); backend → provider API; provider → backend webhooks; backend → shops; shops → backend order webhooks. No processor, no network, no bank.

## Deployment
- **PoC and development:** `docker compose` on the Pi: PostgreSQL, control-backend, control-mcp (hosting the connector gateway behind its own listener: T-037 measured at most about 16 MB resident for hosting it against 182 MB for a separate JVM ([07-walking-skeleton](07-walking-skeleton.md)), so it stays hosted until epic K needs it apart; the gateway is idle in the PoC, since V10 comes after v1), agent-harness, the harness's egress proxy, a reverse proxy serving the web build, plus a `sim` profile with the provider simulator, the demo shop and the drivers. The PoC itself runs against Stripe in test mode, with the demo shop as the test seller, reached for webhooks through a tunnel. Each JVM gets an explicit memory cap; check `free -h` first.
- **Production:** one multi-tenant installation in an EU cloud, the same OCI images, configured with the live provider adapter, the restricted key and the webhook secret ([ADR-0010](../adr/ADR-0010-standalone-app-and-provider-payment-tokens.md)). Simulator images are never part of it. Live payments wait for the legal opinion ([05-open-items.md](05-open-items.md)).
- **Banks later:** a bank channel would add its identity provider behind `CallerIdentity` and, if it wants one, its own authorisation check as a third line that consumes the token terms; neither is built now.
