# 05 Open items

What this design leaves open, and what closes each item. Backlog items are in [backlog.md](../backlog.md).

| Item | Why it is open | Closes it | Stand-in until then |
|---|---|---|---|
| Does Visa's agent checkout gateway return populated line items and totals in a UCP or ACP session? | known only from the published SDK models; no live response seen | T-034 (read the public UCP and ACP specs; one sandbox call once VIC access arrives) | the demo shop returns the cart as the specs describe it |
| Mastercard Agent Pay sandbox access | the agent-side APIs need a company registered with Mastercard as a certified agent platform, or a partner bank's access | T-035 | a labelled simulator of Level 3 and Verifiable Intent from public specs |
| Which model answers the intent check's typed questions | Jev (TypeSafe) fits the "typed questions, scored answers" shape; its deployment (EU, inside a bank), pricing, Java client and data retention are not yet known | T-036, then measured in the intent check and benchmark tasks | a fixture adapter |
| Signing the agent's browsing requests (Visa TAP `agent-browser-auth`) | the signing key belongs in the trusted zone, but browsing happens in the harness | T-005 (options: a signing endpoint on `control-mcp` limited to the browse tag; or no browse signing until a merchant requires it) | no browse signing in the PoC |
| The bank's processor, hook payload, timeout behaviour and clearing format | not public for Czech issuers | the first bank | Thredd- and Enfuce-shaped profiles; synthetic clearing files |
| The bank's identity provider, claims and token lifetimes | first-bank item | the first bank | local accounts behind `CallerIdentity` |
| Whether a bank-embedded agent counts as a "digital wallet" under Visa's agentic rules | needs the first bank and Visa | the first bank and Visa | nothing assumed |
| Java MCP SDK coverage for the tool surface and streamable HTTP transport, including a client that advertises no sampling, elicitation or roots and handles `tools/list_changed` | to be verified; [ADR-0009](../adr/ADR-0009-tech-stack-revision.md) lists what T-008 checks | T-008 spike | — |
| Sonar hosting: SonarCloud or a self-hosted SonarQube | SonarCloud's terms for a private repository are not checked; a self-hosted server needs memory the Pi, also the home server, may not have | T-008 (the user picks) | none; `./mvnw verify` runs the other checks locally |
| Java 25 support across the toolchain on aarch64 (Mockito and ByteBuddy, JaCoCo, the mutation tool, Sonar's analyser, Flyway, Testcontainers) | a new class-file version lags in some tools; not tried on the Pi | T-008 spike | none; ADR-0009 decides no fallback to Java 21 |
| Whether Spring Security's OAuth2 client performs the RFC 9207 issuer check and accepts registrations built from connector manifests without a fork | not tried; V10 is after v1 | the first item of epic K | the controls are fixed in 02-system and ADR-0009; a purpose-built client is the fallback |
| The log and telemetry export formats a bank's operations accept | first-bank item | the first bank | ECS-format JSON logs, Prometheus-style metrics on the management port, OTLP traces (ADR-0009) |
| Merchant identity mapping between the registry id in the checkout session and the acquirer merchant id, descriptor and category code in authorisation and clearing | not public; differs per acquirer | the first bank's hook data in shadow mode; T-005 proposes the conservative rule | shadow mode only; demo shop uses one id everywhere |
| The pre-approval window (how long after APPROVE an authorisation may match) | must cover the credential's validity and the merchant's authorisation delay; the network's credential lifetime is not public | T-005, then a sandbox run | a `settings` value, default seven days, equal to the credential TTL we request |
| Merchants that authorise in several parts (per shipment) | one pre-approval matches one authorisation id | T-005 (option: one pre-approval per expected part, from the cart's fulfilment data) | shadow mode records them; enforcing mode would decline the later parts |
| Cardholder assurance for the network instruction | the network wants proof of the cardholder's authentication when the instruction is created, and may hold it pending; our confirm screen is where that proof must come from | T-005 with the sandbox; the bank's passkey or app step later | local-account confirmation with a labelled assurance value in the sandbox; a mandate whose instruction is still pending cannot produce an APPROVE on that network |
| The network instruction's amount ceiling is in one currency while the budget is in the base currency | FX moves between confirmation and purchase | T-005: compile a conservative ceiling (rounded down with a margin from `settings`); our decision stays authoritative | — |
| Can our demo shop be reached through Visa's agent checkout gateway in the sandbox? | the gateway talks to merchants registered in Visa's registry; whether a sandbox merchant of ours can register is unknown | T-034, T-005 | call the demo shop's session endpoint directly through the same `Checkout` port, labelled "gateway bypassed" |
| Memory caps for four JVMs (five if the connector gateway runs apart), the simulators and PostgreSQL on the Pi | not measured | T-008, T-037 | explicit `-Xmx` per service |
| A processor profile that carries only the cardholder's billing amount | the match compares transaction amount and currency; a billing-only profile needs a tolerance rule | that bank | not supported |
| Retention and erasure of personal data in the insert-only audit store | deferred by the user (2026-10-29); the bank is the data controller; network rules ask for order confirmations for at least 120 days | a later ADR before the first bank; candidate: per-cardholder encryption of personal text, erasure by key deletion | keep everything; cardholder id on every audit row, personal text never in keys or hash inputs |
| Audit export format accepted by a bank's compliance | first-bank item | the first bank | JSON Lines per event plus a per-purchase summary; hash chain if cheap |
| Do checkout sessions carry travel attributes (origin, destination, date, passengers) as structured fields? | unattended flight purchase under ADR-0007 needs them settled by fixed rules; T-034 so far covers line items and totals only | T-034, widened to travel and other spec categories | a flight-shaped item in the demo shop, labelled synthetic |
| Any airline or travel agency on an agent checkout protocol, in Czechia or elsewhere | none named in any source read; Kiwi.com is the Czech candidate to check | T-034 | V9 is "watch, notify and link" wherever the merchant is unreachable |
| Travel agencies that charge their fee apart from the airline's fare | two merchants and two authorisations against one decision; the hook matches one | T-005, with the multi-part item above (one pre-approval per expected part from the cart) | shadow mode records the second; enforcing mode would decline it |
| Can a months-long network instruction release credentials without a fresh cardholder step, and can it be scoped to a category range rather than one merchant? | if not, an unattended standing mandate is impossible on that network | T-005 with the sandbox | the PoC watch runs against the demo shop |
| The web-push library for the `Notifier` port, and what the confirm screen requires as "reachable" | a standing mandate cannot be confirmed without a channel; [ADR-0009](../adr/ADR-0009-tech-stack-revision.md) chose server-sent events and e-mail (Jakarta Mail) for the PoC and left web push out of it | T-003 (contract and "reachable"); epic J (the push library) | server-sent events to the open app plus e-mail through a fixture sender |
| Whether Spring Modulith's verification accepts event types in the shared kernel's `events` package as the way to keep modules that listen to each other (`mandates`↔`agents`, `agents`↔`payments`, `payments`↔`mandates`) acyclic in code | not yet tried | T-037 | the shared kernel's `events` package, records of ids, amounts and enums only |
| What the first candidate grocer's MCP server and ordering API offer: a quote bound to prices with an idempotent order, a delivery address per order, slot holds and their expiry, substitution settings, whether a card-on-file order can require the cardholder's authentication, and the terms for third-party automated ordering | known only from its public description; no manifest drafted | T-038 | the demo connector, labelled synthetic, offers quote id, idempotent order and a weighed item |
| Whether a merchant's ordering API can be paid with a network agent credential instead of the card on file | would give connector orders the networks' line of defence | T-005, T-038 | the card on file: an agent card in a bank, the one-line mode standalone |
| A bank-issued agent card for connector orders: issuance, how the hook recognises its card id at the processor, how `payments` reads the card on file at each merchant (last four digits and network per manifest), and the processor's view of a grocer's late authorisation (slot end plus lag) | first-bank item; the merchant side comes from T-038 | the first bank, T-005, T-038 | standalone runs the labelled one-line mode after v1; nothing in the PoC |
| Whether ordering on a user's linked merchant account with a card on file makes us a payment initiation service or a similar regulated party | legal question outside the design | the user, with counsel, before the first bank | nothing assumed; ADR-0008 records the question in its consequences |
| The ledger counts the ceiling of a connector order; the difference to the billed amount, refunds, deposits and returned items freeing budget | the counting rule knows reservations at one amount | T-003 (counting rule) and the reconcile epic | the ceiling stays counted; reconciliation records the actual |
| The published connector manifest format and admission checklist, so a merchant can prepare its own connector | not yet written | T-003 (schema) and T-038 (first instance) | the demo connector's manifest |
| A fifth JVM for the connector gateway on the Pi | not measured | T-037 | hosted inside `control-mcp`'s process behind its own listener |
| Spending insights from the bank's transaction history (N19): consent basis, which derived facts, retention, how they reach the agent and the decision as caution only | noted by the user on 2026-10-31; not designed | a later ADR, after the first bank's data is known | nothing; past orders from a connector's account class feed only the merchant-derived list rule |
