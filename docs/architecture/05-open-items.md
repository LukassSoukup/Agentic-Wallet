# 05 Open items

What this design leaves open, and what closes each item. Backlog items are in [backlog.md](../backlog.md). The bank-, processor- and network-specific items (Visa's gateway, Mastercard Agent Pay access, browse signing, the processor's hook and clearing format, the bank's identity provider, the pre-approval window and multi-part authorisations, network instructions, merchant identity mapping to acquirer ids) were closed on 2026-11-19 by [ADR-0010](../adr/ADR-0010-standalone-app-and-provider-payment-tokens.md): the bank and the networks are no longer integrated, and the token is scoped to the seller identity the shop's own discovery document names. They return only with banks later.

| Item | Why it is open | Closes it | Stand-in until then |
|---|---|---|---|
| Does the SPT's maximum amount cap each charge or the cumulative total, and what happens with partial captures, split shipments, over-capture and incremental authorisations? | the provider documents the token as usable "until it expires, you revoke it, or cumulative captured payments reach" the maximum, so it is amount-capped rather than strictly single-use; our design deactivates it after the first confirmed use, and a shop that charges per shipment or captures above the authorisation would meet that | T-005, verified in Stripe test mode | the maximum equals the approved total; deactivate after the first `used` event; a second use is `UnexpectedTokenUsage` and a case |
| Which provider events carry the charged amount and currency, and can a charge be tied back to the seller's order | reconciliation can flag "charged more than approved" only where the provider's event says what was charged; otherwise only the token's limits stand | T-005 (test mode) | reconciliation matches by token id; the amount check is skipped and labelled where the event does not carry it |
| How many EU sellers accept SPT, through UCP, ACP or directly, by country | no public count exists; Stripe's agentic selling for EU businesses is announced, not confirmed as shipped ([payments-for-a-standalone-app](../research/payments-for-a-standalone-app.md)) | T-005, then tracked per milestone (T-007) | the demo shop as a Stripe test seller; "can't buy here" everywhere else |
| How often 3-D Secure is asked when a seller redeems the token, especially for unattended purchases (standing mandates) | SCA still applies at redemption; a frequent challenge makes the price watch lapse in the EU | T-005 with the provider's 3-D Secure test cards; then measured on the first live users | `PENDING_USER` with notification; lapse and release when unanswered |
| The provider's preview terms ("Agentic Commerce Agent Services Preview"): availability to an EU consumer app, fees, limits, country list, change notice | SPT is a preview product; its terms, limits and countries can change | T-005 (read and record), before live payments | Stripe test mode only |
| Legal opinion before live payments: the PSD2 technical service provider exclusion, our control over funds, the SPT preview terms, our GDPR duties as controller, and whether ordering on a user's linked merchant account with a card on file (ADR-0008) makes us a payment initiation service or a similar regulated party | the design stays outside payment licensing only while we never possess or control funds; a lawyer must confirm; PSD3 and the PSR are agreed, not yet applicable | T-043 (legal opinion), the user with counsel, before the first live payment | test mode only; the restricted key with no right to create charges, refunds or payouts |
| Retention and erasure of personal data in the insert-only audit store, and in application logs and traces, which carry pseudonymous ids ([ADR-0009](../adr/ADR-0009-tech-stack-revision.md)) | deferred by the user on 2026-10-29; since 2026-11-19 **we are the data controller**, so it is no longer deferrable past the first live user; order confirmations may need to be kept for disputes | T-045 (retention and erasure ADR), before the first live user; candidate: per-cardholder encryption of personal text, erasure by key deletion; a retention bound for logs and traces | keep everything; cardholder id on every audit row, personal text never in keys or hash inputs; log and trace retention is a configuration value; no live users |
| Does a live UCP or ACP session return populated line items, totals, shipping options and structured attributes, and a merchant-signed checkout, and how is the signature verified? | known from the public specs only; no live response seen | T-034 (read the public UCP and ACP specs and the discovery documents; one call at a live shop where one exists) | the demo shop returns the cart, the shipping options and a signed checkout as the specs describe them |
| Which model answers the intent check's typed questions | Jev (TypeSafe) fits the "typed questions, scored answers" shape; its deployment (EU), pricing, Java client and data retention are not yet known | T-036, then measured in the intent check and benchmark tasks | a fixture adapter |
| Java MCP SDK coverage for the tool surface and streamable HTTP transport, including a client that advertises no sampling, elicitation or roots and handles `tools/list_changed` | verified in T-008 ([toolchain-on-the-pi](../research/toolchain-on-the-pi.md)): tools, capabilities, `list_changed` (with the GET stream open) and a client certificate from an SSL bundle all work; the SDK has no Apache HttpClient transport, so the fenced merchant calls need an egress proxy or our own transport | epic K (the transport or the proxy) | an egress proxy in front of the gateway's merchant calls |
| Java 25 support across the toolchain on aarch64 (Mockito and ByteBuddy, JaCoCo, the mutation tool, Sonar's analyser, Flyway, Testcontainers) | confirmed in T-008 on the Pi with Temurin 25.0.5 ([toolchain-on-the-pi](../research/toolchain-on-the-pi.md)); jqwik (anti-AI usage clause, agent-directed text in test output) was rejected and the user chose jetCheck (ADR-0009 option 13, 2026-11-01) | closed | — |
| Whether Spring Security's OAuth2 client performs the RFC 9207 issuer check and accepts registrations built from connector manifests without a fork | not tried; V10 is after v1 | the first item of epic K | the controls are fixed in 02-system and ADR-0009; a purpose-built client is the fallback |
| More than one `control-backend` process per deployment (job locking, outbox resubmission, cache staleness, the webhook path behind a load balancer) | ADR-0009 assumes one process per deployment; one multi-tenant installation for consumers across the EU may outgrow it | a later ADR, when measured load or availability asks for it; T-037 recorded what a single process sustains ([07-walking-skeleton](07-walking-skeleton.md)) | one process per deployment; PostgreSQL may be highly available (02-system) |
| The log and telemetry export formats and the operations setup of the EU cloud | not chosen; no production deployment yet | the first production deployment (T-007 milestone) | ECS-format JSON logs, Prometheus-style metrics on the management port, OTLP traces (ADR-0009) |
| Memory caps for the JVMs (three, four if the connector gateway runs apart), the simulators and PostgreSQL on the Pi | measured idle by T-008 and with the purchase flow by T-037 ([07-walking-skeleton](07-walking-skeleton.md)) | closed | the caps in the T-037 report |
| Audit export format | users and their bank's dispute process are the readers now | T-003 and the audit epic | JSON Lines per event plus a per-purchase summary; hash chain if cheap |
| Do checkout sessions carry travel attributes (origin, destination, date, passengers) as structured fields? | unattended flight purchase under ADR-0007 needs them settled by fixed rules; T-034 so far covers line items and totals only | T-034, widened to travel and other spec categories | a flight-shaped item in the demo shop, labelled synthetic |
| Any airline or travel agency on an agent checkout protocol that accepts provider tokens, in the EU or elsewhere | none named in any source read; Kiwi.com is the Czech candidate to check | T-034 | V9 is "watch, notify and link" wherever the merchant is unreachable |
| Travel agencies that charge their fee apart from the airline's fare | two sellers and two charges against one decision; a token is scoped to one seller | T-005 (option: one token per seller from the cart's breakdown, each with its own terms) | not supported: such a cart is DECLINE "can't buy here" |
| The web-push library for the `Notifier` port, and what the confirm screen requires as "reachable" | a standing mandate cannot be confirmed without a channel; [ADR-0009](../adr/ADR-0009-tech-stack-revision.md) chose server-sent events and e-mail (Jakarta Mail) for the PoC and left web push out of it; a 3-D Secure challenge for an absent user needs the channel to reach them in time | T-003 (contract and "reachable"); epic J (the push library) | server-sent events to the open app plus e-mail through a fixture sender |
| Whether Spring Modulith's verification accepts event types in the shared kernel's `events` package as the way to keep modules that listen to each other (`mandates`↔`agents`, `payments`↔`mandates`) acyclic in code | confirmed by T-037: `payments` ↔ `mandates` listen to each other through kernel records and `ApplicationModules.verify()` passes ([07-walking-skeleton](07-walking-skeleton.md)) | closed | — |
| What the first candidate grocer's MCP server and ordering API offer: a quote bound to prices with an idempotent order, a delivery address per order, slot holds and their expiry, substitution settings, whether a card-on-file order can require the cardholder's authentication, and the terms for third-party automated ordering | known only from its public description; no manifest drafted | T-038 | the demo connector, labelled synthetic, offers quote id, idempotent order and a weighed item |
| Whether a merchant's ordering API can be paid with a provider token instead of the card on file | would give connector orders the provider-enforced line of defence | T-005, T-038 | the card on file, in the labelled one-line mode, after v1 |
| The ledger counts the ceiling of a connector order and the approved total of a token purchase; the difference to the billed amount, refunds, deposits and returned items freeing budget | the counting rule knows reservations at one amount; refunds do not restore budget automatically in v1 (ADR-0010) | T-003 (counting rule) and the reconcile epic | the approved amount stays counted; reconciliation records the actual and activity shows refunds |
| The published connector manifest format and admission checklist, so a merchant can prepare its own connector | not yet written | T-041 (schema) and T-038 (first instance) | the demo connector's manifest |
| A separate JVM for the connector gateway on the Pi | measured by T-037 both ways, hosted in `control-mcp` and as its own JVM ([07-walking-skeleton](07-walking-skeleton.md)): at most about 16 MB resident when hosted against 182 MB as its own JVM; the Pi can afford either | closed | hosted inside `control-mcp`'s process behind its own listener until epic K needs it apart |
| Spending insights from the user's own bank data (N19): consent basis, which derived facts, retention, how they reach the agent and the decision as caution only | noted by the user on 2026-10-31; not designed | a later ADR | nothing; past orders from a connector's account class feed only the merchant-derived list rule |
| `Money` at scale 2 against the provider's minor units and zero-decimal currencies (ISK, JPY, HUF and the provider's other special rules) | the token's maximum must equal the cart total exactly in the cart's currency; a currency whose minor unit is not 2 dp, or that the provider rounds by its own rule, could make the converted maximum differ from the approved total | T-010 (Money and FX), with T-005 for the provider's currency rules | the conversion to minor units happens in the `PaymentProvider` adapter only; a cart in a currency the adapter cannot represent exactly is DECLINE "can't buy here" |
