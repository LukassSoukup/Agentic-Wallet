# 04 One purchase, end to end

The cart and auto-purchase rules are decided in [ADR-0007](../adr/ADR-0007-cart-evidence-and-auto-purchase.md); the payment through a provider token, the merchant directory and the checkout states in [ADR-0010](../adr/ADR-0010-standalone-app-and-provider-payment-tokens.md); the deployables and modules in [02-system.md](02-system.md) and [03-modules.md](03-modules.md).

## Sequence
```
user      web     harness+LLM     control-mcp     control-backend                         shop / provider
 │ "buy …" │ ───────▶ │
 │         │          │ search, read pages, merchant scan (untrusted), rank with memory
 │         │          │ propose_purchase ─▶ │ validate, type text as untrusted
 │         │          │                     │ ─REST─▶ decisioning: purchaseKey seen? → same answer
 │         │          │                     │         payments: discovery document ───────▶ https://<shop>/.well-known/ucp
 │         │          │                     │                   ◀── endpoints, seller's provider identity
 │         │          │                     │         payments: open checkout session ────▶ shop's UCP/ACP endpoint
 │         │          │                     │                   (country and postcode only)
 │         │          │                     │                   ◀── priced cart, merchant-signed (tier 1)
 │         │          │                     │         or: quote through an admitted connector ─▶ merchant API
 │         │          │                     │                   ◀── priced quote (+ ceiling) (tier 1)
 │         │          │                     │         payments: product records ──────────▶ catalogue (tier 2)
 │         │          │                     │         intent model: typed questions ──────▶ extraction model
 │         │          │                     │         control-core: decide(input), token terms  (pure)
 │         │          │                     │         ONE TRANSACTION: decision with token terms, reservation,
 │         │          │                     │                          audit record, outbox rows
 │         │          │ ◀── outcome + reasons
 │ STEP_UP: question ◀── backend (event) ; answer ──▶ backend directly (never via MCP)
 │                                          backend: re-check → APPROVE or DECLINE
 │                                          payments (event listener after APPROVE):
 │                                            issue token: seller, max amount, currency, expiry ──▶ provider
 │                                            complete checkout with the token and the address ──▶ shop
 │                                                       shop charges the token ──▶ provider ──▶ user's bank
 │ 3-D Secure? ◀── provider's SDK in the web app ◀── webhook requires_action ◀─────────────── provider
 │                                          webhook used ◀────────────────────────────────────── provider
 │                                          payments: COMPLETED; token deactivated ───────────▶ provider
 │                                          reconciliation: decision ↔ token events ↔ shop order record
```

## Steps
1. **Shop (harness).** The agent searches and reads merchant pages as untrusted text, and searches the catalogues of the connectors the user turned on through the connector gateway's discovery tools (also untrusted text). For a shop the user never bought from through us, the **merchant scan** reads its reviews and rating, which may order results and add caution, and tells the user. It ranks with the user's memory and picks the shop, items and quantities. It never picks a delivery slot or a shipping option; the backend does. Memory and reviews may lead to a question, never a permission.
2. **Propose (control-mcp).** `propose_purchase` carries the `purchaseKey` (the harness generates it once per intended purchase and reuses it on every retry), the shop's domain (or an admitted connector's merchant reference), the lines (each a merchant item id **or** a typed item spec, with a quantity) and the agent's own description and reasons. A line never carries personal data; a proposal that does is rejected as a named error. The server validates the shape, wraps every free-text field as `UntrustedText`, attaches the caller's identity from the session or run token and forwards it to the backend.
3. **Idempotency.** The key is (agent instance, `purchaseKey`). Equal binding fields (shop, lines, quantities, mandate) return the stored decision; different binding fields are a conflict (invariant 7). The agent's free text is not compared ([06-consistency.md](06-consistency.md) §5).
4. **Discovery, reachability and route.** `payments` looks the shop up in its **merchant directory**. For a domain it has no fresh entry for, it fetches only the protocol's fixed discovery document at that domain's HTTPS origin (UCP `/.well-known/ucp`, or the ACP equivalent), under the fence (public addresses only, no redirects off the origin, size and schema limits), and takes the checkout endpoints and the seller's provider identity from there only, never from a session response, a page or the agent ([02-system.md](02-system.md)). Admitted connector manifests and, in the PoC, the demo shop are the directory's other sources (the demo connector joins in epic K). No discovery document, no checkout that accepts the provider's tokens and no admitted ordering connector means DECLINE with the reason "this shop can't be bought from by an agent". A connector merchant whose connector is suspended, not enabled by the operator or turned off by the user, or whose account is not linked, is DECLINE with that reason (the app, not the chat, offers the fix). Otherwise `payments` selects the **route**: for a protocol checkout, which of the user's saved payment methods pays, by fixed rules from the mandate's allowed methods and the user's preference order; for a connector, the linked account the mandate names and the payment method on file there (last four digits and network), read through the `MerchantAccount` port while gathering evidence and read again when the attempt enters `COMPLETING`; a card-on-file order passes only where `settings` allows the labelled one-line mode, otherwise the route rule is DECLINE. The decision (step 7) records that route with its reason and re-validates it; it can decline the route, never switch it. A change of payment method is a new proposal.
5. **Gather cart evidence.** `payments` opens the checkout session straight at the shop's UCP or ACP endpoint from the directory with the item ids and quantities, sending only the country and postcode of the current profile version where the protocol allows (where a shop needs the full address to price shipping and VAT, it is sent and the disclosure recorded), and receives the shop's priced cart in the shop's currency, the shipping options it offers and, where the protocol provides one, a **merchant-signed checkout** (UCP checkout JWT), which `payments` verifies and stores as tier-1 evidence. A pure rule in `control-core` picks the shipping option (the cheapest that satisfies the mandate; every option is kept for the `DecisionInput`), and the session is updated to it. A line with an **item spec** (a flight: origin, destination, local date, passenger count, cabin) is first checked against the mandate's facts as a hard rule, then resolved: `payments` searches the merchant's offers through the `MerchantCatalogue` port at the directory's endpoint, a pure rule in `control-core` picks among the matches by their search prices (the lowest total that satisfies every structured requirement), every candidate is kept for the `DecisionInput`, and no match is DECLINE. One session is then opened on the chosen offer, and its total is what binds. At a **connector merchant**, `payments` lists the delivery slots inside the mandate's window, a pure rule in `control-core` picks one (the earliest, then the cheapest; every candidate is kept for the `DecisionInput`), and `payments` asks the connector for a priced **quote** for exactly these lines, that slot and the delivery address from the profile version it records (a quote-class call with the user's token; a side effect at the merchant, never a payment, rate-limited like a session). The quote total binds. Where the manifest says the final amount can differ, `payments` gathers the **ceiling's components** (the quote total, each weighed line's price and the manifest's allowance for it, the fees and deposits from the quote or the manifest's maxima) and the pure `ceiling` function in `control-core` turns them into the amount the rules see. The user's own cart at the merchant is never written. It also fetches the merchant's product records where the merchant publishes them, and reads whether this cardholder has bought at this shop through us before. See the tiers below.
6. **Extract facts (outside the core).** Mandate requirements are stored as structured facts (attribute, operator, value) since the confirm step. For each requirement that structured cart data cannot settle, fixed code derives one typed question ("is the size 42?", "is it leather?") and asks the intent model about the merchant's product text. The answers and their scores are stored as decision inputs. A failed or slow call means no answer.
7. **Decide (pure core).** `decide(DecisionInput) → Decision`. Order: hard rules (`converted + margin` against the limit with the mandate's operator, `<` or `≤`, where the amount is the session total or the connector ceiling converted at the decision's FX rate into the currency of the limit it is compared with (the mandate's confirmed currency; the base currency for the global budget), the margin added on that cart side only; budget, each counted in its period's currency (a mandate budget in the mandate's confirmed currency, the global budget in the user's base currency current when its period opened); purchase count; merchant; category; quantity; timing; the item spec inside the mandate's facts; the route still valid; for a connector order the picked slot inside the window, the minimum order met, the connector admitted, enabled and not suspended, the toggle on for this instance, the account linked and named by the mandate, a card-on-file order only where the one-line mode is allowed; a failure is DECLINE), then the fixed caution rules that can only raise (the **first purchase by this user at a shop new to them** → at least STEP_UP; a merchant-derived item list with no completed purchase under this mandate version → STEP_UP), the intent check (matches, deviates or uncertain, per ADR-0007), ledger checks (duplicate, split order, velocity), routing feasibility, then the caution combiner, where the outcome only rises: APPROVE < STEP_UP < DECLINE. A risk signal, a model finding or a merchant scan can only raise it. Every decision carries its reasons. For an APPROVE the pure **token terms** function derives what the token will allow: the seller's provider identity from the directory, a maximum amount equal to the approved cart total in the cart's currency, that currency, and an expiry at the earlier of the stored checkout session expiry and the decision time plus the attempt window from `settings` ([ADR-0010](../adr/ADR-0010-standalone-app-and-provider-payment-tokens.md)).
8. **Commit.** One transaction, under row locks on the budget periods it touches: the decision with its token terms (APPROVE only), the ledger reservation (APPROVE only), the audit record with the complete `DecisionInput` (the replay unit), and the outbox rows ([06-consistency.md](06-consistency.md) §1, §6).
9. **Step-up (M5).** The cardholder app shows one specific question with the shop's cart (in the shop's own price and currency), the reasons and an approve/decline answer, with an expiry set per decision as `min(the configured ceiling, the stored session expiry − a margin)`. The answer goes from the app to the backend, authenticated as the user. On approve, `decisioning` makes a **second decision** in one transaction: same mandate version, the ledger still allows it under the budget locks, the route still valid, the checkout session's, quote's or slot hold's stored expiry has not passed (no merchant call inside the transaction; an expired one means DECLINE with "propose again"). On APPROVE it reserves, stores its own token terms and its own `DecisionInput` ([06-consistency.md](06-consistency.md) §2). Expiry is enforced by a scheduled job in `decisioning`. Expiry or decline releases nothing, because nothing was counted.
10. **Token and checkout (payments, after APPROVE).** An outbox listener drives a persisted **checkout attempt** ([06-consistency.md](06-consistency.md) §3): it issues **one payment token** through the `PaymentProvider` port on the routed saved payment method with exactly the stored token terms (seller, maximum amount, currency, expiry), with the provider's idempotency key derived from the attempt id, so a repeated call returns the same token; it fills the buyer, traveller or delivery details from the **profile version** the decision recorded (read from `profiles` at this moment, never carried in an event or a proposal); and it completes the shop's checkout session with the token, using an idempotency key derived from the `purchaseKey`. The token's id stays on the attempt; it is never logged, put in an event or given to the harness. **Through a connector** there is no token, unless the connector merchant accepts provider tokens ([ADR-0008](../adr/ADR-0008-merchant-connectors-and-the-connector-catalogue.md) as amended; see [05-open-items.md](05-open-items.md)); then the token path of [06-consistency.md](06-consistency.md) §3 applies. Otherwise the attempt goes `CREATED → COMPLETING` and places the order on exactly the quoted id through the user's linked account, with the delivery address from the recorded profile version and our idempotency key as the merchant's order reference; the merchant charges what is on file (one line of defence, labelled). An `UNKNOWN` outcome is resolved by looking up that order reference through the `MerchantAccount` port, never by placing the order again; a merchant that asks for the cardholder's authentication on a card-on-file order puts the attempt in `PENDING_USER`, and the same lookup tells when it went through ([06-consistency.md](06-consistency.md) §3).
11. **Charge, 3-D Secure and token use.** The shop charges the token through the provider; the provider enforces the token's limits (this seller only, at most the maximum amount, before the expiry) and the user's bank pays. When the bank asks for 3-D Secure, the provider reports `requires_action`: the attempt goes `PENDING_USER`, the user is notified and completes the challenge in our web app through the provider's own SDK; when the user is away and the challenge is not completed before the token or the cart expires, the purchase lapses, the reservation is released once the token is dead, and the user is told. The provider's `used` webhook confirms the charge: the attempt is `COMPLETED`, the reservation counted, and the token is deactivated after this first confirmed use ([06-consistency.md](06-consistency.md) §4). This is the second line of defence, and it is described as what it is: limits our backend set, enforced by the provider ("this shop can charge at most €90, until 10:30"), not an independent check.
12. **Reconcile.** The decision and its token terms, the token's events from the provider and the shop's order record (its order webhook, merchant-reported, and the session status) are matched. A mismatch we can see (a charged amount above the terms where the provider's event carries it, a second use, a use or an order with no decision, a missing confirmation) opens a case with drafted dispute evidence the user files with their bank. What we cannot see (the amount billed in the card's currency, refunds, chargebacks, charges outside our token) is said so in the app; a refund does not restore budget automatically in v1. For a connector order the merchant's order record and invoice lines (read through the account class, kept as merchant-reported) are matched against the approved lines and the ceiling; a billed amount above the ceiling or a line that was not approved opens a case.

## Standing mandates: the same flow without the user
A price watch (V9) or "look every morning" mandate runs the twelve steps above with four differences. **Who starts it:** the confirmed mandate carries a run frequency and a purchase count; `agents` keeps the due runs; the harness runtime claims one, gets a short-lived agent run token for that mandate and runs the watch module ([02-system.md](02-system.md), identity). **How it shops:** the price check in the harness is advisory and needs no model; only a candidate below the threshold is proposed, with a `purchaseKey` derived from the mandate, the run and the offer, so a retried run repeats the same proposal while a later run gets a fresh decision on today's price. **What the user sees:** nobody is in chat, so the mandate's "when unsure" policy defaults to "decline and tell me", the confirm screen says plainly that the watch either buys on its own or does not buy (a step-up cannot wait for a fare that lives minutes), and `notifications` reports completed, unknown, failed, lapsed and unsettled-requirement outcomes over the user's channel. The first purchase at a shop new to the user is a STEP_UP, so an unattended run at a new shop under "decline and tell me" does not buy there. **3-D Secure:** a challenge at redemption while the user is away is announced at once; if it is not completed before the token or the cart expires, the purchase lapses cleanly and the user is told (user, 2026-11-19). Reaching the purchase count makes the mandate fulfilled: no more runs. A failed or cancelled attempt releases its reserved count once its token is dead, and the watch goes on; an unknown one holds the count until resolved, so a run in the meantime is declined on the count.

Where the fare is in a foreign currency, the limit is compared at the decision's FX rate plus the margin from `settings`, in the currency the user confirmed the mandate in (changing the base currency later never changes it); the user is shown the shop's own price and the currency their card will be charged in, and the converted figure only labelled as our rules' check ("about … at today's rate"). What the user's bank finally bills in the card's currency is a blind spot: `reconciliation` cannot flag it.

## Cart evidence tiers
| Tier | Source | What it can establish |
|---|---|---|
| 1 | The shop's priced cart returned through a protocol checkout session at the shop's own endpoint (with the merchant-signed checkout where the protocol provides one), or the priced quote an admitted connector returned, both fetched by the backend ([ADR-0008](../adr/ADR-0008-merchant-connectors-and-the-connector-catalogue.md), [ADR-0010](../adr/ADR-0010-standalone-app-and-provider-payment-tokens.md)) | binding facts: shop, item ids, quantities, unit prices, total (or the ceiling derived from it), currency, shipping option, delivery slot; structured attributes the merchant sends |
| 2 | Product records the backend fetched from the merchant's own catalogue or feed | descriptive facts; structured fields such as GTIN, size or category, by fixed rules |
| 3 | What the agent says (its description, reasons, the pages it read, the merchant scan) | nothing positive; a contradiction with tiers 1 and 2 raises the outcome to at least STEP_UP |

**Auto-purchase (APPROVE without asking) needs tier 1, every requirement in the mandate settled by fixed rules over tier 1 or tier 2 structured data, and a shop the user has bought from through us before.** A tier-1 cart that leaves a requirement open is at most STEP_UP, and the user decides on that cart's binding total. **No tier-1 cart or quote means DECLINE "can't buy here"**: nothing binding exists to approve or to pay. Through a connector, auto-purchase also needs an order that the merchant binds to the quote (a quote id with an order idempotent on our reference, or a two-phase order); a merchant that offers neither is not admissible for ordering, so it is DECLINE "can't buy here" like a merchant with no session. A broken hard limit is DECLINE whatever the evidence. The intent model can find a problem but never clear one, because invariant 2 allows a model to make a decision more cautious, never less. So mandates that name exact products, categories or price ranges can run on their own at shops the user knows, and free-text quality requirements ("leather, size 42" when the merchant sends only a title) go to the user.

The **seller** the decision approves is the provider identity the shop's own discovery document names, and the token is scoped to exactly that seller, so the provider enforces it; reconciliation matches the provider's events by token, so no mapping to acquirer merchant ids, descriptors or category codes is needed.

Where this works today: at shops that run a UCP or ACP checkout and accept the provider's tokens, few in the EU today (no public count; no airline or travel agency anywhere), and at merchants with an admitted connector, which the operator adds one reviewed manifest at a time (a Czech online grocer with its own MCP server is the first candidate, T-038). In the PoC this is our demo shop as a Stripe test seller; the demo connector comes with epic K. The merchant directory records which structured attributes each shop settles, so the confirm screen can warn when no reachable shop can settle a requirement and the mandate could never buy on its own. Which fields a live UCP or ACP session populates is known from the public specs only; T-034 checks it.

## Failure behaviour
| Situation | Behaviour |
|---|---|
| The shop has no discovery document, it fails the fence (private address, redirect off the origin, oversize, bad schema), or it names no checkout that accepts the provider's tokens | DECLINE "can't buy here" (reason: no agent checkout); nothing else at that domain is fetched |
| The shop offers no agent checkout session, can't open one, or returns an error | DECLINE "can't buy here" (reason: no session). A session that opened but left requirements unsettled is a STEP_UP with that cart |
| The merchant-signed checkout fails verification | the cart is not tier-1 evidence: DECLINE "can't buy here", recorded |
| The shop needs the full address before it can price | it is sent, and the disclosure is recorded with the decision; the user sees it in the purchase's detail page |
| First purchase by this user at this shop | at least STEP_UP with its own reason code, mapped through the mandate's "when unsure" policy like an open requirement: a question, or on a standing mandate set to "decline and tell me" a decline that tells the user |
| A connector merchant whose connector is suspended (tool list drifted, approval expired), not enabled by the operator or turned off by the user, or whose account is not linked | DECLINE with that reason; the user is told where to fix it (the app), never asked in chat; the agent may still research and link |
| The quote or the slot hold expires before the step-up is answered | the expiry per decision was bounded by it; an answer after it is DECLINE "propose again" |
| The merchant's order call answers with a different total than the quote | the attempt is `FAILED` with "cart changed"; a new quote is a new proposal |
| The merchant's final amount after picking is above the ceiling, or an invoice line was not approved | `reconciliation` flags it and opens a case; the ledger counted the ceiling; the difference and refunds are an open item |
| A connector order would pay with the card on file at the merchant | the route rule is DECLINE, unless `settings` allows the one-line mode, which the user was told about at the link and when the mode changed |
| The card on file changed between the decision and the order (a step-up can take hours) | the re-read at `COMPLETING` no longer matches: the attempt is `FAILED` with "card on file changed"; the reservation is released (no token exists); a new proposal is needed |
| The merchant requires the cardholder's authentication on a card-on-file order | `PENDING_USER`, bounded by the quote's expiry; the user finishes it in the merchant's or their bank's flow; the order lookup tells when it went through |
| A connector order times out | `UNKNOWN`; the resolver looks up our order reference at the merchant (the window runs to the slot's end plus the manifest's authorisation lag); found means `COMPLETED`, not found by the window's end means `FAILED`; the order is never placed again blindly |
| The order lookup is impossible (the link ended and its resolution-only use is gone, or the merchant is unreachable past the window) | the attempt stays `UNKNOWN` and a mismatch case is opened; never a silent `FAILED` that releases approved money |
| The harness is asked to connect another MCP server | impossible by mechanism: the two server addresses are deployment configuration, the harness refuses to start with any other, and its egress policy allows nothing else; nothing in a conversation, a tool result or the user's settings can add one |
| The intent model times out, errors or exceeds its spend cap | no answer → the requirement stays unsettled → uncertain → the mandate's "when unsure" (ask or decline), never approve |
| The user's bank asks for 3-D Secure when the shop charges the token | `PENDING_USER`: our decision stands and the reservation counts; the user completes the challenge in our web app through the provider's SDK; success continues to `COMPLETED`; failure or expiry leaves the token dead, then `FAILED`, release, the user is told |
| The bank asks for 3-D Secure while nobody is present (standing mandate) | `PENDING_USER` is bounded by the token's expiry and the stored session expiry; when either passes the purchase lapses: `FAILED` once the token is dead, release, the watch goes on, and the user is told |
| The token was issued but the checkout fails | the token is revoked first; once the provider confirms it revoked (or it has expired), the attempt is `FAILED` and the reservation released in that transaction; a retry with the same `purchaseKey` gets the stored decision, and a new token needs a new decision |
| The completion call times out | the attempt is `UNKNOWN`, never `FAILED`: the reservation stays; `CheckoutOutcomeUnknown` tells the user and the activity page; a resolver reads the session status and the token's state; a used token makes it `COMPLETED`; a token dead and unused with no completed session makes it `FAILED`; the token's expiry bounds the wait |
| The mandate is revoked or the agent stopped after APPROVE | an attempt in `CREATED` is `CANCELLED`; otherwise the unused token is revoked, and the attempt is `CANCELLED` once the provider confirms it, or `COMPLETED` if the token was already used |
| The shop tries to charge more than approved, a second time, or after the token's end | the provider refuses beyond the token's limits; a use we did not expect is recorded as `UnexpectedTokenUsage` and opens a case; whether the maximum caps one charge or the total is verified in T-005 ([05-open-items.md](05-open-items.md)) |
| A webhook arrives with a bad signature, or the same provider event twice | a bad signature is refused and counted, nothing is processed; a duplicate event id is recorded once and processed once |
| The process dies between issuing the token and completing | on restart the attempt is resolved from the session status and the token's state; a repeated issue call carries the same idempotency key and returns the same token, so there is never a second token for one decision |
| An item spec matches no offer, or several | none: DECLINE "nothing matches"; several: the core's pick rule chooses, every candidate is in the `DecisionInput` |
| The agent puts a name, address or document in a proposal | a line has a closed schema; unknown fields are rejected as a named error before any merchant call; recorded. Personal fields a merchant echoes back are dropped before storage |
| Too many proposals or runs for one mandate or agent | the caps in `settings` return a named error; recorded; the watch's next run is still claimable when its turn comes |
| Two proposals race for the last of a budget | budget-period row locks: exactly one reserves; the other is decided on the updated ledger |
| The shop changes the price or adds items at completion | the amount or items no longer match the decision; the token's maximum refuses a higher charge; the attempt revokes the token and goes to `FAILED` with "cart changed" once it is dead; the new cart is a new proposal |
| The same request arrives twice (proposal, event, webhook) | deduplicated by `purchaseKey`, outbox event id or the provider's event id |
| The harness or the LLM is down | nothing is proposed; the backend, the webhooks and the cardholder app keep working |
| Hostile text in a product page, a review or the agent's reasons | stored as data; the suspicious-text flag raises the outcome to at least STEP_UP |
