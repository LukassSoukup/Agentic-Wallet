# 04 One purchase, end to end

The cart and auto-purchase rules are decided in [ADR-0007](../adr/ADR-0007-cart-evidence-and-auto-purchase.md); the deployables and modules in [02-system.md](02-system.md) and [03-modules.md](03-modules.md).

## Sequence
```
user      web     harness+LLM     control-mcp     control-backend                         merchant / network
 │ "buy …" │ ───────▶ │                                                                    
 │         │          │ search, read pages (untrusted), rank with memory                   
 │         │          │ propose_purchase ─▶ │ validate, type text as untrusted              
 │         │          │                     │ ─REST─▶ decisioning: purchaseKey seen? → same answer
 │         │          │                     │         payments: merchant reachable? ──────▶ registry
 │         │          │                     │         payments: open checkout session ────▶ UCP/ACP session
 │         │          │                     │                   ◀── priced cart (evidence tier 1)
 │         │          │                     │         or: quote through an admitted connector ─▶ merchant API
 │         │          │                     │                   ◀── priced quote (+ ceiling) (tier 1)
 │         │          │                     │         payments: product records ──────────▶ catalogue (tier 2)
 │         │          │                     │         intent model: typed questions ──────▶ extraction model
 │         │          │                     │         control-core: decide(input)  (pure)
 │         │          │                     │         ONE TRANSACTION: decision, reservation, pre-approval,
 │         │          │                     │                          audit record, outbox rows
 │         │          │ ◀── outcome + reasons
 │ STEP_UP: question ◀── backend (event) ; answer ──▶ backend directly (never via MCP)
 │                                          backend: re-check → APPROVE or DECLINE
 │                                          payments (event listener after APPROVE):
 │                                            request credential for exact amount + merchant ──▶ VIC / Agent Pay
 │                                            complete checkout with it (same idempotency key) ─▶ merchant
 │                                            confirm to network with the decision id ─────────▶ network
 │                                          credential discarded; "released" event recorded
 │                                                   merchant's PSP authorises ─▶ network ─▶ bank processor
 │                                                   bank processor ─▶ hook-responder: match pre-approval
 │                                          reconciliation: decision ↔ authorisation ↔ clearing
```

## Steps
1. **Shop (harness).** The agent searches and reads merchant pages as untrusted text, and searches the catalogues of the connectors the user turned on through the connector gateway's discovery tools (also untrusted text), ranks with the user's memory, and picks merchant, items and quantities (and, at a delivery merchant, a slot inside the mandate's window). Memory may lead to a question, never a permission.
2. **Propose (control-mcp).** `propose_purchase` carries the `purchaseKey` (the harness generates it once per intended purchase and reuses it on every retry), the merchant reference, the lines (each a merchant item id **or** a typed item spec, with a quantity) and the agent's own description and reasons. A line never carries personal data; a proposal that does is rejected as a named error. The server validates the shape, wraps every free-text field as `UntrustedText`, attaches the caller's identity from the session or run token and forwards it to the backend.
3. **Idempotency.** The key is (agent instance, `purchaseKey`). Equal binding fields (merchant, lines, quantities, the typed delivery slot where there is one, mandate) return the stored decision; different binding fields are a conflict (invariant 7). The agent's free text is not compared ([06-consistency.md](06-consistency.md) §5).
4. **Reachability and route.** `payments` looks the merchant up in its directory (built from the networks' merchant registries, the admitted connector manifests and, in the PoC, the demo shop and the demo connector). No agent checkout path on any of the user's allowed networks and no admitted ordering connector means DECLINE with the reason "this merchant can't be bought from by an agent". A connector merchant whose connector is suspended, not enabled by the bank or turned off by the user, or whose account is not linked, is DECLINE with that reason (the app, not the chat, offers the fix). Otherwise `payments` selects the **route**: for a network path the card and network by fixed rules from the mandate's allowed cards, the user's preference order and the merchant's paths, because the checkout session is opened on one network's path; for a connector the linked account the mandate names, and the payment on file there (an enrolled agent card, or another card where `settings` allows the one-line mode). The decision (step 7) records that route with its reason and re-validates it; it can decline the route, never switch it. A card change is a new proposal.
5. **Gather cart evidence.** If the merchant supports protocol checkout sessions (UCP or ACP through Visa's gateway; a Mastercard Level 3 merchant API, simulated), `payments` opens the session with the item ids and quantities and receives the merchant's priced cart. A line with an **item spec** (a flight: origin, destination, local date, passenger count, cabin) is first checked against the mandate's facts as a hard rule, then resolved: `payments` searches the merchant's offers through the `MerchantCatalogue` port at the directory's endpoint, a pure rule in `control-core` picks among the matches by their search prices (the lowest total that satisfies every structured requirement), every candidate is kept for the `DecisionInput`, and no match is DECLINE. One session is then opened on the chosen offer, and its total is what binds. At a **connector merchant**, `payments` instead asks the connector for a priced **quote** for exactly these lines, the proposed slot and the delivery address from the profile version it records (the user's token is used for this call and no other purpose); the quote total binds, and where the manifest says the final amount can differ (weighed goods, substitutions, fees, deposits) `payments` computes the **ceiling** from the quote and the manifest's declared allowances plus the mandate's substitution policy, and that ceiling is what the amount rules see. It also fetches the merchant's product records where the merchant publishes them. See the tiers below.
6. **Extract facts (outside the core).** Mandate requirements are stored as structured facts (attribute, operator, value) since the confirm step. For each requirement that structured cart data cannot settle, fixed code derives one typed question ("is the size 42?", "is it leather?") and asks the intent model about the merchant's product text. The answers and their scores are stored as decision inputs. A failed or slow call means no answer.
7. **Decide (pure core).** `decide(DecisionInput) → Decision`. Order: hard rules (`converted + margin` against the limit with the mandate's operator, `<` or `≤`, where the amount is the session total or the connector ceiling; budget; purchase count; merchant; category; quantity; timing; the item spec inside the mandate's facts; for a connector order the slot inside the window, the minimum order met, the connector admitted and on, the account linked; a failure is DECLINE), the intent check (matches, deviates or uncertain, per ADR-0007), ledger checks (duplicate, split order, velocity), routing feasibility, then the caution combiner, where the outcome only rises: APPROVE < STEP_UP < DECLINE. A risk signal or a model finding can only raise it. Every decision carries its reasons.
8. **Commit.** One transaction, under row locks on the budget periods it touches: the decision, the ledger reservation (APPROVE only), the pre-approval for the bank's hook (APPROVE only), the audit record with the complete `DecisionInput` (the replay unit), and the outbox rows ([06-consistency.md](06-consistency.md) §1, §6).
9. **Step-up (M5).** The cardholder app shows one specific question with the merchant's cart, the reasons and an approve/decline answer, with an expiry set per decision as `min(the configured ceiling, the stored session expiry − a margin)`. The answer goes from the app to the backend, authenticated as the user. On approve, `decisioning` makes a **second decision** in one transaction: same mandate version, the ledger still allows it under the budget locks, the checkout session's stored expiry has not passed (no merchant call inside the transaction; an expired session means DECLINE with "propose again"). On APPROVE it reserves, writes the pre-approval and stores its own `DecisionInput` ([06-consistency.md](06-consistency.md) §2). Expiry is enforced by a scheduled job in `decisioning`. Expiry or decline releases nothing, because nothing was counted.
10. **Checkout (payments, after APPROVE).** An outbox listener drives a persisted **checkout attempt** ([06-consistency.md](06-consistency.md) §3): it requests one credential for exactly this amount, merchant and line items (VIC `/credentials` with the mandate reference; the Agent Pay token and cryptogram in the simulator), fills the buyer, traveller or delivery details from the **profile version** the decision recorded (read from `profiles` at this moment, never carried in an event or a proposal), completes the merchant's checkout session with it using an idempotency key derived from the `purchaseKey`, and sends the network confirmation with the decision id as its reference. The credential lives only in memory for that call and is never stored or logged; only the event "credential released" is recorded. **Through a connector** there is no credential step: the attempt goes `CREATED → COMPLETING` and places the order on exactly the quoted id through the user's linked account, with the delivery address from the recorded profile version and our idempotency key as the merchant's order reference; the merchant charges what is on file. An `UNKNOWN` outcome is resolved by looking up that order reference, never by placing the order again; a merchant that asks for the cardholder's authentication on a card-on-file order puts the attempt in `PENDING_USER` ([06-consistency.md](06-consistency.md) §3).
11. **Authorise and hook.** The merchant's payment provider authorises through the network to the issuing bank. Where the bank points its processor at us, the hook responder matches the authorisation to the pre-approval (token, transaction amount at or below in the same currency, same merchant, inside the window, not yet consumed), consumes it under a unique constraint, answers within budget and logs the processor's id ([06-consistency.md](06-consistency.md) §4). In the PoC, the processor hook simulator does this in shadow mode. A connector order reaches the hook only when it is paid with an enrolled agent card; on any other card the hook has no opinion, and the mode is labelled "one line of defence".
12. **Reconcile.** Decision, authorisation (from the network confirmation or the hook log) and clearing (the bank's feed; synthetic files in the PoC) are matched. A mismatch opens a case with drafted evidence. Money that settled without an approval (network stand-in, over-capture, force post) is kept in its own record and flagged; it never counts toward or against the user's limits silently. For a connector order the merchant's order record and invoice lines (read through the account tier, kept as merchant-reported) are matched against the approved lines and the ceiling; a billed amount above the ceiling or a line that was not approved opens a case.

## Standing mandates: the same flow without the user
A price watch (V9) or "look every morning" mandate runs the twelve steps above with three differences. **Who starts it:** the confirmed mandate carries a run frequency and a purchase count; `agents` keeps the due runs; the harness runtime claims one, gets a short-lived agent run token for that mandate and runs the watch module ([02-system.md](02-system.md), identity). **How it shops:** the price check in the harness is advisory and needs no model; only a candidate below the threshold is proposed, with a `purchaseKey` derived from the mandate, the run and the offer, so a retried run repeats the same proposal while a later run gets a fresh decision on today's price. **What the user sees:** nobody is in chat, so the mandate's "when unsure" policy defaults to "decline and tell me", the confirm screen says plainly that the watch either buys on its own or does not buy (a step-up cannot wait for a fare that lives minutes), and `notifications` reports completed, unknown, failed and unsettled-requirement outcomes over the user's channel. Reaching the purchase count makes the mandate fulfilled: no more runs, the instruction cancelled where allowed. A failed or cancelled attempt releases its reserved count and the watch goes on; an unknown one holds the count until resolved, so a run in the meantime is declined on the count.

Where the fare is in a foreign currency, the limit is compared at the decision's FX rate plus the margin from `settings`, and `reconciliation` flags a billed amount above the limit in the base currency; the confirm screen shows the limit as "about … at today's rate".

## Cart evidence tiers
| Tier | Source | What it can establish |
|---|---|---|
| 1 | The merchant's priced cart returned through a protocol checkout session, or the priced quote an admitted connector returned, both fetched by the backend ([ADR-0008](../adr/ADR-0008-merchant-connectors-and-the-connector-catalogue.md)) | binding facts: merchant, item ids, quantities, unit prices, total (or the ceiling derived from it), currency, delivery slot; structured attributes the merchant sends |
| 2 | Product records the backend fetched from the merchant's own catalogue or feed | descriptive facts; structured fields such as GTIN, size or category, by fixed rules |
| 3 | What the agent says (its description, reasons, the pages it read) | nothing positive; a contradiction with tiers 1 and 2 raises the outcome to at least STEP_UP |

**Auto-purchase (APPROVE without asking) needs tier 1, and every requirement in the mandate settled by fixed rules over tier 1 or tier 2 structured data.** A tier-1 cart that leaves a requirement open is at most STEP_UP, and the user decides on that cart's binding total. **No tier-1 cart or quote means DECLINE "can't buy here"**: nothing binding exists to approve or to pay. Through a connector, auto-purchase also needs an order that the merchant binds to the quote (a quote id with an idempotent order, or a two-phase order); a connector whose manifest offers neither gives at most STEP_UP. A broken hard limit is DECLINE whatever the evidence. The intent model can find a problem but never clear one, because invariant 2 allows a model to make a decision more cautious, never less. So mandates that name exact products, categories or price ranges can run on their own, and free-text quality requirements ("leather, size 42" when the merchant sends only a title) go to the user.

The **merchant identity** the decision approves (the registry's merchant id and name) must be mapped to what the hook and the clearing see (acquirer merchant id, descriptor, category code). That mapping is part of the merchant directory and is measured in shadow mode before enforcing; until a bank's data exists it is an open item ([05-open-items.md](05-open-items.md)).

Where this works today: at merchants that run a protocol checkout session and return the cart, a small set (US-first; a handful named in Europe; none known in Czechia, and no airline or travel agency anywhere), and at merchants with an admitted connector, which the operator adds one reviewed manifest at a time (a Czech online grocer with its own MCP server is the first candidate, T-038). In the PoC these are our demo shop and the demo connector. The merchant directory records which structured attributes each merchant settles, so the confirm screen can warn when no reachable merchant can settle a requirement and the mandate could never buy on its own. Whether Visa's gateway relays populated line items and totals is known from the published SDK models only, not from a live call; T-034 checks it.

## Failure behaviour
| Situation | Behaviour |
|---|---|
| The merchant offers no agent checkout session, can't open one, or returns an error | DECLINE "can't buy here" (reason: no session). A session that opened but left requirements unsettled is a STEP_UP with that cart |
| A connector merchant whose connector is suspended (tool list drifted, approval expired), not enabled by the bank or turned off by the user, or whose account is not linked | DECLINE with that reason; the user is told where to fix it (the app), never asked in chat; the agent may still research and link |
| The quote or the slot hold expires before the step-up is answered | the expiry per decision was bounded by it; an answer after it is DECLINE "propose again" |
| The merchant's final amount is above the ceiling, or an invoice line was not approved | `reconciliation` flags it and opens a case; the ledger counted the ceiling; the difference and refunds are an open item |
| The merchant requires the cardholder's authentication on a card-on-file order | `PENDING_USER`, bounded by the quote's expiry; the user finishes it in the merchant's or the bank's flow |
| A connector order times out | `UNKNOWN`; the resolver looks up our order reference at the merchant; found means `COMPLETED`, not found by the window's end means `FAILED`; the order is never placed again blindly |
| The harness is asked to connect another MCP server | impossible by construction: the two server addresses are deployment configuration; nothing in a conversation, a tool result or the user's settings can add one |
| The intent model times out, errors or exceeds its spend cap | no answer → the requirement stays unsettled → uncertain → the mandate's "when unsure" (ask or decline), never approve |
| The network answers "pending cardholder authentication" | two independent gates: our decision stands and the reservation counts; the user finishes the network step in the app; any outcome other than success releases the reservation |
| The credential was released but checkout fails | the attempt goes to `FAILED`: release the reservation, cancel the pre-approval, cancel the network instruction where allowed; the credential expires unused; a retry with the same `purchaseKey` gets the stored decision, and a new credential needs a new decision |
| The completion call times out | the attempt is `UNKNOWN`, never `FAILED`: reservation and pre-approval stay; `CheckoutOutcomeUnknown` tells the user and the activity page; a resolver reads the session status; a matching authorisation makes it `COMPLETED`, the window ending without one makes it `FAILED` |
| The network wants the cardholder to authenticate while nobody is present (standing mandate) | `PENDING_USER` is bounded by the stored session expiry as well as the pre-approval window; when either passes the attempt is `FAILED`, the watch goes on, and the user is told |
| An item spec matches no offer, or several | none: DECLINE "nothing matches"; several: the core's pick rule chooses, every candidate is in the `DecisionInput` |
| The agent puts a name, address or document in a proposal | a line has a closed schema; unknown fields are rejected as a named error before any merchant call; recorded. Personal fields a merchant echoes back are dropped before storage |
| Too many proposals or runs for one mandate or agent | the caps in `settings` return a named error; recorded; the watch's next run is still claimable when its turn comes |
| The process dies between requesting the credential and completing | on restart the attempt is resolved from the session status; a second credential is never requested for the same decision |
| Two proposals race for the last of a budget | budget-period row locks: exactly one reserves; the other is decided on the updated ledger |
| The merchant changes the price or adds items at completion | the amount or items no longer match the decision; the attempt goes to `FAILED` with the reason "cart changed" and the new cart is a new proposal |
| The same request arrives twice (proposal, event, hook call) | deduplicated by `purchaseKey`, event id or the processor's authorisation id |
| The harness or the LLM is down | nothing is proposed; the backend, the hook responder and the cardholder app keep working |
| Hostile text in a product page or the agent's reasons | stored as data; the suspicious-text flag raises the outcome to at least STEP_UP |
