# 06 Consistency, concurrency and replay

The mechanics that keep money right when things run at the same time, fail half-way or arrive twice. Decided in [ADR-0006](../adr/ADR-0006-architecture-style-and-module-cut.md); the checkout attempt, the payment token and the provider's webhooks since 2026-11-19 in [ADR-0010](../adr/ADR-0010-standalone-app-and-provider-payment-tokens.md). Every mechanism here has a required test (see the end).

## 1. Budget reservations under concurrency (invariant 5)
Two proposals, or a proposal and a step-up approval, can arrive at the same moment against the same budget. Both would read "enough left" and both would reserve.

- The ledger keeps one **budget-period row** per (mandate budget, period) and one per (global budget, period). It holds the reserved and counted totals in one currency, stamped on the row when the period opens: a mandate budget's rows count in the mandate's confirmed currency, a global budget's rows in the user's base currency current when the period opens; each purchase is converted into the row's currency at the decision's rate, so changing the base currency never changes a confirmed mandate or an open period.
- Locking is done by `ledger`'s published API, which `decisioning` calls in the decision's transaction right after the proposal row is inserted under its unique key (§5; T-037); `decisioning` never touches ledger tables. **Every first decision and every step-up approval** locks every budget-period row it touches (a first decision does not yet know whether it will reserve) with `SELECT … FOR UPDATE`, in a fixed order (global first, then by mandate id) so two transactions can't deadlock. Then it share-locks the mandate version it decides under (`SELECT … FOR SHARE`, so a revocation either is seen or waits for the commit; T-037), reads the remaining amount, decides and writes, all under those locks.
- Isolation level `READ COMMITTED` plus these explicit row locks. No `SERIALIZABLE` retries.
- Rows for a period that doesn't exist yet are created with `INSERT … ON CONFLICT DO NOTHING` before they are locked.
- The duplicate, split-order and velocity checks read the ledger under the same locks, so they see every committed reservation.
- **What counts:** remaining = budget − reserved − counted. A reservation is made at APPROVE for the approved amount in the currency of the budget-period row at the decision's FX rate (the foreign-currency margin applies to the cart side of the comparison only, never to the reserved amount) (for a connector quote with a variable final amount, the **ceiling**; the difference to the billed amount returning budget is an open item); it turns into *counted* when the checkout attempt reaches `COMPLETED`, at the same amount (the amount the shop charged is reconciliation's business, not the ledger's, and a refund does not restore budget automatically in v1); it is released on `FAILED` or `CANCELLED`, which a token attempt enters only once its token is dead (§3, §4). The exact counting rule with its edges is written in T-003 from this.
- **The purchase count** of a mandate (one for a one-shot watch) is kept the same way, in `ledger` only: one **purchase-count row** per mandate with reserved and counted purchases, locked with `SELECT … FOR UPDATE` after the budget-period rows, by mandate id, so two runs racing for the last purchase get exactly one APPROVE. It is reserved at APPROVE, counted at `COMPLETED`, released on `FAILED` or `CANCELLED`, held while `UNKNOWN` or `PENDING_USER`. Each counted purchase records the mandate version it was approved under, so the first-run rule for a merchant-derived list can ask "any completed purchase under this version?". A per-purchase ceiling alone would let two offers at two merchants both pass; the count is what makes "buy one ticket" mean one. `mandates` reads it through `ledger`'s API to raise `MandateFulfilled`.

## 2. Every step-up outcome is a second decision
A STEP_UP ends in exactly one of: the user approves, the user declines, the question expires (the scheduled job in `decisioning`; the expiry is set per decision as `min(the ceiling in settings, the stored session expiry − a margin)` and stored in the `DecisionInput`), the mandate is revoked or fulfilled, the agent is stopped. **Each of these is a new decision record** in `decisioning`, linked to the first, with its own `DecisionInput`, its reason code, its audit row and its `DecisionMade` outbox row, committed in one transaction. A user's decline, an expiry, a revocation, a fulfilment or a stop produce DECLINE with the corresponding reason and lock nothing. An approval runs the re-check:
1. lock the budget-period rows (section 1);
2. re-read the mandate version, the ledger, the route (the payment method still saved and not blocked) and the checkout session's **stored** expiry (no merchant call inside the transaction);
3. decide APPROVE or DECLINE with reasons;
4. on APPROVE, write the reservation, the token terms (computed at this decision's time, so the expiry is the earlier of the stored checkout session expiry and this decision's time plus the attempt window), the audit record and the outbox row.

If the stored session has expired, the answer is DECLINE with the reason "the merchant's cart expired; propose again". The agent's next proposal opens a new session, outside any transaction.

## 3. Checkout attempts
After an APPROVE, `payments` runs the checkout as a persisted state machine, one **checkout attempt** per approved decision (unique on the decision id).

```
CREATED ──▶ TOKEN_ISSUED ──▶ COMPLETING ──────────────────────────▶ COMPLETED
   │             │               │   │                                  ▲
   │             │               │   └──▶ PENDING_USER ──(3-D Secure done, token used)──┤
   │             │               │        (requires_action)  └──▶ FAILED*  (challenge failed or lapsed)
   │             ├──▶ FAILED*    ├──▶ FAILED*                                           │
   │             └──▶ UNKNOWN    └──▶ UNKNOWN ──(resolved: token used)──────────────────┘
   │                                     └──(resolved: token dead, unused)──▶ FAILED*
   ├──▶ FAILED     (payment method removed or blocked before a token exists)
   └──▶ CANCELLED  (mandate revoked or agent stopped before a token exists)

 TOKEN_ISSUED ──(requires_action)──▶ PENDING_USER
 TOKEN_ISSUED ──(token used)──▶ COMPLETED

 TOKEN_ISSUED | COMPLETING | PENDING_USER | UNKNOWN ──(revocation, stop, or payment method removed or blocked)──▶ revoke the token:
     confirmed revoked and unused ──▶ CANCELLED* (FAILED* for a removed method)        already used ──▶ COMPLETED

 * entered only once the token is revoked, deactivated or expired (§4); the release is in that transaction
```

- Each transition is committed **before** the remote call it announces, in a transaction of its own; a listener that makes remote calls is therefore a plain transactional event listener with explicit transactions per step, never Spring Modulith's `@ApplicationModuleListener`, which would wrap the whole listener in one (T-037). A transition is a plain conditional update (`UPDATE … WHERE state = expected`): under `READ COMMITTED` PostgreSQL re-checks the condition after the row lock, so exactly one of two racing transitions wins; no separate `SELECT … FOR UPDATE` on the attempt is needed. Leaving `CREATED` re-reads the mandate under a share lock and cancels instead when it was revoked since the decision (T-037); it also re-validates the route, and a payment method removed or blocked since the decision makes the attempt `FAILED` with "payment method removed" before any token exists.
- **At most one token per decision.** The move to `TOKEN_ISSUED` is committed before the issue call it announces, with the provider's idempotency key derived from the attempt id; the token's id is stored on the row when the provider answers. A repeated issue call with that key returns the same token, so a crash or a redelivered event can never produce a second one. Each of the two call-announcing transitions (`TOKEN_ISSUED`, `COMPLETING`) stores on the attempt row the deadline of the call it announces plus the bound of the follow-up commit ([ADR-0009](../adr/ADR-0009-tech-stack-revision.md) B6); before that deadline a redelivery does nothing, because the first call may still be running. After it only the resolver job acts: it reads the shop's checkout session status and the token's state at the provider. A token reported used means `COMPLETED`. A token dead and unused with no completed session means `FAILED`. Anything else means `UNKNOWN`, the timeout rule below, never a `FAILED` on missing evidence.
- **A timeout is `UNKNOWN`, never `FAILED`.** While an attempt is `UNKNOWN`, the reservation stays in force. Entering `UNKNOWN` publishes `CheckoutOutcomeUnknown`, so `activity` shows the honest state and `notifications` can tell the user. The resolver job reads the session status and the token's state. A used token makes the attempt `COMPLETED`; a token that has expired or been deactivated unused makes it `FAILED`. The token's short expiry therefore bounds `UNKNOWN`. A shop that reports the order completed while the token was never used opens a mismatch case (an order with no charge through our token); the attempt still fails on the token's evidence.
- **`PENDING_USER`:** the provider reported `requires_action` (the user's bank asks for 3-D Secure when the shop charges the token). The reservation stays; the `CheckoutPendingUser` event lets `notifications` tell the user, who completes the challenge in our web app through the provider's own SDK. The attempt becomes `COMPLETED` when the provider reports the token used; it becomes `FAILED` when the challenge fails, or the token's expiry or the **stored checkout session expiry** passes, once the token is dead. For a standing mandate with the user away this is the lapse: release, the watch goes on, the user is told.
- **`COMPLETED`:** entered when the provider reports the token used (by webhook or by the resolver's read); the shop's own confirmation is recorded as merchant-reported and does not complete an attempt on its own. In the same transaction as the state change and the `CheckoutCompleted` outbox row, `payments` calls `ledger.count(decisionId)` and records the shop for this cardholder, keyed by its domain together with the seller's provider identity from its discovery document (the history the first-purchase rule reads; a change of either is a new shop). After the commit it deactivates the token (the first confirmed use is its only use), retried by the resolver until the provider confirms; `PaymentTokenEnded` records it.
- **`CANCELLED`:** a mandate revocation, a fulfilment or an agent stop reaches an attempt. In `CREATED`, no token exists: the attempt is `CANCELLED` at once. Past `CREATED`, `payments` revokes the token; the attempt becomes `CANCELLED` once the provider confirms the token revoked and unused, or `COMPLETED` if it was already used (the provider is the arbiter of that race, §4). This replaces ADR-0006's "attempts past the credential run to their end" ([ADR-0010](../adr/ADR-0010-standalone-app-and-provider-payment-tokens.md)).
- **Release only when the token is dead.** A failure seen while the token can still be charged (the completion refused, the cart changed, the payment method gone) first revokes the token: the attempt row records the outcome it is heading for (`FAILED` with its reason, or `CANCELLED`) and the resolver retries the revocation until the provider confirms it or the token expires. Only then does `payments`' application service call `ledger.release(decisionId)` **in its own transaction**, together with the attempt's state change and the `CheckoutFailed` (with its reason) or `CheckoutCancelled` outbox row, so the facts change atomically. Budget never frees while money can still move. Events are for read models and reconciliation, never for keeping these facts consistent.
- Idempotency keys toward the shop and the provider come from the `purchaseKey` and the attempt id, so a retried call is the same call.
- **Connector orders** ([ADR-0008](../adr/ADR-0008-merchant-connectors-and-the-connector-catalogue.md)) have no token, unless the connector merchant accepts provider tokens (ADR-0008 as amended; see [05-open-items.md](05-open-items.md)); then the token path of §3 applies. Otherwise the attempt goes `CREATED → COMPLETING → COMPLETED | FAILED | UNKNOWN | PENDING_USER`, and the release on `FAILED` or `CANCELLED` needs no revocation. `COMPLETING` is committed before the order call, which carries the quote id and our idempotency key as the order reference. `UNKNOWN` and `PENDING_USER` are resolved only by looking that reference up at the merchant through the `MerchantAccount` port (the resolver job, with the link's token); the order call is never repeated blindly. `PENDING_USER` here means the merchant requires the cardholder's authentication on a card-on-file order, bounded by the stored quote or slot-hold expiry. The resolution window runs to the slot's end plus the manifest's authorisation lag. An ended link keeps a resolution-only use of its token until every attempt and reconciliation read for it is final, at the latest until the last order's slot end plus the reconciliation window from `settings`; a connector order re-reads the card on file when it enters `COMPLETING` and goes `FAILED` with "card on file changed" if it no longer matches the decision's route; when a lookup is nevertheless impossible, the attempt stays `UNKNOWN` and a mismatch case is opened, never a silent `FAILED` that would release approved money while the merchant delivers and charges. A card-on-file order has one line of defence (the decision), labelled; reconciliation works from the merchant's order record. A connector turned off for an instance or an agent stopped cancels that instance's attempts still in `CREATED` at that merchant like a revocation does; a link ended or a connector disabled or suspended cancels every attempt in `CREATED` there.

## 4. The payment token: issue, revocation and use
The token replaces the pre-approval and the bank's hook ([ADR-0010](../adr/ADR-0010-standalone-app-and-provider-payment-tokens.md)). What the hook once matched, the provider now enforces on limits we set.
- **Terms.** The token terms are a pure function of the decision, stored in its `DecisionInput`: the seller's provider identity from the merchant directory, the maximum amount equal to the approved cart total in the cart's currency (exact; converted to the provider's minor units in the adapter), that currency, and the expiry at the earlier of the stored checkout session expiry and the decision time plus the attempt window from `settings`. `payments` issues exactly these terms on the routed saved payment method and never widens them; a replay recomputes them identically.
- **One token per decision.** The attempt is unique on the decision id, and the provider's idempotency key derives from the attempt id (§3). No code path issues a token outside an attempt in `TOKEN_ISSUED`.
- **Use.** The provider's `used` event (or the resolver's state read) for the attempt's token moves an attempt in `TOKEN_ISSUED`, `COMPLETING`, `PENDING_USER` or `UNKNOWN` to `COMPLETED` and publishes `PaymentTokenUsed` for reconciliation. `requires_action` moves `COMPLETING` (or `TOKEN_ISSUED`) to `PENDING_USER`. The token is deactivated after its first confirmed use.
- **Revocation race.** A revocation (mandate revoked, agent stopped, failure seen) and the shop's charge can reach the provider at the same moment. The provider decides which came first, and we never assume the revocation won: the attempt stays where it is until the provider confirms the token revoked and unused (`CANCELLED` or `FAILED`) or reports it used (`COMPLETED`). A `used` event that arrives after our revocation request means the charge won.
- **Dead token.** A token is dead when the provider reports it revoked, deactivated or expired. Our clock passing the expiry triggers a state read, not a release, and an event alone never releases: before a release `payments` reads the token's state from the provider, so a `deactivated` that overtakes a `used` in delivery cannot free budget for a charge that happened. Only a dead token releases a reservation.
- **Unexpected usage.** A use the attempt does not expect (a second use, a use after `CANCELLED` or `FAILED`, an amount above the terms where the event carries it, a use of a token we hold no attempt for) publishes `UnexpectedTokenUsage`; it never changes the ledger silently. Reconciliation opens a case and `notifications` tells the user.
- **What the provider does not tell us** stays a blind spot, stated in the app: the amount billed in the card's currency, refunds, chargebacks, charges outside our token. Whether the maximum caps one charge or the cumulative total, and which events carry the charged amount, are verified in T-005 ([05-open-items.md](05-open-items.md)).

## 5. Idempotency of proposals (invariant 7)
- The key is (**agent instance**, `purchaseKey`), so two agents can never collide. It is a **unique constraint** on the proposal table.
- **Concurrent delivery:** two deliveries of the same key may both pass the "seen?" check and both open a merchant session. The proposal row is the first write of the decision's transaction, before the budget lock, so the second delivery blocks on the unique key until the first commits and then fails without ever deciding or waiting for the budget (T-037). The handler then re-reads the stored proposal: equal binding fields return the stored decision (the duplicate session is left to expire), different binding fields are the conflict below. There is never a second decision for one key.
- "Same request" means the **binding fields** are equal: shop (domain or connector merchant), lines (item ids or item specs), quantities, mandate id. The slot and the shipping option are not binding fields: the backend picks them. The agent's free-text description and reasons are not compared, so a reworded retry returns the stored decision instead of a conflict. The profile version is not compared either: the decision records the version current when it was made, and a redelivery after a profile edit still returns that decision.
- A watch run derives its `purchaseKey` from the mandate id, the run id (in the run token) and the merchant's offer id: a retried run repeats the same proposal and gets the stored decision; the next run gets a new key and a fresh decision on that day's price; the purchase count (section 1) keeps two offers from both buying.
- Different binding fields with the same key is a conflict (a named error), and nothing is decided.

## 6. The replay unit (invariant 8)
Each decision stores its complete **`DecisionInput`** in the audit record. Replaying means `decide(storedInput)` in `control-core`, with no adapter, model or network call. It must return the stored decision, and for an APPROVE the same token terms. The stored input holds:
- the mandate version (its full content, not only its id) and the agent instance's status;
- the proposal's binding fields and the agent's untrusted text; the **profile version id** current at the decision (never the personal data), and what was disclosed to the shop before the decision (country and postcode, or the full address where the shop required it);
- for an item spec: every candidate offer the merchant returned and the pick rule's choice;
- the merchant directory answer (the discovery document's checkout endpoints, protocol, the seller's provider identity, its fetch time, or the connector manifest) and whether this cardholder has bought at this shop through us before;
- the **route**: the selected saved payment method (the provider's reference), the mandate's allowed methods and the user's preference order that the selection was made from, and whether it was still saved and not blocked;
- the cart evidence as received: the tier-1 session cart (with the merchant-signed checkout and its verification result where present) or connector quote, the shipping options and the pick, tier-2 product records, and the session's, quote's or slot hold's expiry; for a connector: the manifest version, the slot candidates and the pick, the ceiling's components (quote total, each weighed line's price and allowance, fees, deposits, and whether the quote included them), the connector's state and the toggle, whether the account was linked and named by the mandate, the payment method on file, the one-line-mode setting in force, whether the item list was merchant-derived and the completed purchases under this mandate version;
- the intent model's questions, answers, scores, model id and version, or "no answer" with the reason;
- the risk signals and their sources;
- the ledger snapshot used: budget-period totals, the mandate's reserved and counted purchase count, and the earlier purchases the duplicate, split and velocity checks looked at;
- the cardholder's base currency, the FX rates used, with their source and timestamp, or the source's named answer (no rate for the currency, unavailable, stale), the foreign-currency margin applied and the mandate's comparison operator;
- the clock reading;
- the `DecisionInput`'s schema version and the rule set's version ([ADR-0009](../adr/ADR-0009-tech-stack-revision.md) B7);
- the settings in force (thresholds, "when unsure" default, the step-up expiry ceiling and margin, the attempt window) and the step-up expiry computed for this decision;
- for an APPROVE, the **token terms** (seller, maximum amount, currency, expiry).

A step-up re-check stores its own `DecisionInput` (section 2). A replay test runs over every stored decision in CI against the labelled cases.

## 7. Event delivery
Spring Modulith's event publication registry delivers each event **at least once, in no guaranteed order**, to in-process listeners. Every listener:
- is idempotent (keyed on the event id, or on the `purchaseKey` and attempt id);
- tolerates reordering. For example, `activity` may see `CheckoutFailed` before `DecisionMade` and must still end in the right state, so it applies state by the aggregate's version, not by arrival order.

The registry records a publication per (event, listener): an event nobody listens to leaves no row, so every event in the catalogue names at least one consumer (T-037). The monitor may mark a listener failed while it is still running, and resubmission then redelivers to it; that is harmless only because every listener is idempotent and the attempt's transitions are fenced (§3), never because the registry prevents it (T-037).

When a broker is added later, the relay publishes from the same registry, and these rules don't change.

## 8. Provider webhooks and saved payment methods
- **Ingress.** The provider's webhooks arrive on one public path of `control-backend`. The signature over the raw body is verified with the webhook signing secret, within the provider's timestamp tolerance, before anything else is parsed; a failure is refused, counted and never processed.
- **Record, then process.** A verified event is inserted into an insert-only record under a unique constraint on the provider's event id; a duplicate delivery hits the constraint and is acknowledged without further work. Processing runs from the record in its own transaction, idempotently, and through the attempt's conditional transitions (§3), so a reordered or redelivered event changes nothing it should not. The provider delivers at least once and in any order; an event is a trigger, and a release rests on a state read (§4).
- **Shop order webhooks** (UCP, ACP) take the same path shape: verified where the protocol defines a signature, deduplicated, recorded insert-only as **merchant-reported, untrusted** data, published as `ShopOrderReported`. They feed reconciliation and the activity page; they never complete an attempt, release budget or reach a rule.
- **Saving a payment method.** The cardholder app asks `payments` to start a setup (with a client-generated id, idempotent per owner, [ADR-0009](../adr/ADR-0009-tech-stack-revision.md)); the user enters the card or wallet in the provider's own form; the provider confirms, by return and by webhook, and `payments` stores only the provider's reference with its display data and publishes `PaymentMethodSaved`. A setup that needs 3-D Secure is completed in the same form. Removing or blocking a method takes effect at once for new decisions and at the next route re-validation (§2, §3). Like a stop, it also revokes every unused token drawn on that method: each such attempt heads for `FAILED` with "payment method removed", and its release follows once the token is dead (§3, §4); a token already used stays `COMPLETED`.

## 9. Runs of standing mandates
- `agents` materialises each due run as a row (mandate id, due time) from the confirmed frequency, on the `Clock` port; for a standing mandate whose item list was derived from a merchant account, the first run is due at confirmation, so the STEP_UP it produces reaches the user while they are in the app. A claim is `UPDATE … SET claimed_at, run_id WHERE claimed_at IS NULL`; zero rows updated means already claimed, which is answered as "nothing due" and recorded as a duplicate claim. A claimed run that proposes nothing within its window simply ends; the next due run is independent.
- The run token is minted inside the claim's transaction and is not stored; its verification is by signature and expiry. The run id is in its claims, so a proposal can be tied to the run that made it.
- `MandateFulfilled`, `MandateRevoked` and `AgentStopped` delete or mark the mandate's unclaimed runs in their listener; a claim that races one of them still yields a token, and the proposal it makes is declined on the mandate's or agent's status, which is in the `DecisionInput`.
- Runs and proposals per mandate and per day are counted in `agents` and `decisioning` against `settings`; exceeding a cap is a named error, recorded, and never silent.

## Required tests
- Two concurrent proposals that each fit the budget, but not together: exactly one APPROVE, the other DECLINE or STEP_UP. The same for a proposal racing a step-up approval, and for two mandates racing on the global budget.
- Two runs of a one-shot watch proposing two different offers at once: exactly one APPROVE; the mandate is fulfilled once the attempt completes; a failed attempt releases its reserved count and the next run may buy.
- Two claims of the same due run: one token, the second answered "nothing due" and recorded.
- A proposal carrying personal data in a line: rejected before any merchant call. Before the decision the shop receives only country and postcode where its protocol allows; a shop that requires the full address gets it and the disclosure is in the `DecisionInput`.
- An item spec matching zero, one and several offers; the pick rule's result replays from the stored candidates. The shipping option pick: the cheapest option that satisfies the mandate, replayed from the stored options.
- The step-up expiry per decision: a session shorter than the ceiling in settings shortens the expiry; an approval after it is DECLINE "propose again".
- A cart in a foreign currency at the limit, one cent over, and inside the margin, under `<` and under `≤`: the margin can only turn APPROVE into DECLINE, never the reverse; a negative margin rate is refused by `settings` validation; a cart in the limit's currency has margin zero even when that is not the base currency, and a cart in the base currency under a mandate confirmed in another currency gets the margin. A change of base currency applies from the next budget period, never to the open one, and never changes a confirmed mandate's amounts or their currency; a budget confirmed in EUR keeps counting a CZK purchase converted into EUR at the decision's rate.
- Discovery: the endpoints and the seller's identity come only from the document at the named domain's HTTPS origin; a redirect off the origin, a private address, an oversize or malformed document, an endpoint offered in a session response or by the agent are each refused, and the proposal is DECLINE "can't buy here".
- The first purchase by a user at a shop new to them is at least STEP_UP and is mapped through the mandate's "when unsure" policy like an open requirement: on a standing mandate set to "decline and tell me" it is DECLINE and the user is told; after a completed purchase there, the next is not raised by that rule.
- A merchant-signed checkout that fails verification is not tier-1 evidence: DECLINE "can't buy here".
- Removing the cardholder's last channel suspends the due runs of their standing mandates; adding one resumes them.
- The `ceiling` function: at the limit, one cent over, a quote total under the limit while the ceiling is over (the ceiling decides), a weighed line in a foreign currency, fees inside and outside the quote; half-even at each step; the components replay from the stored input.
- A proposal at a connector merchant that is suspended, not enabled, turned off for this instance, not linked, or linked but not named by the mandate: DECLINE with the matching reason and no merchant call that uses the user's token. A minimum order at and one cent under. No slot inside the window.
- A connector order paid with the card on file: DECLINE with the one-line mode disallowed, APPROVE possible with it allowed, and the mode recorded in the input. The card changed between the decision and `COMPLETING`: `FAILED` "card on file changed", reservation released, no order call.
- An ended link's resolution-only use ends at the latest at slot end plus the reconciliation window, even with a case open; the token is then gone and the case runs on the stored record.
- A merchant's tool hash that differs from the manifest, at session start and on `tools/list_changed`: the connector is suspended, toggles and links are untouched, the next proposal is DECLINE, and re-approval restores service with no user action.
- A discovery argument over its cap is refused at the gateway; injected text in a discovery result, a stored tool description or a merchant review is data and raises nothing but the suspicious-text flag on the proposal that cites it.
- A connector order that times out and is later found by its order reference: `COMPLETED`, counted once; the same timeout with nothing found by the window's end: `FAILED`, released; a lookup that is impossible: `UNKNOWN` plus a mismatch case. The order call was made exactly once, also under a duplicate `DecisionMade` delivery.
- A link ended while an attempt is `COMPLETING` or `UNKNOWN`: the resolution-only use resolves it; the token is never used for a quote or an order after the end, and never for another cardholder.
- Turning a connector off for one instance leaves the link and a second instance's use of it intact; the operator disabling the connector ends every link to it and cancels attempts in `CREATED`.
- A pending step-up at a connector merchant counts nothing until approved.
- The first run of a merchant-derived list is STEP_UP by its own reason code even under "decline and tell me"; the second run, after a completed purchase, is not.
- An OAuth callback with a wrong `state` or a wrong issuer is refused and recorded.
- The harness configured with a third server address fails to start; a tool result or conversation naming a server changes nothing; an egress attempt outside the policy is refused and logged.
- **One token per decision under redelivery:** a crash at each checkout-attempt transition and a redelivered `DecisionMade` while the attempt is mid-call: the provider sees one token (the same idempotency key on every issue call), and the final state is correct. Before the stored deadline a redelivery changes nothing; after it the resolver, not the listener, settles the attempt, and a shop that has not answered yields `UNKNOWN`, not `FAILED`. The boundary race: the listener commits its outcome just after the deadline while the resolver runs; exactly one transition wins.
- **The token terms:** maximum amount equal to the approved total in the cart's currency, exact in minor units, the seller from the directory, the expiry the earlier of the stored checkout session expiry and the decision time plus the attempt window; recomputed identically on replay; never widened by `payments`.
- **Release only when the token is dead:** a checkout failure after the token was issued releases nothing until the provider confirms the token revoked, deactivated or expired; a `deactivated` event delivered before a `used` event releases nothing (the state read says used) and the attempt is `COMPLETED`.
- **The revocation race:** a mandate revocation or an agent stop while the shop charges: if the provider reports the token used, the attempt is `COMPLETED` and counted; if it confirms the token revoked unused, `CANCELLED` and released; never both, never released while the token can still be charged.
- **3-D Secure:** `requires_action` puts the attempt in `PENDING_USER` and notifies the user; a completed challenge followed by `used` is `COMPLETED`; an unanswered challenge past the token's or the session's expiry is `FAILED` once the token is dead, released, and the user told (also for a standing mandate with the user away).
- **Duplicate and reordered webhooks:** the same provider event id delivered twice is recorded and processed once; a wrongly signed request is refused and recorded nowhere but the counter; events in any order end in the same attempt state.
- **Unexpected usage:** a second use, a use after `CANCELLED` or `FAILED`, and a use of an unknown token each publish `UnexpectedTokenUsage` and open a case; the ledger is unchanged.
- **No charge rights:** the build test that the `PaymentProvider` adapter makes no charge, refund or payout call.
- The credential the harness holds for a chat session is refused by every cardholder and console endpoint (ADR-0009 B1).
- A completion timeout followed by a used token: `COMPLETED`, and the reservation counted once. A completion timeout with the token expiring unused: `FAILED`, reservation released.
- The same `purchaseKey` delivered twice concurrently: one decision, the same answer twice, one proposal row.
- Each step-up outcome (approve, user decline, expiry, revoke, stop) writes a second decision with its audit row and event.
- A replay of every stored decision returns the same outcome, reasons and token terms.
- Each listener under duplicate and reordered delivery.
