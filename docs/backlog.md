### Definition of ready (for every implementation item T-007 creates)
An item may start only when a developer can build it without asking anyone:
- it names its module and deployable (per ADR-0006) and the feature ids it serves;
- the aggregates, value types and state transitions it touches are specified in `docs/domain/` (T-003);
- every port, REST endpoint, MCP tool, event and table it adds or uses has a written contract: shape, failure modes, idempotency, versioning (T-003, T-005);
- the rules it implements are in the rule catalogue with their edges (at the limit, one cent over, foreign currency, duplicate delivery, injected text, pending step-up);
- its tests are listed: unit per rule, property tests where money or the combiner is touched, the concurrency, crash and replay tests of [06-consistency](architecture/06-consistency.md) it touches, the contract suite of each port it implements, Testcontainers for each DB adapter;
- it fits in one PR, and its acceptance is a replay of labelled cases or an observable check;
- every open question it depends on is closed or has a labelled stand-in.

### T-003 Domain model and contracts (supersedes ADR-0002)
Brief step 3, inside the module cut of ADR-0006. The developer handoff package, written to `docs/domain/` and `docs/architecture/`, so that every item meets the definition of ready:
- **Domain model:** aggregates per module, their fields, identities and state machines (mandate versions with the fulfilled state, proposal, decision, step-up, reservation, pre-approval, checkout attempt with the connector variant, due run, profile version, connector manifest with its states, connector toggle, account link, settlement, refund, mismatch case), the invariants each guards; an owner (cardholder) id on every aggregate and audit record.
- **Mandate schema:** exactly what a mandate can express (budget and period with time zone, merchant lists, item requirements as structured facts, item spec categories with their validated values and time zones, quantity, purchase count, timing and run frequency, expiry, the strict-or-inclusive limit, the profile entries it may use, the linked account it may order through, the substitution policy and slot window, the "when unsure" policy with the standing-mandate default) and how a tightening is told apart from a loosening (adding a traveller or a linked account is a loosening).
- **Mandate drafting (decided with the user, 2026-10-31):** the agent drafts, the backend checks, the user confirms. A draft carries two states. **Enforceable** is the backend's fixed checklist per mandate kind over the generic schema above, settled by T-003; for example: amount and currency, period or expiry, scope as merchants, categories or an item spec, requirements as structured facts where the scope needs them; for a standing mandate also its run frequency, purchase count and either an item list or an item spec (a flight price watch has a spec and no list), and a reachable notification channel at confirmation. A draft with missing items is stored and `draft_mandate` returns them by name so the agent asks the user about exactly those ("what I usually buy" without items or categories is a missing scope item); the backend refuses to confirm a draft with missing items, as a named error. **Ready** is the agent's own assertion, sent with the draft, that it understands the request well enough to search accurately; the harness prompt instructs the agent to maintain it, `mandates` stores and audits it with the draft, and nothing in the backend branches on it. It gates only the agent's own choice between going back to the user and going on to a targeted search. Neither state is a permission: the confirm screen renders the enforceable draft and the decision never reads `ready`. No category templates beyond the item specs that exist where merchant data is structured. The shopping tools do not depend on a mandate, so the agent may search before a draft is ready to learn the market; only `propose_purchase` needs an active mandate. **Readjustment:** `decisioning` adds an advisory reason code to the `n`th first-decision DECLINE with the same reason code under one mandate version (`n` from `settings`; step-up declines and expiries do not count, the user answered those; the outcome is never changed by it). On that code, or when the agent's searches find nothing that fits, the agent shows the user what happened and offers a new draft: the declines' amounts and reason codes come from the backend, and any price the agent saw on the web is labelled merchant-reported and unverified. The change goes through the version diff and the confirm screen, loosening shown as such, never applied from chat. Contracts: the `draft_mandate` request and response (the draft, `ready`, the checklist result with missing items by name, the draft's version; idempotent by a draft key the harness generates once per draft, like `purchaseKey`), the advisory decline-count reason code, the harness's drafting and readjustment conversation as a required test with scripted turns.
- **Rule catalogue:** each rule with precise semantics and reason codes (limits with the foreign-currency margin, the ceiling for connector quotes with its components, budget periods, purchase count, duplicate, split order, velocity, the counting rule, the cart evidence tiers of ADR-0007 and ADR-0008, the offer pick rule for item specs, the minimum order and slot-in-window rules, the connector-state, toggle, account-linked and mandate-names-the-link rules, the agent-card route rule with the one-line mode, the first-run STEP_UP for a merchant-derived list (reason code, not mapped through "when unsure"), the merchant-derived list rule itself (`k` of the last `n` orders), the step-up expiry per decision, the intent check questions and thresholds), and the caution combiner.
- **Data model:** tables per module schema, keys, the unique constraints that carry idempotency and single-use run claims, the audit table and its replay record, the `profiles` tables with version ids as the only foreign reference, the encrypted account-link tokens, the views the hook responder reads, retention.
- **Contracts:** the MCP tools as JSON schemas (a proposal line as item id or item spec; no slot, no personal data); the **connector manifest schema** and the admission checklist, publishable to merchants (tool classes, canonical tool hashing, the order-reference requirement, the payment-method read, the authorisation lag); the `MerchantAccount` port and the pure `ceiling` and slot-pick functions; the connector gateway's contract (manifests it reads, the per-call check, the discovery tool pass-through, the ingest log); the backend's OpenAPI (agent side, cardholder side including profile, channels, connector toggles and account links, console side including connector approval and enablement, the run claim); the event catalogue with payloads and versions (`MandateFulfilled`, `CheckoutOutcomeUnknown`, `RunClaimed`, `ProfileChanged`, `ConnectorToggled`, `AccountLinkChanged`, `ConnectorStateChanged` included; where shared event types live); every port in `control-core` with inputs, failure modes and idempotency (`Notifier` included; the connector adapters behind `Checkout` and `MerchantCatalogue`); the trace and conversation ingest with its chat and watch quotas; the audit export format (JSON Lines per event plus a per-purchase summary).
- **Keeps from ADR-0002:** pure core with ports; the flow order; the caution combiner; agent identity from the credential, never from the body. `ScenarioSource` is a test adapter, not a core port.

- **Answers the questions the hackathon left open** (they block T-018 and T-026):

  2. Where does the idempotency key come from in that format?
  3. After APPROVE, what do we return, to whom, and who executes the payment?
  4. How long does a single-use authorisation stay valid (this also sets the ask expiry, T-023/T-025, which must be configurable)?
- **Keeps from ADR-0004:** non-custodial; single-use credential bound to the decision; the route chosen by fixed rules before the checkout session, recorded and re-validated by the decision (ADR-0006); "we decide, the issuer executes" wording.

## Settled decisions
- Payment networks are sandboxed or simulated, never live money (2026-10-14). Synthetic and sandbox data only, opaque tokens, never a PAN.
- ~~Shopping agents are external third-party platforms; we build none.~~ Replaced 2026-10-29: we build the shopping agent (the agent harness), because a pure MCP provider cannot own the step-up and the approved purchase. Other agent hosts can use the same MCP server later. A scripted driver remains a test harness.
- Users cannot install MCP servers or tools into the agent (2026-10-31). Merchants with their own API or MCP server are admitted by the operator (us, or the bank for its deployment) as reviewed connector manifests; users turn connectors on and off and link their own accounts from the app; the agent gets the catalogue tools only, through our gateway; the backend quotes and orders after a decision (ADR-0008). Checkout "only through the networks' protocols" became "through the networks' protocols or an admitted connector"; form filling and browser automation stay out.
- The mandate compiler is an LLM that turns words into hard, structured rules, shown back and applied only after confirmation. The LLM is never in the pure decision core; the intent model answers typed questions outside it and can only add caution (ADR-0007). OpenRouter with a very small budget (~$9.40 total, 2026-10-17).
- Mandate drafting (2026-10-31): the agent drafts and judges when a draft is **ready** to search accurately on; the backend judges only whether it is **enforceable** (a fixed checklist over the generic schema, no category templates); the user confirms. Neither judgement is a permission. The agent may search before a draft is ready; repeated declines for one reason lead to a readjustment offer through the confirm screen (T-003).
- No ML risk model early: a `RiskSignal` port with heuristics (invariant 2 keeps it safe to add one later).
- The Leash case is inspiration only: no code, docs or design reused from the `leash` repo.
- Deployment to the Pi is optional and a later epic; local `docker compose` first.
- By 26 Dec 2026: a working proof of concept outside any bank (sandbox cards, Visa live sandbox, Mastercard simulated, our demo shop, the control layer, the audit export, the M16 benchmark). The date may cut scope, never the quality bar.
