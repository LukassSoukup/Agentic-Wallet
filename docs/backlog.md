### Definition of ready (for every implementation item T-007 creates)
An item may start only when a developer can build it without asking anyone:
- it names its module and deployable (the modules of ADR-0006 as amended by ADR-0010, [03-modules](architecture/03-modules.md)) and the feature ids it serves;
- the aggregates, value types and state transitions it touches are specified in `docs/domain/` (T-003, T-039);
- every port, REST endpoint, MCP tool, event and table it adds or uses has a written contract: shape, failure modes, idempotency, versioning (T-039, T-041, T-005);
- the rules it implements are in the rule catalogue (T-040) with their edges (at the limit, one cent over, foreign currency, duplicate delivery, injected text, pending step-up);
- its tests are listed: unit per rule, property tests where money or the combiner is touched, the concurrency, crash and replay tests of [06-consistency](architecture/06-consistency.md) it touches, the contract suite of each port it implements, Testcontainers for each DB adapter;
- it fits in one PR, and its acceptance is a replay of labelled cases or an observable check;
- every open question it depends on is closed or has a labelled stand-in.

#### T-039 Mandate schema and drafting
- **Mandate schema:** exactly what a mandate can express (budget and period with time zone, its amounts in the currency the user confirmed them in, which a later change of base currency never changes (ADR-0010), merchant lists, item requirements as structured facts, item spec categories with their validated values and time zones, quantity, purchase count, timing and run frequency, expiry, the strict-or-inclusive limit, the profile entries it may use, the linked account it may order through, the substitution policy and slot window, the "when unsure" policy with the standing-mandate default) and how a tightening is told apart from a loosening (adding a traveller or a linked account is a loosening).
- **Mandate drafting (decided with the user, 2026-10-31):** the agent drafts, the backend checks, the user confirms. A draft carries two states. **Enforceable** is the backend's fixed checklist per mandate kind over the generic schema above, settled by T-039; for example: amount and currency, period or expiry, scope as merchants, categories or an item spec, requirements as structured facts where the scope needs them; for a standing mandate also its run frequency, purchase count and either an item list or an item spec (a flight price watch has a spec and no list), and a reachable notification channel at confirmation. A draft with missing items is stored and `draft_mandate` returns them by name so the agent asks the user about exactly those ("what I usually buy" without items or categories is a missing scope item); the backend refuses to confirm a draft with missing items, as a named error. **Ready** is the agent's own assertion, sent with the draft, that it understands the request well enough to search accurately; the harness prompt instructs the agent to maintain it, `mandates` stores and audits it with the draft, and nothing in the backend branches on it. It gates only the agent's own choice between going back to the user and going on to a targeted search. Neither state is a permission: the confirm screen renders the enforceable draft and the decision never reads `ready`. No category templates beyond the item specs that exist where merchant data is structured. The shopping tools do not depend on a mandate, so the agent may search before a draft is ready to learn the market; only `propose_purchase` needs an active mandate. **Readjustment:** `decisioning` adds an advisory reason code to a first-decision DECLINE when the count of earlier first-decision DECLINEs with the same reason code under the same mandate version has reached `readjustAfterDeclines` (from `settings`; step-up declines and expiries do not count, the user answered those); the code stays on every later such DECLINE, a new version starts the count again, and the outcome is never changed by it. The count is read from `decisioning`'s own decisions in the decision transaction, under the per-mandate lock the ledger already takes, and recorded in the `DecisionInput` so the decision replays. On that code, or when the agent's searches find nothing that fits, the agent shows the user what happened and offers a new draft: the declines' amounts and reason codes come from the backend, and any price the agent saw on the web is labelled merchant-reported and unverified. The change goes through the version diff and the confirm screen, loosening shown as such, never applied from chat. Contracts: the `draft_mandate` request and response (the draft, `ready`, the checklist result with missing items by name, the draft's version; idempotent by a draft key the harness generates once per draft, like `purchaseKey`: the same key with the same content returns the stored response, the same key with changed content creates the next version of that draft, unique on agent instance, draft key and version), the advisory readjustment reason code, the harness's drafting and readjustment conversation as a required test with scripted turns.

**At the end we have:**
- the mandate schema field by field, with types, validated values and time zones;
- the enforceable checklist per mandate kind, each missing item with the name `draft_mandate` returns for it;
- the tightening-or-loosening table over every field, which the version diff and the confirm screen follow;
- the `draft_mandate` request and response as a JSON Schema in `docs/contracts/`, with its idempotency by draft key and the versioning of drafts;
- the readjustment reason code and its counting, ready for T-040 to list;
- the drafting and readjustment conversation as scripted turns, the test the harness must pass.

- **From ADR-0006, ADR-0007 and ADR-0010:** checkout runs in the trusted backend; the token never reaches the harness; checkout only at the shop's own UCP or ACP endpoint from its discovery document, or through an admitted connector; how buyer and delivery data from `profiles` enter a session (country and postcode before the decision where the protocol allows, the full address after APPROVE); offer search for item specs through `MerchantCatalogue`; token terms as a pure function of the decision.
- **For standing mandates (V9):** a token is issued per approved run, so no long-lived instruction is needed; what 3-D Secure at redemption does to an absent user (the purchase lapses, ADR-0010); travel agencies that charge their fee apart from the fare (two charges, one decision, one token or two); airline sessions that live minutes against `PENDING_USER`.
- **For merchant connectors (V10, ADR-0008):** whether a connector merchant's ordering API accepts a provider token rather than the card on file.
- **Answers the four questions the hackathon left open, for the token flow** (they block T-018 and T-026):
  1. In what format does an agent deliver a purchase, and how is it identified? (A `propose_purchase` call under the agent session token; the agent session token is ours to issue, never the agent's.)
  2. Where does the idempotency key come from? (The harness's `purchaseKey` for the proposal; the attempt id for the provider call.)
  3. After APPROVE, what do we return, to whom, and who executes the payment? (The backend issues the token to the seller's provider profile and completes the checkout; the seller charges through the provider; the user's bank pays.)
  4. How long does a token stay valid? (the earlier of the stored checkout session expiry and the decision time plus the attempt window from `settings`; the step-up expiry follows, T-023/T-025, configurable.)
  The answers in brackets are ADR-0010's direction; T-005 confirms or corrects each against the preview.

## Settled decisions
- Payment networks are sandboxed or simulated, never live money (2026-10-14). Synthetic and sandbox data only, opaque tokens, never a PAN. Since 2026-11-19: the payment provider in test mode; no live money before the legal opinion (T-043).
- A standalone EU consumer app paying through provider tokens on the user's stored card, banks later (user, 2026-11-19, [ADR-0010](adr/ADR-0010-standalone-app-and-provider-payment-tokens.md)). No licence, no customer funds, no card data, no account the user must open and fund; one-time virtual cards rejected; each user's base currency from their location, EUR by default.
- ~~Shopping agents are external third-party platforms; we build none.~~ Replaced 2026-10-29: we build the shopping agent (the agent harness), because a pure MCP provider cannot own the step-up and the approved purchase. Other agent hosts can use the same MCP server later. A scripted driver remains a test harness.
- Users cannot install MCP servers or tools into the agent (2026-10-31). Merchants with their own API or MCP server are admitted by the operator (us, or the bank for its deployment; since 2026-11-19 us, banks later) as reviewed connector manifests; users turn connectors on and off and link their own accounts from the app; the agent gets the catalogue tools only, through our gateway; the backend quotes and orders after a decision (ADR-0008). Checkout "only through the networks' protocols" became "through the networks' protocols or an admitted connector", and on 2026-11-19 "through the shops' agent checkout protocols (UCP, ACP) at the shop's own endpoint, or an admitted connector" (ADR-0010); form filling and browser automation stay out.
- The mandate compiler is an LLM that turns words into hard, structured rules, shown back and applied only after confirmation. The LLM is never in the pure decision core; the intent model answers typed questions outside it and can only add caution (ADR-0007). OpenRouter with a very small budget (~$9.40 total, 2026-10-17).
- Mandate drafting (2026-10-31): the agent drafts and judges when a draft is **ready** for an accurate search; the backend judges only whether it is **enforceable** (a fixed checklist over the generic schema, no category templates); the user confirms. Neither judgement is a permission. The agent may search before a draft is ready; repeated declines for one reason lead to a readjustment offer through the confirm screen (T-003).
- No ML risk model early: a `RiskSignal` port with heuristics (invariant 2 keeps it safe to add one later).
- The Leash case is inspiration only: no code, docs or design reused from the `leash` repo.
- Deployment to the Pi is optional and a later epic; local `docker compose` first.
- ~~By 26 Dec 2026: a working proof of concept outside any bank (sandbox cards, Visa live sandbox, Mastercard simulated, our demo shop, the control layer, the audit export, the M16 benchmark).~~ Replaced 2026-11-19 (ADR-0010, the brief's PoC): by 26 Dec 2026 a working standalone application: Stripe in test mode (saved test cards and wallets, Shared Payment Tokens, 3-D Secure test cards, the token webhooks); our demo shop as a Stripe test seller accepting the tokens through a UCP-style session, labelled synthetic; the control layer, the audit export and the M16 benchmark; the cardholder web app with local accounts.
